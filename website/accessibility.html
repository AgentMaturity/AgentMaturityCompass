accessibility

You should be able to use AMC without relying on color or a mouse.

Last reviewed: 2026-06-16. This statement covers the website, the browser playground, the dashboard AMC generates, the local Studio, and the command-line output.

What we aim for

  • Website and generated dashboard: checks based on WCAG 2.2 AA for contrast, visible keyboard focus, skip links, and chart names.
  • Generated dashboard: Settings includes a high-contrast theme, and the onboarding dialog traps keyboard focus while open.
  • Generated dashboard heatmaps give score, target, gap, and confidence as text, and to screen readers as ARIA grid, gridcell, selected-state, and meter values.
  • Command line: color is never the only signal. Use NO_COLOR=1 or --no-color for plain output where supported.
  • Proof: accessibility claims should be backed by tests, not only screenshots.

What works today

  • Static pages have skip links and a visible keyboard focus.
  • Decorative canvases are hidden from assistive technology.
  • Charts in the playground and the generated console have names that screen readers can read.
  • The generated dashboard's secondary text now has more contrast, after an audit flagged it.
  • The generated dashboard can switch to a high-contrast theme for low-vision review.
  • The generated dashboard's question heatmap shows level, gap, and confidence as visible labels, so color is not the only signal.

Known limits

  • Interactive terminal prompts depend on terminal and screen-reader support.
  • Dense generated reports still need a person to review them with a screen reader and realistic data.
  • Automated axe checks do not replace testing by hand with a keyboard and assistive technology.

Feedback

Open an issue. Tell us the page, command, or file; the assistive technology and browser or terminal you used; what you expected; what happened; and any screenshot, terminal output, or axe report.
