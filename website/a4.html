A4 Forge (preview)

A4 Forge takes one AI agent from a written brief to a recorded deployment in four stages (Aspire, Assemble, Adapt, Activate), and no stage moves on until the people you name approve the exact version in front of them.

  • Preview
  • Current source build only, not in the published 1.1.1 release
  • Off unless AMC_A4_PREVIEW=1
  • Every record signed and self-reported

Who it is for

Teams in enterprises and regulated industries who must be able to show, later, how an agent came to be: who asked for it, what it was meant to do and never do, who approved each step, which exact bytes they approved, and what the operator says was deployed.

It is not a scoring tool and it does not judge the agent. AMC's maturity score is a separate feature. A4 keeps the record of the build; it never says the agent is safe, correct or lawful.

The four stages

Every stage runs the same eight steps: you answer its questions, AMC writes down how it understood them and you confirm, AMC explains the choices at your level, proposes a specification, people approve the direction, AMC builds, someone reviews, and people approve completion, which opens the next stage. A changed answer makes a new revision, and any open gate on the old one goes stale. The approval counts below are AMC's default workspace approval policy.

01 · CONCEPTUALIZATION

Aspire

What you do
Answer questions about the agent: the problem, audience, goals, success metrics, constraints, actions it must never take, risk tier and markets.
What AMC records
Your answers, AMC's reading of them as you confirmed it, and the brief as a numbered revision; its build writes the agent's context graph, quality specification and value contract draft, offline. A hypothesis leaves "proposed" only through a row the runtime wrote.
Gates
Direction and completion: one approval each, from someone other than the author and the requester.

02 · CREATION

Assemble

What you do
Say what the agent must do, how much autonomy it gets (advise only, or act with approval using the signed workspace tools), which tools and connectors, which model provider builds it, and the engineering path: native in Studio, or an external framework.
What AMC records
The build plan, one bounded native build session that you close and verify before review, and its runtime rows. On the offline stub provider the record says "tool pipeline observed on a stub model; agent behaviour not evaluated".
Gates
Direction: one approval. Completion: two distinct approvers, none of whom built it, then a separately approved effect that applies the reviewed resources as the agent's active manifest.

03 · CONTEXTUALIZATION

Adapt

What you do
State who the agent serves, its languages, jurisdictions, sector, data classes, retention, processors and deployment needs. Unknown facts stay unknown; AMC never guesses them.
What AMC records
A control plan compiled for those facts, which requirements apply and which are unresolved, a context probe run on the stub provider, and a conformance statement as counts, never a percentage. Its regulatory records are experimental: drafted by an agent, citations not yet fetched or legally reviewed, approved by no named expert.
Gates
Direction: two approvals. Completion: two approvals, one from a workspace auditor; that is an acknowledgement, not an expert review. An owner may record unresolved requirements as out of scope with a reason; they stay unresolved in the counts.

04 · COMMERCIALIZATION

Activate

What you do
Choose the target (Docker Compose or Helm), the host the deployed Studio answers on, lease scopes, routes, models, request and token caps, and your update, monitoring and rollback expectations.
What AMC records
A release draft; after approval, a signed release package with Compose or Helm files for your operator to run, the operator's deployment receipt, AMC's own reachability check kept apart from it, rollbacks and value claims. AMC never deploys.
Gates
Release approval (the direction gate) and completion: two distinct approvers each, and the release itself is a separately approved effect. Today the release approval is refused unless the Studio itself runs under Compose or Helm (see below).

What you get at the end

  • One hash-chained project record per agent in your workspace ledger: every answer, revision, gate request, decision, build, review and effect, each decision bound to the digest of what was approved.
  • The approved brief, build plan, compiled control plan and (when Activate can run) the signed release package, deployment plan and the operator's receipts.
  • A record you can check yourself: amc a4 verify recomputes every digest and signature under a trust list you choose, and amc a4 export writes the records into a signed .amcbundle that a verifier without your keys can check.

On a Studio that does not itself run under Compose or Helm, which is any laptop install, a walk ends after Adapt: Activate records its release draft and then refuses the release approval with A4_NOT_READY: not ready: deployment.same_host. Installing a package into another workspace is planned work (P2-40).

How to try it today

A4 Forge is only in the current source build: install AMC from source. The published 1.1.1 release (npm, GitHub, the install scripts) does not contain it. Without AMC_A4_PREVIEW=1 the A4 API answers 404 and every amc a4 command exits 1.

A Studio that is already running keeps the environment it started with, so stop it first and start it again with the flag:

# in your workspace
amc down
AMC_A4_PREVIEW=1 amc up

# the first console login is an OWNER; add the people who will approve
amc user init --username <you>
amc user add --username <second> --role OWNER,APPROVER
amc user add --username <third> --role APPROVER,AUDITOR

Sign in to the Compass Console at the address amc up prints and start a project on its A4 page; creating one needs a signed-in OWNER or OPERATOR. The stage steps run there, or through the same API routes. The command line reads projects and decides, completes and verifies them:

export AMC_A4_PREVIEW=1
amc approvals login --username <you> --token-file <new file>
amc a4 list
amc a4 guide <projectId>      # next action, head seq, and the exact approve command per open gate
amc a4 members <projectId> --member LOCAL_USER:<userId> --project-role approver \
  --session-token-file <file> --expect-head-seq <n>
amc a4 approve --gate <gateId> --expect-gate-seq <n> --expect-binding-digest <sha256> \
  --expect-readiness-digest <sha256> --reason "<why>" --session-token-file <file>
amc a4 complete <projectId> --stage <stage> --gate <gateId> --expect-head-seq <n> \
  --session-token-file <file>
amc a4 verify <projectId> --allow-unpinned --allow-unanchored   # integrity only, exit 2
amc down

Each approver runs amc approvals login with their own username and passes their own token file. A workspace APPROVER or AUDITOR decides only once added as a project member with amc a4 members; add them before requesting a gate, because a membership change supersedes open gates. Opening an effect gate and deciding its request is done in Studio or the API; the command line has no command for it yet. Without your own trust list, amc a4 verify reports integrity only and never "trusted".

These commands were run against the current source build on 14 November 2026 with three local users. Aspire, Assemble and Adapt completed; Activate stopped at its release approval as described above.

What it does not do yet

  • No independently reviewed claims. That lane needs a record from an issuer outside the workspace on the operator's trust list (P2-24, P3-21); until then every A4 claim is self-reported.
  • No real deployment target. Version 1 records only a same-host restart of the Compose- or Helm-hosted Studio that built the agent (P2-40). Compose is documented but not qualified; Helm passed its qualification checks locally only; the image is pinned by tag, not digest.
  • No expert-reviewed regulation. Adapt's regulatory records stay experimental until a named expert approves them (D-08), and reporting clocks are listed for classification, not enforced (P3-23).
  • No evaluation of the agent's behaviour. A build on the stub provider shows the tool pipeline ran; it says nothing about how the agent behaves.
  • No update enforcement. The release's update policy is signed and recorded; nothing enforces it yet (P2-34).
  • Not every step is on the command line. Creating a project, the stage steps and effect gates run in Studio or through the API.

Questions

Is my data sent anywhere?

A4 itself makes one outbound connection: the owner's token-less check of the host a deployment receipt names, at Activate. Its records stay in your workspace ledger. Free text that may hold personal data (personal context, brief free text, comments) is not stored in the ledger: it is encrypted in the project's own store, the ledger keeps a salted hash, and an owner can erase it by destroying the project key, which takes full effect once every older backup has been rotated out.

The build session runs on the model provider you pick: the stub provider is offline, while a hosted provider receives that session's prompts as any native AMC task would. Exports are plaintext so that a verifier can recompute every digest; keep them under your control.

What does a signature prove?

Who wrote a record and that it has not changed since. Never that what it says is true. Every record A4 writes is self-reported. To trust the signer you check the record under your own pinned trust list; without one, amc a4 verify reports integrity only.

Who approves?

The people you name in your workspace. The author of a revision, the person who requested a gate and the people who built it cannot approve it, and every approver must be a different user. Under the default policy, Aspire's gates and Assemble's direction need one approval; Assemble's completion and every Adapt and Activate gate need two, and Adapt's completion needs one of them to hold the AUDITOR role.

A second approver in the same workspace satisfies separation of duties, not independent review: every local user's key is minted under one workspace signing authority, so two local users are not evidence of two people. A workspace with exactly one user may approve its own one-approval gates on a non-regulated project, and the record marks that.

Can I use my own model?

For Assemble's build session, yes: answer the provider question with stub or provider:model, the provider one of openai, openai-responses, anthropic, deepseek, gemini, gemini-audio or ollama. A4 records whether a provider is configured, never its credential. Adapt's context probe always runs on the stub provider, and with a stub build, readiness reports model delivery as not evaluated.

The full reference, every refusal code and the API are in the A4 Forge guide.
