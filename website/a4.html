A4 Forge (preview)

A4 Forge walks one AI agent from a written brief to a recorded deployment in four stages: Aspire, Assemble, Adapt and Activate. A stage moves on only when the people you name approve the exact version in front of them.

  • Preview
  • Current source build only, not in the published 1.1.1 release
  • Off unless AMC_A4_PREVIEW=1
  • Every record signed and self-reported

Who it is for

Teams in large companies and regulated industries who must later show how an agent was made: who asked for it, what it should and should never do, who approved each step, exactly which version they approved, and what the operator says was deployed.

It does not score or judge the agent. AMC's score is a separate feature. A4 keeps the record of how the agent was built. It never says the agent is safe, correct or lawful.

The four stages

Every stage runs the same eight steps. You answer its questions. AMC writes down how it understood them, and you confirm. AMC explains the choices in plain terms and proposes a plan. People approve the direction. AMC builds. Someone reviews. People approve completion, which opens the next stage. If you change an answer, AMC makes a new version, and any open approval (gate) on the old one lapses. The approval counts below are AMC's default rules.

01 · CONCEPTUALIZATION

Aspire

What you do
Answer questions about the agent: the problem, audience, goals, success metrics, constraints, actions it must never take, risk tier and markets.
What AMC records
Your answers, AMC's reading of them as you confirmed it, and the brief as a numbered version. Its build writes, offline, a map of the agent's context, a quality plan and a draft of the value it promises. A guess stays "proposed" until the running system writes a record that settles it.
Gates
Direction and completion: one approval each, from someone who did not write it or ask for it.

02 · CREATION

Assemble

What you do
Say what the agent must do, how much autonomy it gets (advise only, or act with approval using the signed workspace tools), which tools and connectors, which model provider builds it, and the engineering path: native in Studio, or an external framework.
What AMC records
The build plan, one limited build session in Studio that you close and check before review, and the records it wrote while running. On the offline stub provider, a stand-in model, the record says "tool pipeline observed on a stub model; agent behaviour not evaluated".
Gates
Direction: one approval. Completion: two different approvers, neither of whom built it. Then a separate approval puts the reviewed parts into use as the agent's active setup.

03 · CONTEXTUALIZATION

Adapt

What you do
Say who the agent serves, its languages, legal regions, sector, kinds of data, how long data is kept, who processes it and where it will run. Facts you do not know stay unknown. AMC never guesses them.
What AMC records
A plan of controls built for those facts, which rules apply and which are still open, a test run of the agent's context on the stub provider, and a count of rules met, never a percentage. Its legal records are experimental: an AI agent drafted them, nobody has fetched or legally reviewed the citations, and no named expert has approved them.
Gates
Direction: two approvals. Completion: two approvals, one from a workspace auditor. That approval only acknowledges the work; it is not an expert review. An owner may mark open rules as out of scope, with a reason. They still count as open.

04 · COMMERCIALIZATION

Activate

What you do
Choose the target (Docker Compose or Helm), the address the deployed Studio answers on, what access it gets and for how long, routes, models, limits on requests and tokens, and how you expect to update, watch and roll back.
What AMC records
A release draft. After approval: a signed release package with Compose or Helm files for your operator to run, the operator's signed note that it was deployed (a receipt), AMC's own separate check that the address answers, rollbacks and value claims. AMC never deploys.
Gates
Release approval (the direction gate) and completion: two different approvers each. The release itself needs its own approval. Today AMC refuses the release approval unless the Studio itself runs under Compose or Helm (see below).

What you get at the end

  • One project record per agent in your workspace log (ledger), each entry linked to the one before it. It holds every answer, version, approval request, decision, build, review and change. Each decision is tied to a fingerprint (digest) of exactly what was approved.
  • The approved brief, build plan, compiled control plan and (when Activate can run) the signed release package, deployment plan and the operator's receipts.
  • A record you can check yourself. amc a4 verify recomputes every fingerprint and signature against a trust list you choose. amc a4 export writes the records into a signed .amcbundle file that someone without your keys can check.

Any laptop install runs Studio outside Compose or Helm. There, a project ends after Adapt: Activate records its release draft and then refuses the release approval with A4_NOT_READY: not ready: deployment.same_host. Installing a package into another workspace is planned (P2-40).

How to try it today

A4 Forge is only in the current source build. Install AMC from source. The published 1.1.1 release (npm, GitHub, the install scripts) does not have it. It is off unless you set AMC_A4_PREVIEW=1; without it the A4 API answers 404 and every amc a4 command exits 1.

A running Studio keeps the settings it started with, so stop it and start it again with the flag:

# in your workspace
amc down
AMC_A4_PREVIEW=1 amc up

# the first console login is an OWNER; add the people who will approve
amc user init --username <you>
amc user add --username <second> --role OWNER,APPROVER
amc user add --username <third> --role APPROVER,AUDITOR

Sign in to the Compass Console at the address amc up prints. While the workspace has no project, Home shows a card “Start an agent project”; creating one needs a signed-in OWNER or OPERATOR. Name the project, or press Use an example to fill in a sample project. It is marked “(sample)” so the records show it is sample data.

Each project page opens with a What to do now panel. It shows the four stages, the current step, one sentence on what is needed, and one button that takes you to the right control or presses it (Studio checks every action again). Every empty answer field shows an example, and on Aspire, Assemble and Adapt Use an example fills the empty fields with answers marked “(sample)” that you can change before saving. While an approval is open, a Who must approve block shows how many different people must approve, the role they need, who may not approve (because they wrote, asked for or built it), who has approved so far, and the command that adds a person. At Activate on a laptop, the panel has no button and says this is where the preview stops on this Studio.

You run the stage steps in the console or through the API. The command line can read projects, approve, complete and check them:

export AMC_A4_PREVIEW=1
amc approvals login --username <you> --token-file <new file>
amc a4 list
amc a4 guide <projectId>      # next action, head seq, and the exact approve command per open gate
amc a4 members <projectId> --member LOCAL_USER:<userId> --project-role approver \
  --session-token-file <file> --expect-head-seq <n>
amc a4 approve --gate <gateId> --expect-gate-seq <n> --expect-binding-digest <sha256> \
  --expect-readiness-digest <sha256> --reason "<why>" --session-token-file <file>
amc a4 complete <projectId> --stage <stage> --gate <gateId> --expect-head-seq <n> \
  --session-token-file <file>
amc a4 verify <projectId> --allow-unpinned --allow-unanchored   # integrity only, exit 2
amc down

Each approver runs amc approvals login with their own username and their own token file. A workspace APPROVER or AUDITOR can decide only after you add them to the project with amc a4 members. Add them before you ask for an approval, because changing members cancels open approvals. Approvals that put a change into use are opened and decided in Studio or the API; the command line cannot do that yet. Without your own trust list, amc a4 verify only checks that nothing changed and never says "trusted". It exits 2 only when you give every allow flag that applies. A new workspace needs both --allow-unpinned and --allow-unanchored; with one missing it exits 1 and names the missing flag.

These commands were run against the current source build on 14 November 2026 with three local users. Aspire, Assemble and Adapt completed; Activate stopped at its release approval as described above.

What it does not do yet

  • No claims checked by someone independent. That needs a record signed by someone outside the workspace whom the operator trusts (P2-24, P3-21). Until then every A4 claim is self-reported.
  • No real deployment target. Version 1 records only a restart, on the same machine, of the Compose- or Helm-hosted Studio that built the agent (P2-40). Compose is documented but has not passed AMC's qualification checks. Helm passed them, but only locally. The image is pinned by tag, not by digest.
  • No expert-reviewed regulation. Adapt's legal records stay experimental until a named expert approves them (D-08). Reporting deadlines are listed for reference, not enforced (P3-23).
  • No test of how the agent behaves. A build on the stub provider shows the tools ran. It says nothing about how the agent behaves.
  • No update enforcement. The release's update policy is signed and recorded; nothing enforces it yet (P2-34).
  • Not every step is on the command line. Creating a project, the stage steps and approvals that put changes into use run in Studio or through the API.

Questions

Is my data sent anywhere?

A4 itself makes one outside connection: at Activate, the owner's check, with no token, that the address in a deployment receipt answers. Its records stay in your workspace log. Free text that may hold personal data (personal context, free text in the brief, comments) is not kept in the log. It is encrypted in the project's own store, and the log keeps only a salted fingerprint. An owner can erase it by destroying the project key. That takes full effect once every older backup has been replaced.

The build session runs on the model provider you pick. The stub provider is offline. A hosted provider receives that session's prompts, as with any AMC task. Exports are not encrypted, so that a checker can recompute every fingerprint. Keep them under your control.

What does a signature prove?

Who wrote a record, and that it has not changed since. Never that what it says is true. Every record A4 writes is self-reported. To trust the signer, check the record against your own trust list of keys you chose in advance. Without one, amc a4 verify only checks that nothing changed.

Who approves?

The people you name in your workspace. Whoever wrote a version, asked for the approval or built the work cannot approve it, and every approver must be a different user. By default, Aspire's approvals and Assemble's direction need one approval. Assemble's completion and every Adapt and Activate approval need two, and for Adapt's completion one of them must have the AUDITOR role.

A second approver in the same workspace keeps duties apart, but is not an independent review. Every local user's key comes from the same workspace, so two local users do not prove two real people. A workspace with only one user may approve its own one-approval steps on a non-regulated project, and the record says so.

Can I use my own model?

For Assemble's build session, yes. Answer the provider question with stub or provider:model, the provider one of openai, openai-responses, anthropic, deepseek, gemini, gemini-audio or ollama. A4 records whether a provider is set up, never its credential. Adapt's context test always runs on the stub provider, and after a stub build, the readiness report lists model delivery as not evaluated.
