### p.53 — Close of Section 4 metatheory
- Completes the proof that the lifecycle relation has **unique normal forms**: episodes are sorted/made contiguous by induction; two enumerations linearizing the order differ only by transpositions of incomparable episodes (Lemma 71 leaves endpoints unchanged); with termination (Theorem 66), quiescent states agree.
- **Failure** is explicitly excluded: whether a step raises depends on the state, so one schedule may fail a fiber another completes; the two quiescent states differ *only* in that fiber's lifecycle state (Corollary 62 puts a failed fiber's state contribution at nothing).
- Payoff: an orchestrator that adds/removes/replaces components arrives at the same state as writing the final composition down at the outset — a Cordis app can be reasoned about as **statically assembled**. Guarantee covers *state*, not *emissions* (foreshadows §6.1 acquisition vs. emission).

### 5. Implementation — Cordis
Cordis is a **meta-framework** of spatiotemporal composability (no domain; only universal dynamic composition semantics), in three tiers: (1) **core library** (§5.1) implements effect/coeffect systems; (2) **component loader** (§5.2) adds config reconciliation + HMR; (3) app frameworks like **Koishi** (§5.3) build domain features on top.

### 5.1 Core Library — Table 2 theory↔runtime map
`ctx` = first-class context; `ctx.effect(callback)` = effectΓ; symbol-keyed slots `ctx[@@store]`, `ctx[@@isolate]`, `ctx[@@intercept]` = Σ, Σ^iso, Σ^inter; `ctx.get/set/isolate/intercept` = the coeffect ops. A **fiber** = component instantiation ⟨d,p,e,π,σ,τ,θ⟩ with fields `uid`, `inject` (d), `provide` (p), `apply` (e), `parent.fiber.uid` (π), `ctx` (derived child context), `state` (θ; LOADING doubles as Reloading, FAILED = Inactive(ξ)), `dispose` (recover accumulator), `committed` (view ω), `target` (recomputed by refresh; ⊥ = INACTIVE), `inertia` (in-flight transition handle). O-Insert/O-Retire = `ctx.use` and its callback's inverse; L-rules map to `execute`'s loop, `guard` failure, `refresh` marking UNLOADING, `unload` + inertial chaining.

**5.1.1 Effect tracking (Algorithm 1).** Every context mutation flows through the single primitive `ctx.effect` — provision, instantiation, everything — so all mutations are auto-tracked and recovered on unload. It takes an effect-iterator callback (plain effect = degenerate iterator yielding one inverse); `execute` drives the iterator, composing inverses `f∘g` (prepend ⇒ **LIFO recovery**), consulting a caller-supplied **guard before each step** — guard trip stops iteration keeping accrued inverses (the step-boundary interruption / Maybe continuation). `ctx.effect` adds: (a) **self-disposal** via an `armed` flag — dispose flips it, halting in-flight iteration and making recovery fire at most once; (b) **parent composition** — dispose is prepended to `ctx.dispose`, so a child effect's inverse is itself an effect on the parent (recursive ∂²Γ). The runtime does **not verify** that an inverse actually recovers its effect — that is an obligation on the component author (delimited in §6.1).

**5.1.2 Coeffect operations (Algorithms 2–3).** Two-layer resolution k → ρ(k) → σ(ρ(k)): `get` reads realm symbol from `@@isolate` then value from `@@store`; `@@intercept` is consulted only at access, reshaping use not resolution. `ctx.set` is itself a `ctx.effect` (auto-tracked); install and removal both call `notify`. `notify` scans live fibers: if a changed key is in `fiber.inject` and resolves to the same realm, `refresh(fiber)` — reactive (de)activation; refresh idempotence makes neutral changes harmless. A binding counts only while its provider fiber is **ACTIVE**, so a provider entering UNLOADING is visible to dependents **one step before** teardown — they begin their own teardown while bindings are still in place. `isolate`/`intercept` derive a child context adjusting one table; recovery is implicit (discard the child), no inverse needed.

**5.1.3 Component lifecycle (Algorithms 4–5).** `ctx.use(component, config)` builds a fiber (binds config into `fiber.apply`) and tracks a `callback` effect in the **parent** fiber: executing it calls `refresh(child)`; its inverse forces target←⊥ and unloads — so instantiation is an ordinary tracked parent effect and unloading a parent **cascades to children**. `refresh` recomputes `fiber.target` from the store; if not mid-transition, spawns `reload` or `unload` (inertial: once entered, a transition runs to completion — mutual recursion `reload`↔`unload` chains when target changed meanwhile). `reload`: commit resolved view, run `execute(fiber.apply, guard: target unchanged)`, prepend recover to dispose; if target still matches → ACTIVE + notify provided keys, else chain to unload. `unload`: **first await all notified dependents' inertia** (drain dependents, line 25 — guard on L-Unload), then run dispose (LIFO), reset, and either INACTIVE or chain to reload. `fiber.target` digests bindings **by provider uid**, not value — fresh never-reused uids mean a replaced provider is never mistaken for its predecessor; a provider overwriting its own binding in place is *not* observed (must withdraw + reinstall to propagate). Two levels: transition-level chaining + iteration-level guard checks = inter-transition chaining and intra-transition staleness (Theorem 64). Coeffect ordering (Theorem 63) hangs on three lines: commit view at reload L14; UNLOADING marked before the task exists (L-Leave); dependent-drain wait ahead of the whole recovery. Termination per Theorem 66; provider graph traversed on demand.

**5.1.4 Context access (Algorithm 6).** Besides reflective `ctx.get/set`, **property access** `ctx[key]` via a TypeScript **Proxy** get-trap: walk the fiber chain upward; return from the first fiber whose *committed view* binds the key; a fiber declaring but not committing key ⇒ `INACTIVE_ACCESS`; root reached ⇒ `UNDECLARED_ACCESS`. Reads the view, not the store — keeps a dependency readable during teardown (Theorem 63) and enforces the declared coeffect spec d at point of use. This runtime check is in principle compile-time detectable (§6.4: type-level declarations + metaprogramming).

### 5.2 Component Loader
Core serves *component developers*; the loader serves *application orchestrators* via a **declarative configuration** the loader realizes as fibers.

**5.2.1 Entries & reconciliation.** **Definition 74**: an entry records `id` (reconciliation key), `url` (module), `isolate`, `intercept`, `config`, `disabled`. An entry is a faithful spec because the support set (Def 67) reads exactly τ,π,d,p, all derivable from the entry. Entries form a **configuration tree**; `@cordisjs/group` loads child-entry lists, `@cordisjs/include` grafts external YAML/JSON files — both ordinary components on the registration primitive. **Reconciliation** is incremental, justified by metatheory: Theorem 73 (quiescent state a function of final config alone), Theorem 66 (quiescence), Corollary 62 (departing fiber contributes nothing), Theorem 63 (**no load order to arrange** — dependencies gate activation, not module fetch, so modules load concurrently). Per-field least-disruptive dispatch: `id`/`url` → rebuild; `isolate` → realm reassignment (Alg 7); `intercept` → in-place (read-time); `config` → handed to component to diff (group entries apply keyed diff over child ids, recursing); `disabled` → unload/reload. **Managed realms**: `isolate: true` = local realm tagged by entry id (travels with the entry); string = global shared realm; realms discarded when unreferenced. Alg 7 uses per-key **delimiter symbols δ_k**: a fresh tag on the entry's context, inherited by descendants, identifies "derived from this entry" (eq. 65); contexts satisfying `own` move realms with the binding; dependents are notified exactly when the move separates them from/joins them to the binding.

**5.2.2 HMR (Algorithms 8–10).** Revertible effects at **module level**: since a fiber bounds all a component's effects, replacement = dispose old fiber + instantiate from reloaded module — **no developer-annotated acceptance boundaries** (vs Webpack/Vite HMR). `@cordisjs/hmr` runs three phases: (1) **classify** stashed (changed) vs externals (non-replaceable) — fixed point: a module is accepted once one import is accepted, declined once all imports are declined; import-cycle leftovers default to declined; (2) **stale-entry detection** — walk each entry's transitive imports respecting declined as boundary; stale iff tree ∩ accepted ≠ ∅, folding the tree into accepted; (3) **transactional reload** — invalidate caches (both ESM and CJS on Node) with backup, dispose + re-`use` each stale entry; on any import failure, restore caches and rebuild every stale entry from backup — **never a half-reloaded state**.

### 5.3 Case Study: Koishi
Open-source chatbot framework on Cordis (v3; paper presents v4, same compositional core), **4000+ community plugins** over four years. (1) **Expressive/general**: every Koishi feature is a plugin over §5.1 primitives; the web console is a *second, independent* Cordis app composing browser primitives — the model presupposes no domain or runtime. (2) **Temporal composability without cognitive overhead**: plugins disabled from console have effects withdrawn in place; HMR re-applies edited plugins on save preserving caches/live connections; inexperienced authors get ordered cleanup **without writing uninstall paths** — locality-of-concern discharged once by the abstraction. (3) **Spatial composability across an open ecosystem**: genuine dependency topology (IM adapters, DB drivers, functional plugins declaring coeffects); switching a storage backend reactivates only dependents whose resolved dependency changed; unavailable deps ⇒ inactive, not erroring; holds across independently authored code coordinating only through coeffects. **Threats to validity**: single ecosystem/host language; observational, existence-and-adoption result, not quantitative; overhead/productivity measurement is future work.

### 6. Discussion (start)
**6.1 System boundary**: inside = locations the system modifies exclusively and can restore (tracked in Γ, recoverable); outside = tracked as id_Γ. Coeffects **move the boundary** by reifying an external location behind invertible operations. Boundary is per-location, not per-medium. **Acquisition vs. emission**: acquisition installs a revertible record inside (open/close, malloc/free, fork/kill) and is the channel; emission (write bytes, send datagram) crosses the boundary as id_Γ. Recovery from emissions: **withholding** (output-commit problem) or **compensation** (coarser equivalence; LIFO composition transfers but commutation metatheory must be re-proved). **6.2 Service multiplexing**: OSGi-style services = interface behind a key; **exclusive binding** (swap perturbs consumers) vs **service broker** (injected by providers and consumers; absorbs provider updates, no reload). Broker enables **load balancing** (policy or consumer-named target; provider unload auto-drops from routing via revertible registration), **rolling updates** (load new provider, shift traffic, unload old — blue/green as application-level composition), **cross-process invocation** (per-process contexts, RPC-bridged remote providers, must be async-contract). **6.3 Access control/sandboxing**: `inject` declarations + proxy mediation ≈ **capability-based security** — static declarations let the orchestrator review the complete capability set at load time; **interception** adds fine-grained runtime policy (e.g., path-scoped filesystem, read-only DB for community components) living on the context, adjustable at runtime with no reload since it changes only invocation, not satisfaction. Untrusted code needs an external sandbox (SFI/process/container); the bridge is an ordinary fiber, attenuable by the same access control. **6.4 Language independence** (start): temporal composability needs closures + introducible/retractable module loading (module registries, dlopen/dlclose, Wasm embedder-dependent); spatial composability = DI, typed via typeclasses/traits/TS module augmentation, with runtime-mediated dynamic access.

**No agent-harness claims appear in these pages** — the material is entirely framework runtime semantics; nearest analogues are the capability/sandboxing (§6.3) and rolling-update (§6.2) discussions.
