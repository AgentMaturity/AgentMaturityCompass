Experimental purpose binding and restoration of protected values at egress (partial P2-02 source, slice 3). Tokenization reduces the identifiers that reach model context and logs; it is not de-identification or anonymization under any standard or regulation. The processor, PHI and card-data rules stay experimental until a named expert approves them, and contract references are operator declarations: neither a signature nor a receipt shows that a contract exists, is in force or is legally sufficient.

**Opt-in is unchanged.** Everything below applies only where the processor registry `.amc/dataflow/processors.yaml` or its `.sig` exists (latched per process, as redaction is). Workspaces that have not opted in are unchanged: authorization records keep `resource: { purpose: null, dataClasses: [] }`, `http.fetch` and native MCP calls send what they sent before, and model requests are not admitted.

**Registry.** Two optional, owner-signed fields: `runPurpose` names the purpose every tool call in the workspace serves (one per workspace; it must name a declared purpose), and `processors[].destinationIds` names the P2-01 destinations (`.amc/residency/destinations.yaml`) a processor operates (a destination has at most one processor). Existing registries parse and verify unchanged.

**Opted-in workspaces.**

- With a `runPurpose`, a bound call to a tool the purpose's `allowedTools` does not list is denied `purpose_violation` at authorization, before any approval is asked. The record's `resource` is `{ purpose, dataClasses }` from that purpose, never from arguments, model text or tool output, so residency checks of web and network tools apply the purpose's classes. The recheck denies `purpose_violation` when `resource` changed since bind. The purpose check runs wherever records bind: the tool pipeline, bridge hooks and ToolHub. MCP tool names (`mcp_<server>_<hash16>`), `run_code`, `delegate` and hook tool names must be listed to run.
- A registry that is missing after opt-in, or does not verify, denies bound calls (`authority_store_unavailable`) and refuses every model request with the registry's reason, even one with no detection.
- A model request needs a BAA route when its run purpose allows PHI or it holds an issued PHI token, even when every identifier is tokenized, because the rest of the text may still be PHI. The `PROTECTED_DATA_DETECTED` row then carries `declaredClasses`.
- `http.fetch` and native MCP calls whose arguments carry tokens pass through the new detokenization gate as their last step before sending. It restores values only for a call with a bound authorization record, whose purpose is the signed `runPurpose`, to a P2-01 destination a registry processor lists in `destinationIds`, when the purpose allows that tool, that processor and every class present and the processor holds an in-force covering contract per class (a BAA for `phi`). Nothing is decrypted before those checks pass. `http.fetch` restores JSON body leaves and headers that are one whole token, never the URL; MCP over HTTP restores argument leaves. Stdio MCP calls carrying tokens are refused. Echoed values in the response are turned back into tokens before the session sees them.
- Refusals are `DetokenizeRefused` (code `PROTECTED_DATA_EGRESS_REFUSED`, a definite failure: the journal records `completed/not_applied`) with the static reasons `processor_not_allowlisted`, `purpose_violation`, `token_unknown` (including another workspace's tokens), `payload_not_restorable`, `vault_unavailable`, `vault_integrity` and `receipt_failed`, and a `PROTECTED_DATA_EGRESS_REFUSED` ops audit row holding codes, IDs, classes and a count, never a value, token, URL or hash.

**New.** The `RecheckFailure` value `purpose_violation`; the public contract `detokenization-receipt` (`amc.detokenization-receipt/v1`, `spec/schemas/v1/detokenization-receipt.schema.json`), written before the send as the `receipt` of a `PROTECTED_DATA_DETOKENIZED` ops audit row (released, not delivered); and the two ops rows, which are enforcement bookkeeping, never maturity evidence.

**Deviations from the P2-02 issue.** Processors map to destinations in `processors.yaml` (`destinationIds`) instead of a new `DestinationRecordV1.processor` field, so the P2-01 schema is unchanged. The provider block for PHI sessions runs in model admission instead of `checkEgress`. The receipt lists every covering contract (`contractReferences`) and adds `destinationId` and `registryDigest`. Image and audio stay refused in opted-in sessions under every contract.
