A4 Activate prepares and records deployments, checks them and rolls them back, behind the A4 preview (`AMC_A4_PREVIEW=1`). AMC never deploys, holds no deployment credential and never merges the operator's statement with its own check.

- Each release package now carries the prepared deployment under `deploy/`: the Compose overlay `docker-compose.a4-<releaseId>.yml` or the Helm values overlay `values.a4-<releaseId>.yaml`, and `deploy/plan.json` (signed `a4-deployment-plan`) with the steps (pre-flight `amc doctor --strict --json`, deploy, verification, rollback), the receipt form and the gaps. The image is pinned by tag (`IMAGE_TAG_ONLY`) and a Helm topology is undecided (`TOPOLOGY_UNDECIDED`); both are WAITING and both targets are recordable. The Compose overlay puts `AMC_CONTROL_CHECKPOINT_DIR` on its own named volume outside the workspace; the chart cannot, and the plan says so. The chart renders a fixed environment list, so the Helm overlay cannot set `AMC_A4_PREVIEW=1` either: the Helm plan names the gap `A4_PREVIEW_NOT_SET_BY_CHART` and adds a step that sets it on the Studio container after the upgrade. The update policy is now `update-policy.yaml`, signed beside it with `A4_PACKAGE` (enforcement `none`, P2-34). The release record names the overlay digest and the prepared rollback commands.
- `POST /api/v1/a4/projects/:id/releases/:rid/deployments` (owner) records the operator's receipt (`amc.a4-deployment-receipt/v1`, signed `a4-deployment-receipt`, `self_reported`). Its fields are `kind` (`deploy`, or `rollback`), `environment`, `target`, `packageDigest`, `imageDigest`, `overlayDigest`, `restartedAt`, `helmRevision` (Helm only), `leaseIds`, `destinationRef` and `operatorStated.status`, and no free text. It is refused with `DEPLOYMENT_NOT_SAME_HOST` (P2-40) unless this Studio runs under the target. Other refusals are `PACKAGE_DIGEST_MISMATCH`, `LEASE_NOT_OF_RELEASE`, `TARGET_MISMATCH`, `DESTINATION_MISMATCH` (a deploy row naming another destination than the one the release was packaged for), `RELEASE_NOT_CURRENT`, `RELEASE_ROLLED_BACK` (a deploy row for a rolled-back release) and `OPERATOR_TIME_REFUSED`. A rollback row is recordable on a held or frozen project. No lease is issued and no runtime run is created. A succeeded production receipt moves `deployedReleaseId`, and so does a succeeded rollback row. Whoever records a deploy receipt counts as a builder of the revision, so they cannot approve the deployment approval that rests on it. `GET …/releases/:rid/deployments` lists the receipts in two columns, `recordedStatus` and `amcCheckStatus`, with a composed status text. The deployment receipt contract's `kind` now also takes `rollback`.
- `POST …/releases/:rid/verify { environment }` (owner) is AMC's token-less check of the newest receipt's `destinationRef` through `resolveAndCheck`. The connection is pinned, TLS verifies against the system CA set, redirects are refused, and the check is bounded at 5 s and 256 KiB. A receipt destination that is not the one the release was packaged for (its own revision's proposal, as `deploy/plan.json` records it) fails with `DESTINATION_MISMATCH`. A private, link-local or mapped destination is refused (409 `VERIFY_EGRESS_REFUSED`, naming the address), and nothing is recorded. `/readyz` READY gives `reachable`; a 503, a redirect, a refused certificate or a mismatch gives `failed`. Image, package and plan-head checks are `not_evaluated` until P2-40, so `passed` is unreachable in v1, and no probe turn runs. The row records the resolved address, the response digest and a VerifierReportV1 (signed `a4-amc-check`) that names the `/readyz` response it hashed, with `not_evaluated` as the digest when nothing was fetched. It never touches the operator's status.
- Rollback: `POST …/releases/:rid/rollback/preview` (owner) opens the effect gate `a4.activate.rollback` (DEPLOY, decided under A4's separation of duties). `POST …/releases/:rid/rollback` confirms the exact release and Enforce manifest the preview bound. It is journaled as an effect: `EFFECT_STARTED` commits first, pinned to `expectedHeadSeq`, and a second attempt while one runs is refused (`EFFECT_RUNNING`). It then consumes the grant, freezes first for a high or critical risk tier, restores the Enforce snapshot, and revokes every lease of the release, read again at that point (a production lease minted after the preview and a failed attempt's journaled lease included). It answers the prepared commands and writes a signed `a4-rollback-receipt`, then `ROLLBACK` and `EFFECT_FINISHED` in one transaction. A failed step is `EFFECT_FAILED` with its code, and a new request runs it again on the grant this rollback's execution consumed (`GRANT_ALREADY_USED` when another execution consumed it). A rollback is refused `EFFECT_RUNNING` while the deployment approval's production-lease effect runs, that effect refuses `RELEASE_ROLLED_BACK` while a rollback attempt has not settled, and the rollback reads the lease journal again before it settles. It may run on a held or frozen project. A rolled-back release is terminal for its cycle: `deployment.receipt` reads BLOCKED `RELEASE_ROLLED_BACK`. The lifecycle is never moved backwards.
- The lifecycle bridge advances the agent's lifecycle one stage at a time. After `RELEASE` it moves development → testing when the agent is still at development, then testing → staging. After the deployment approval's production lease it moves staging → production. It advances only when every bridge control has a ref, and records each control's ref, claim kind and reason; in v1 two production controls need P2-40, so the agent stays at staging. `recordDeployment` and `verifyDeployment` now take an owner.
- Activate readiness adds `deployment.receipt` (bound), `backup.include_paths` (not mandatory: the signed ops policy must back up `a4-releases/` and `a4-projects/`) and `lifecycle.production_controls` (not mandatory). `deployment.amc_check` is bound to the receipt and its newest check, so a later receipt or check stales an open deployment approval.
