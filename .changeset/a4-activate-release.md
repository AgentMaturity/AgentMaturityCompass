A4 Activate builds a signed agent package and records the release, behind the A4 preview (`AMC_A4_PREVIEW=1`). AMC never deploys: it signs, prepares and records.

- New sign kind `A4_PACKAGE` in both sign-kind lists and in both `requireNotaryFor` default copies (18 kinds in each list). The `requireNotaryFor` default applies only to a `trust.yaml` that omits the field. In NOTARY mode with the default `denyLocalVaultSigningIfNotaryEnabled: true`, `A4_RECORD` and `A4_PACKAGE` both route to the notary. An explicit list with that flag set to `false` needs `A4_PACKAGE` added and the file re-signed. AMC's own notary signs only the kinds its notary config lists in `allowedSignKinds`, and the default list names neither `A4_RECORD` nor `A4_PACKAGE`: add both there for NOTARY mode, or every A4 signature fails as `NOTARY_UNREACHABLE`. A4's checks of `A4_RECORD` and `A4_PACKAGE` signatures (a release record's `envelopeValid`, the packaged update policy, a value claim's envelope) accept the auditor key history or the notary the signed trust config pins, so a valid notary signature no longer reads invalid. New artifact kinds `a4-package`, `a4-deployment-plan`, `a4-deployment-receipt`, `a4-rollback-receipt` and `a4-amc-check`, and the transparency kind `a4-package`.
- Activate asks 27 questions: `deploymentNeeds`, carried from Adapt (`CARRIED_STALE:deploymentNeeds` when it no longer equals Adapt's); `target` (`compose` or `helm`), `destinationRef` (a host name and optional port from 1 to 65535), `leaseScopes`, `stagingRoutes`, `productionRoutes`, `modelAllowlist`, `budgetRequestsPerMinute` and `budgetTokensPerMinute` (required); `hostHint`, `executeActionClasses`, `accessRoles`, `accessNetworks`, `releaseOwner`, `onCall`, `budgetCostUsdPerDay`, `productionLeaseDays` (1 to 90, default 30), the update policy (`updateChannel`, `updateVersionPin`, `updateApproval`, `updateWindows`, `autoRollbackOn`), `businessOutcomes`, `sustainabilityObjectives`, `socialObjectives`, `monitoringExpectations` and `rollbackAcceptance`. Understand records the lifecycle stage and the controls staging and production require, the deploy base files, image identity, where this Studio runs (Kubernetes reads as `helm`, a Docker or Podman container as `compose`), freeze, both signing routes, the DEPLOY approval rule and earlier releases. Explain renders them at three levels. Propose records the release draft and copies the agent's prompt pack, context plugin, memory policy and signed configs into `a4-projects/<projectId>/<revision>/<sha256>`. Build at Activate has no producer and answers 409 `A4_PRODUCER_REGISTERED`: the release is Activate's build.
- `POST /api/v1/a4/projects/:id/releases { gateId, expectedHeadSeq, clientRequestId }` (owner) consumes the release approval, which is Activate's direction gate (any other gate is 409 `A4_STEP_ORDER`). It then runs the effect `a4.activate.release` inside the request; an owner opens that effect on the gate first (`EFFECT_GATE_NOT_OPEN` otherwise). The effect is a DEPLOY engine request decided separately, consumed by A4 as step 0. The package under `a4-releases/<projectId>/<releaseId>/` holds only content-addressed inputs. The Enforce snapshot comes from the bound resources digest, and each resource must equal the signed snapshot. Each captured file is read by the digest the gate bound. A missing input fails the effect with `INPUT_NOT_CAPTURED <slot>`, and an Enforce snapshot that does not verify fails it with its code. `RELEASE`'s own refusals (`RELEASE_STEP_MOVED`, `RELEASE_STAGE_REDONE`, `RELEASE_ATTEMPT_SETTLED`) are checked on the rows read then, before anything is minted or signed. The package must scan `PASS` for secrets (`SECRET_SCAN_FAILED` otherwise). Only then is the staging lease minted: `WRITE_LOW` at most, the staging routes, 24 hours, with the release as its work order. The manifest (`amc.a4-package/v1`) names the staging lease by id and scope (a new `leases` field; never a token), and is signed `A4_PACKAGE` in `manifest.sig`; the tarball is signed `a4-package`. A `RELEASE` transition moves Activate to `built` and records the release (`amc.a4-release/v1`). The record carries the eight-surface table, the previous and base release (TUNE lineage), the rollback target (the release running in production when it was built: the newest release with a succeeded production deploy row that was not rolled back, never merely the previous release), the staging lease id and its own `A4_RECORD` envelope. Only after `RELEASE` commits does the transparency log get an `a4-package` entry: `EFFECT_FINISHED` names it, a retry reuses the entry of the same release and package, and `GET …/releases/:rid` reads the entry from the log or says why it is missing. When the append fails, readiness item `package.transparency` (mandatory once a release exists, bound) is BLOCKED (`TRANSPARENCY_NOT_APPENDED`, or `TRANSPARENCY_LOG_UNREADABLE`) until an entry names the release's exact package digest, so the deployment approval cannot be requested; `POST …/releases/:rid/transparency { expectedHeadSeq, clientRequestId }` (owner, owner mode; a button on the Activate card) appends it idempotently and is refused `EFFECT_RUNNING` while the release effect runs. A refused release therefore attests nothing in the log; it revokes the lease it minted and removes its release directory and tarball files. The response carries the staging token once. The request's replay row stores only the attempt id. A replay answers from the chain: `token: null` with `TOKEN_ALREADY_DELIVERED` once that attempt finished, the attempt's own failure code when it failed, and 409 `EFFECT_NOT_SETTLED` while it has not settled. A retry revokes every lease an earlier attempt minted before minting again. An inline effect that fails after the gate was consumed answers its own code (409, or 423 `A4_VAULT_LOCKED`, including a locked lease key, artifact signature or grant read; a notary that cannot sign is `NOTARY_UNREACHABLE`) with the attempt and its retry route. The release and production-lease effects read the vault's `lease` and `revocation-list` purpose keys before their first side effect, so a locked vault fails them with `A4_VAULT_LOCKED` (and a revoked key with 409 `A4_KEY_REVOKED`) before anything is revoked, written, minted or signed (revoking an earlier attempt's lease included, which no longer answers `LEASE_REVOKE_FAILED` for a locked vault); a vault already locked when the request is sent is refused before the gate is consumed (`signing.available`, 409 `A4_NOT_READY`). `complete` and effect retries answer the same way for every inline effect.
- `GET …/releases` lists the releases; `GET …/releases/:rid` answers the record with its envelope checked now. Each lease shows its live `status` (`revoked`, `expired`, `active`, or `unknown` with `LEASE_REVOCATIONS_UNVERIFIED`) beside its `recordedStatus`. The eight-surface table names a reason for every surface not evaluated; Passport reads `not_evaluated` with P0-55. `GET /api/v1/a4/options` answers `imageDigest: null` with `imageDigestReason`.
- Completing Activate (the deployment approval) runs `a4.activate.production_lease` on that gate's own quorum and answers the production lease's token once. An owner that quorum counted cannot complete it (409 `SOD_VIOLATION`): the token goes to the caller, and an effect's quorum excludes its caller. A retry of a failed effect refuses the same way a caller its consumed grant or gate quorum counted. The lease takes the scopes, routes, classes and caps of the completion gate's own revision and the release recorded before that gate was requested, never newer answers or a newer release. It is refused with `PRODUCTION_LEASE_STALE` when the revision, step or current release moved since the consumption, `RELEASE_ROLLED_BACK` for a rolled-back release or one whose rollback has started (even an attempt that failed), and `EXPERT_REVIEW_PENDING` on a regulated project without D-21's acknowledgement. Then the lifecycle bridge to production runs (see the deploy changeset). A `DENY` on an unconsumed completion gate revokes the staging lease of the release that gate binds, and the response lists what it revoked. Such a `DENY` is refused, even in NOTARY mode, while the vault's `revocation-list` key that signs the revocation cannot sign: 423 `A4_VAULT_LOCKED` while the vault is locked, 409 `A4_KEY_REVOKED` while that key is revoked; a `DENY` on a consumed gate is refused `A4_GATE_STALE: consumed` first. When a revocation still fails, the `DENY` stands and the answer is 409 `LEASE_REVOKE_FAILED` naming the lease ids (423 `A4_VAULT_LOCKED` when the vault locked meanwhile, also on a replay sent while it is locked); sending the same request again retries the revocation.
- Activate readiness: `ask_complete`, `understanding_confirmed`, `release_proposed`, `package.inputs` (BLOCKED on `INPUT_NOT_CAPTURED:<slot>`, `ENFORCE_RESOURCES_NOT_PRODUCED` or `ENFORCE_SNAPSHOT_MISSING`), and `deployment.same_host`, which is BLOCKED `DEPLOYMENT_NOT_SAME_HOST` with `KEY:P2-40` unless this Studio runs under the chosen target. `deployment.topology` (`TOPOLOGY_QUALIFIED_LOCALLY_ONLY` for Helm, `TOPOLOGY_NOT_QUALIFIED` for Compose, each with `CI_QUALIFICATION_PENDING`) and `deployment.image_pinned` (`IMAGE_TAG_ONLY`) are WAITING and never mandatory. Also `package.transparency` (BLOCKED while the current release has no transparency entry), `lease.scope` (`LEASE_STAGING_ONLY`, then `LEASE_PRODUCTION`), `deployment.amc_check` (`DEPLOYMENT_UNCHECKED`; BLOCKED while the release's newest AMC check failed), `monitoring.source` (`MONITOR_NO_SOURCE`) and `regulatory_sources_status`. On a regulated project `regulatory_sources_status` is WAITING `EXPERT_REVIEW_PENDING` (`KEY:D-08`), mandatory from Review on, until an owner acknowledges it at Activate (D-21). The production lease effect records that acknowledgement; `GET …/releases/:rid` shows it as `expertReview`, and the Activate conformance statement lists it. Activate gates also bind `deployment.same_host`, `package.transparency`, `deployment.amc_check`, `lease.scope`, `monitoring.source` and `regulatory_sources_status`. An owner's acknowledgement records the receipt and check ids the item named and counts only while the item names the same ones. Activate's `regulatory_sources_status` and `deployment.amc_check` are acknowledged only from Review on, and the check only once it names a receipt; earlier, the acknowledgement could never count and is refused `A4_NOT_ACKNOWLEDGEABLE`. At Activate `signing.notary_route` carries `A4_RECORD:<route>` and `A4_PACKAGE:<route>`, and is BLOCKED (`CONFIG_UNTRUSTED`) when either cannot be read.
