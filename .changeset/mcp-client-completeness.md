Native MCP mounts now answer form elicitation, subscribe to resource updates and restart a stdio server that exits.

- Form elicitation (2026-07-28 multi round-trip requests): when the session has a human answerer for `ask_user` (for example `amc acp --ask-user`), a mount declares `elicitation: { form: {} }` on every request. Each server request becomes one signed question that names the server and shows its message escaped on its own delimited line, so server text cannot draw a fake prompt; offered enum choices must be single safe lines of at most 200 characters, with a choice to send or decline and one field per requested property. The answer must carry the workspace auditor signature and match the requested schema; AMC then retries the call as a new request with `inputResponses` and the server's exact `requestState`, at most three rounds. A decline, no answer, a timeout, an invalid answer, URL mode, sampling, roots or a nested schema ends the call with an `MCP_ELICITATION_DENIED` message, and nothing is sent to the server. Without a human answerer nothing is declared and `input_required` still fails closed.
- `subscribeResources({ uris, ttlMs, onUpdated })` on a stdio mount: reviewed resource URIs only, a lifetime of 1 s to 1 h, at most 8 per mount. 2026-07-28 servers get one `subscriptions/listen` per subscription, correlated by its request id; legacy servers get `resources/subscribe` and `resources/unsubscribe`. At expiry or close the stream is cancelled (or each URI unsubscribed) and the handler dropped. HTTP mounts refuse subscriptions.
- A stdio server that exits on its own is relaunched at most three times per mount with the reconnect backoff, and only under the same protocol and the pinned catalog digest. Every attempt writes an `MCP_STDIO_RESTART` audit row (`restarted`, `refused` or `exhausted`). A call in flight when the server exited is `TOOL_OUTCOME_UNKNOWN` and never replayed; live subscriptions are re-opened for their remaining lifetime. After the bound the mount closes as before.
