A4 Adapt runs AMC's own producers for the compiled plan, behind the A4 preview (`AMC_A4_PREVIEW=1`). Adapt asks 20 questions: `markets` and `stations`, carried from Aspire by Understand and marked `CARRIED_STALE:<id>` when they no longer equal Aspire's; `audiences` and `languages` (required); `workflows`, `preferences`, `accessibility`; the compiler's facts `jurisdictions` (depends on `markets`; left empty it uses the carried markets), `primaryStation`, `domains` and `useCases` (depend on `stations`), `roles` and `riskClass` (depend on `jurisdictions` and `markets`, since an empty jurisdictions answer takes the markets), `entityTypes` (depends on `jurisdictions`, `markets` and `stations`) and `dataClasses`; `excludedUses`, `dataResidency`, `dataRetention`, `processors` and `deploymentNeeds`. A fact answer is a list of catalog terms (or one term); an empty or `unknown` answer stays unknown (null). Understand builds the deployment profile (every fact `provenance: asserted`, source `a4:<projectId>@r<revision>`) and compiles it with `compilePlan`, recording the applicability per requirement with reasons and missing facts, each citation's `appliesWhen`, the register entries of the stations with `verified` as recorded, the reporting-clock candidates (all `NEEDS_CLASSIFICATION`, with `CLOCK_REVIEW_STATUS`), the signed configs' states and the active plan's head; a profile or catalog the compiler refuses is recorded by its code. Understand stamps an answer given before a carried question had any value at Adapt (and current then) against the values it carries, so the first carry does not mark it `ANSWER_STALE`; an answer given against another, earlier carried value stays stale. Explain quotes the catalog's notice verbatim (D-08) at every level. Propose freezes the profile, the plan, the diff against the project's previous proposal, the operating scope and the declared data handling (`enforcement: none`, P2-01, P2-02).

Build takes a workspace OWNER and a project owner, as at Aspire and Assemble, and so does Review at Adapt (it signs the control results with the workspace auditor key); Build signs the proposed plan with `signPlan` (`CONTROL_PLAN`, checked against this workspace's keys) and refuses a plan weaker than the plan this project put in force (`POLICY_WIDENING_REFUSED`). Review evaluates every requirement with `evaluateControl` over the admitted evidence (none is loaded yet, so each control is `not_evaluated` with `NO_EVIDENCE_LOADER`; a requirement whose control the shipped catalog no longer holds at that version stays listed, `not_evaluated` with `CONTROL_NOT_IN_SHIPPED_CATALOG`), writes the set signed with `writeSignedControlResults` to `a4-projects/<projectId>/control-results/<sha256>.json` (each directory created plain: a link or a file on the way is refused with 400 `PATH_NOT_PLAIN`), reads it back, and records the counts (`pass`, `fail`, `not_evaluated`, `not_applicable`, `unresolved`; never a percentage). Only a notary-route signature (`NOTARY_ROUTE_NOT_VERIFIED_LOCALLY`) and a workspace key the trust list does not pin (`ISSUER_NOT_PINNED`) are recorded `not_evaluated`; any other read-back failure (missing, changed, unsigned, a signature that does not verify, a distrusted or revoked signer, unparsable bytes or shape) makes the integrity item `adapt.control_results_signature` BLOCKED (`CONTROL_RESULTS_INTEGRITY_FAILED` with the code), and readiness checks the file again on every evaluation, so a set edited or deleted after Review blocks the same way. Review fails with the signing error's code when the set cannot be signed (agent mode, a locked vault). Review also records the `amc.a4-conformance-statement/v1` built from the stored, verified results (`src/a4/a4Conformance.ts`; its claim is the weakest of the envelopes rebuilt from those results, and an unverified set gives a not-evaluated one); an owner's out-of-scope acknowledgement of `plan_unresolved` lists the requirements in `ownerOutOfScope` while they stay in `counts.unresolved`. The conformance view reads that acknowledgement, the sources acknowledgement and the deferred-activation acknowledgement on the Adapt revision it describes as readiness counts them (one readiness ignores is not listed), and once that revision's completion gate is consumed it keeps the ones in force then, after they expire and after Activate records new revisions. Review's own record of the statement carries none of them: no acknowledgement that counts on the revision Review records exists yet.

Completing Adapt in a regulated project runs the new effect `a4.adapt.activate_plan` (`catalog.plan.activate`, `SECURITY`): an owner opens it once the completion gate has its quorum (opening any A4 effect now checks the opener's role and the gate's quorum before the engine request is filed), `signPlan` files the plan review (with the two-distinct-key floor when regulated), project approvers decide it from the A4 card, `complete` verifies the grant and re-checks membership and separation of duties without consuming it, and `activateControlPlan` consumes it as `activate-<digest32>`, which `EFFECT_FINISHED` records. A workspace has one active plan for every agent, so activation replaces it and refuses a plan weaker than it; another agent's active plan always makes this one weaker (its budgets drop), so opening the review is refused with 409 `PLAN_WEAKENS_ACTIVE_PLAN` before any gate is consumed. Understand and Review record the active plan's profile: only when another profile's plan is active and this plan weakens it (activation is then certain to be refused), as read at the plan journal head the head revision binds and unmoved since (until the completion gate is consumed), is a regulated project's activation deferred, and `plan_activated` then waits with `PLAN_ACTIVATION_DEFERRED`, `ACTIVE_PLAN_OF_ANOTHER_PROFILE`, `REPLACES_ACTIVE_PLAN`, `PLAN_WEAKENS_ACTIVE_PLAN` and `WEAKENINGS:<n>`, mandatory from Review on, until an owner acknowledges it with a reason after Review; the project then completes with its plan signed, not activated, and the conformance statement's new `activationAcknowledgement` field records that acknowledgement (null otherwise). Another profile's plan that this one does not weaken, or weakenings not recorded (or recorded at another journal head), leave activation due. `plan_activated` takes an acknowledgement only in that deferred state from Review on (before Review, or in any other state, 409 `A4_NOT_ACKNOWLEDGEABLE`: each step before Review records a new revision, and an acknowledgement counts only on its own). Only a ready plan activates: opening the review on a blocked plan is 409 `PLAN_BLOCKED`, and a regulated project's plan that is not ready reads `PLAN_BLOCKED`, deferred or not. Whenever activation is due or opened, `plan_activated` reads BLOCKED from Review on for a plan activateControlPlan would refuse (`PLAN_BLOCKED`, `PLAN_WEAKENS_ACTIVE_PLAN`, `ACTIVE_PLAN_UNREADABLE`); before Review it shows the same codes as a WAITING item that is not mandatory, so it never holds the direction gate. In a regulated project `plan_activated` waits from Review on. A non-regulated project completes with the plan signed and not activated (`PLAN_SIGNED_NOT_ACTIVATED`, once Build signed it; `PRODUCED_AT_BUILD` before); an owner may still open the effect before completing. An effect gate opened on a consumed gate counts only once an attempt follows it, and an activation that started and has not finished reads `PLAN_ACTIVATION_NOT_FINISHED`, never activated. Remaining limit: a project stays regulated (two distinct keys, live-checked identities) once any of its revisions recorded an active plan's head, whoever activated it. A project is regulated once its own activation finished or any of its revisions recorded an active plan's head (previously only the newest Adapt revision counted, which predates the project's own activation). An A4 effect can now be `optional`: `complete` runs it only when an owner opened it on the gate before completing. Opening an effect whose executor consumes its own grant on a consumed gate is refused with 409 `A4_GATE_STALE` (`consumed`) unless an attempt of it on that gate failed and none finished (previously an optional effect could be opened after a plain completion and filed a plan review nothing could run). Every revision now binds `plan.journalEntrySha256` (the active plan journal's head) and `plan.lockDigest` (the shipped catalog's lock, digested without `generatedBy`, which `verifyCatalogLock` ignores too, so an AMC upgrade with an unchanged catalog moves neither the slot nor `plan_lock_drift`): any activation makes an open gate `RESOURCE_DRIFTED`, and a revision recorded before this release binds both as null, so its open gates read `RESOURCE_DRIFTED` once until a new revision is recorded.

Adapt's readiness items: `ask_complete`, `understanding_confirmed`, `profile_facts_complete`, `plan_proposed`, `plan_compiled`, `plan_no_missing_facts`, `plan_conflicts_resolved`, `plan_unresolved` (WAITING while a mandatory requirement is unresolved; owner-acknowledgeable, then `OWNER_OUT_OF_SCOPE`, never READY; on a regulated project it carries `REGULATED_READY_PLAN_ONLY`, an acknowledgement is refused with 409 `A4_NOT_ACKNOWLEDGEABLE`, and one recorded earlier does not count), `plan_lock_drift`, `plan_signed`, `conformance_statement`, the integrity item `adapt.control_results_signature`, `plan_review_opened` (the review was opened; its decision is the card's to read), `plan_activated`, `adapt.plan.nativeSessionsAllowed` (Studio native tasks with workspace tools started after activation run under a P1-67 lease; tasks started before it, CLI agent sessions and delegated children are denied; NOT_EVALUATED with `PLAN_HEAD_MOVED_OR_UNREADABLE` when the plan journal's head moved since the head revision or no longer verifies, never `NO_ACTIVE_PLAN`), `configs_trusted`, `clocks_classified`, `required_entries_satisfied` (each entry's kind; a role vote is an acknowledgement, never a review), `regulatory_sources_status` (always WAITING with `EXPERT_REVIEW_PENDING` and `KEY:D-08`; informational), `data_handling_declared` and `lifecycle_bridge`, which lists Adapt's `testing → staging` bridge rows (`integration_tests_passing`, `security_review_signed`, `deployment_plan_approved`) for the A4 lifecycle wrapper. Studio's Adapt view adds Applicability, Plan diff, Blockers (grouped by blocker kind), Plan activation and Conformance statement cards.
