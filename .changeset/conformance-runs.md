Adds conformance runs and `amc domain conformance`. A run checks a station's derived requirement set (sector-pack questions, domain-pack questions, the registry's assurance packs and the `injection` scenario pack) against sealed evidence for one agent and writes a sealed `amc.conformance-run/1` JSON and a Markdown summary. Each requirement is `PASS`, `FAIL` or `NOT_EVALUATED` with its evidence ids, its claim kind and its five status dimensions; the run is `REQUIREMENTS_MET` only when every requirement passes, and is evidence of conformity within that set, not a certification. See `docs/CONFORMANCE_RUNS.md`.

- `amc domain conformance --station <station> --agent <id> --max-evidence-age <duration> [--responses <file.json>] [--profile <operating-profile.json>] [--out <dir>] [--json]`. The duration is `<n>h` or `<n>d` and has no default; anything else exits 2 with `invalid --max-evidence-age`. Exit 0 when a run is written (any status), 1 when every input was refused, 2 on usage errors. Text output lists the status, counts, every `FAIL` and `NOT_EVALUATED` requirement with its reason, refused inputs and the export path.
- A questionnaire answer counts only when its ledger session exists, is sealed, its seal verifies (the ledger chain up to the session's last event and the monitor signature over its final hash, against this workspace's keys), and both its sealing time and last event time are within the maximum evidence age and not after the run. Otherwise it is refused with the reason (`session <id> not found in the ledger`, `session <id> is not sealed`, `session <id> is older than the maximum evidence age`). Assurance reports must seal-verify, name a ledger session whose events back every measured scenario, and be within the same age.
- Answers are `self_reported` and assurance and scenario packs are `observed`. Design rule 1: a self-reported answer meets no requirement above L1, so at or above an L3 or L4 minimum it is `NOT_EVALUATED` ("self-reported answer; levels above L1 need observed evidence (design rule 1)"); below the minimum it is a `FAIL`. Until observed evidence exists for questionnaire requirements, every station's run is `REQUIREMENTS_NOT_MET`. Applicability stays unresolved until a compiled plan decides it, so no requirement's status-dimension result is a pass.
- `--profile` takes a signed operating profile for the same station and agent; its industry packs select the sector packs and its assurance packs are added.
- The audit binder gains an optional `sections.conformanceRun` for agent scopes: the agent's newest run that verifies under pinned trust (artifact-seal, P0-09). No run, another scope, or any run file that does not verify gives `status: null` and the note "no verified conformance run". Older binders still verify.
- `Ledger.getSessionById` looks a session up by id.

Security: an exported binder never copies a conformance run file, which holds free text and raw agent, session and answer identifiers. It carries an allowlisted projection (ids, statuses, claim kinds, status-dimension states, counts, digests and times), with session, answer and assurance-run ids and the agent id hashed by the binder's own `hashAuditId` and the audit policy's `hashTruncBytes`, checked by the binder's PII scan, and written as `checks/conformance-run.json` and `summaries/conformance-run.md`; `binder.json` records the SHA-256 of those exact bytes (`checkSha256`, `summarySha256`), so the binder signature covers them. A field added to the run later reaches no binder until it is added to the projection.

Ledger event times are written by the recording process, so freshness is only as good as those clocks until trusted time lands for ledger events.
