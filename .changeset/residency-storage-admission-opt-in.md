Residency storage admission and egress checks are opt-in, including when the control checkpoint root sits inside the workspace. They apply only when the workspace has an active compiled plan (any `.amc/control-plan/`) or a destination registry (`.amc/residency/destinations.yaml` or its `.sig`). Before this fix, a workspace that contained its checkpoint root refused every session open and every egress check, even with no plan and no registry. This happened, for example, after `amc init` in the home directory, where the default root `~/.amc/control-checkpoints` falls inside the workspace. The refusal also named the wrong cause: `registry_unverifiable (active_policy_unverifiable)`. An opted-in workspace in that configuration is still refused, now as `registry_unverifiable (control_checkpoint_root_in_workspace)`, and the message names the checkpoint root and `AMC_CONTROL_CHECKPOINT_DIR`. A present but invalid registry, or an active plan that does not verify, still refuses. `LlmRuntime` also no longer requires a session workspace at construction. The workspace is read when a check runs: the egress check refuses a missing one as `workspace_scope_required`, and protected-data admission treats it as an invalid registry, not a missing one.
