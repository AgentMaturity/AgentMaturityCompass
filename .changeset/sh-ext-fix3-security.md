Extensibility security fixes from the harness-program review: a `.amc/hooks.json` acceptance now binds the digests of the workspace files its commands name and re-checks them before every run, refuses relative program paths and resolves bare program names on `PATH` only (never the working directory, never inside the workspace); a skill's `disallowed-tools` also withholds `delegate` and `workflow`, so a delegated child cannot hand the denied tool back; a project-scope MCP config's signature is verified over the bytes that were parsed and pinned, not a second read of the path.

Skeptic and security follow-ups (same lane): hook scripts must live under `.amc/hooks/`, whose whole tree is bound into the trust value and re-checked before every spawn; code-loading interpreter flags, workspace directories, `--flag=value` workspace paths and alias spellings are refused by canonical location; a hook's over-cap stdout denies instead of abstaining; a trusted file that goes missing fails closed (`hooks untrust` retires the mark); `hooks inspect` reviews an untrusted file; a trust that cannot be recorded is an error; `UserPromptSubmit` receives the typed line and the skill name; a skill's `disallowed-tools` denies `delegate`/`workflow` before the kernel defines them, and `run_code` is refused with a reason; `$ARGUMENTS` text is tokenized only when a placeholder needs words and reaches shared sessions too; legacy `key: value` frontmatter still loads; the user MCP scope directory is created owner-only under any umask, `amc mcp add` validates before writing, `amc mcp sign` checks the id and `--expect-digest` first, and the `.sig` is read through the bounded reader; `amc config provenance` prints the resolved value for the winner.
