A4 agent projects reach MCP and the Node SDK, behind the A4 preview (`AMC_A4_PREVIEW=1`). Without the preview nothing changes: `amc mcp serve` and `amc mcp list-tools` keep their eleven tools.

With the preview, `amc mcp serve` adds `amc_a4_list_projects`, `amc_a4_project`, `amc_a4_readiness`, `amc_a4_conformance` and `amc_a4_comment`. The reads use the same records and readiness evaluator as `/api/v1/a4`, and each result carries a claim label: `amc_a4_project` and `amc_a4_readiness` repeat the readiness evaluator's own envelope, `amc_a4_conformance` is not evaluated (`NO_PRODUCER_REGISTERED`) until Adapt registers its producer, and the listing and the comment are not evaluated. No MCP tool approves, denies, builds, completes or releases. The MCP server has no per-user session, so its identity is an `amc approvals login` token file named by `AMC_A4_SESSION_TOKEN_FILE` in the server's MCP config; each call re-reads that user from the signed users.yaml and refuses a missing, expired or revoked session or a revoked user, without printing the file's path. That file is the user's full Studio session, not a comment-only credential: the agent host runs as the same OS user and can read it, then call Studio or `amc approvals … --session-token-file` as that user until it expires. The server therefore accepts only the session of a user whose sole role is `VIEWER` (403 `A4_SESSION_TOO_PRIVILEGED` otherwise), since `APPROVER`, `AUDITOR` and `OWNER` decide A4 gates and `OPERATOR` builds; use a dedicated `VIEWER` user that is a member of the project, with the shortest `--ttl-minutes`. `amc_a4_comment` refuses without that file; with it, it records a self-reported comment through the same path as `POST /api/v1/a4/projects/:id/comments` (project membership, encrypted blob, `clientRequestId` dedupe). The record is that user's own comment, the same as one typed in Studio, with no MCP marker. Without the file the reads answer as the admin token does (every project, reads only); with it they show what that user may read. Every A4 tool refuses while the workspace's users or trust signature does not verify.

The Node SDK exports `createA4Client({ baseUrl, session })` with typed methods for these `/api/v1/a4` routes: `listProjects`, `getProject`, `readiness`, `answers`, `understand`, `confirmUnderstanding`, `explain`, `propose`, `build`, `review`, `requestGate`, `decide`, `requestChanges`, `complete`, `observeHypothesis`, `members`, `comment`, `comments`, `events` and `verify`. Creating a project, `/options`, `/inbox`, revisions, transitions, gates, evidence, value, monitor, conformance, presence, the owner actions and effect open and retry have no method yet. `session` is a Studio session cookie with its native CSRF proof (`nativeCsrfToken` from `GET /auth/me`), or the admin token, which reads only. Writes carry the native intent header, the CSRF proof, an `Origin` of `baseUrl` and a `clientRequestId` (generated when omitted); stage, gate-request and hypothesis bodies carry `expectedHeadSeq`, `decide` and `requestChanges` carry `expectedGateSeq`, and `comment` carries neither. Each method returns `{ status, body }` with the server's JSON unchanged, errors such as `400 SOD_VIOLATION` included; the client computes no readiness or verdict and adds no label. Only a failed request or a non-JSON answer throws `AMCSDKError`. Redirects are refused. Release, deployment and rollback methods arrive with the Activate routes.
