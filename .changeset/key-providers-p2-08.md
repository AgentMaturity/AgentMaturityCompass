Signing keys can be held by a key provider: AWS KMS, Google Cloud KMS, Azure Key Vault or Managed HSM, or a PKCS#11 token (P2-08). The vault stays the default; a workspace without a `keys` section in `.amc/amc.config.yaml` signs exactly as before.

- `keys.refs.<purpose>` names a provider key by identifier only; credentials, PINs and the PKCS#11 library path come from the environment. A purpose configured this way never signs with its vault key: `getSigningKey` refuses it with `KEY_PROVIDER_HELD`, whether or not the provider is reachable.
- `amc keys rotate --purpose <p>` binds the configured key instead of generating one, reading the ref only from an `amc.config.yaml` whose signature verifies (`amc verify --sign-config`), after the provider proves possession, in one key-set generation (`providers` in `keyset.json` with the ref and key id, `keys/<purpose>-provider.pub` pinned) under the P1-08 anti-rollback marks. Signing reaches a bound key by the ref the key set records, never by the editable config. Only `ledger-row` can be bound in this release: its vault key keeps signing ledger rows as a delegate while a provider-signed delegation of at most 24 hours, renewed by the same command, is current; otherwise `KEY_DELEGATION_INVALID`.
- `amc keys list` adds provider, algorithm, protection and its basis per purpose (text lines gain `file ed25519 protection=software (configured)` for vault keys); `amc keys export-public` prints a provider key's public key and a provider-signed proof of possession only.
- A key rotation now refuses before it commits when the transparency log's signer would refuse the log append after the commit.
- Algorithm policy: ECDSA P-256 with SHA-256 in IEEE P1363 with low S is accepted beside Ed25519 by digest verification, signature envelopes, trust-list entries and roots, issuer admission and the standalone verifier. A DER-encoded or high-S ECDSA signature, and an Ed25519 signature with an unreduced S, are refused everywhere these verify, including where a P-256 key used with Node's default verification accepted DER before. The algorithm comes from the pinned key, and a key's id from its DER bytes, so every PEM spelling of one key has one id.
- The notary has a `KEY_PROVIDER` backend (Ed25519 provider keys) reached through a provider bridge child process. Its `/readyz`, `/pubkey` and `/sign` answers and attestations carry `attestationBasis`: `configured`, `provider-metadata`, or `provider-reported` for an external signer's own hardware claim. Attestations from 2.0.0 carry that field, so a 1.x verifier refuses them.
- Provider failures are typed `KeyProviderError` codes (`KEY_PROVIDER_UNAVAILABLE`, `KEY_PROVIDER_AUTH_FAILED`, `KEY_PROVIDER_KEY_REFUSED`, `KEY_PROVIDER_NOT_INSTALLED`, `KEY_PROVIDER_HELD`, `KEY_DELEGATION_INVALID`) with fixed messages that never copy the provider's text. A provider-held purpose is refused before the vault is touched, so such a refusal never unlocks or reads the vault. The provider SDKs and pkcs11js are not installed with AMC.
- Every signing key, vault or provider, passes one pre-sign gate: it must be the key the committed key set names, the workspace key revocation list must load and verify and not name it, and the built-in distrust list must not distrust it. A vault key on the shipped distrust list now refuses to sign (that list ships empty).

Protection labels are `provider-metadata` or `configured`, never attested. Mocked providers and an in-process PKCS#11 token are tested; a SoftHSM2 CI job is added; no real KMS or HSM was exercised. docs/KEY_PROVIDERS.md has setup, least-privilege access, the dated provider matrix and what is not in this release.
