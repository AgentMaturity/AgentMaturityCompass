Adds an optional Pi extension that sends Pi tool calls to AMC's hook control path (allow or deny; every Pi ask is denied) with signed decision receipts; enforcement is limited to Pi's tool_call hook.

`amc connect hooks install|status|health|remove --provider pi` (`--mode observe` or `--mode control`; `pi` is a new value of the existing `--provider` option, not a new command) writes `.pi/extensions/amc.js`, a dedicated `0600` lease, the managed `.gitignore` block and a manifest signed by the workspace auditor key that binds the SHA-256 of that file and of AMC's extension module, the Bridge origin and the public keys of AMC's `receipt` signing purpose (P1-08). In control mode it also binds the Pi install behind `pi` on `PATH` (option `piPackageDir` programmatically): its version and a SHA-256 over its `package.json` and `dist/bundle`. The extension is exported as `agent-maturity-compass/pi` (`createAmcPiExtension`). Pi loads `.pi/extensions/` only for a trusted project (or with `pi -e`); while Pi does not load it, nothing is enforced.

In control mode the extension posts every Pi `tool_call` to the loopback route `/hooks/control/v1` (new provider `pi`, runtime `pi`). AMC derives the action id from Pi's session and call id, denies a Pi version outside `QUALIFIED_PI_VERSIONS` (1.0.2 and 1.0.4; an unreadable version included, recorded as `unknown`), refuses a Pi whose working directory is not the workspace and a mapped tool name that Pi's tool registry does not name as Pi's built-in (an extension tool registered under that name), maps `read`, `grep`, `find`, `ls` to `fs.read` and `write` and `edit` to `fs.write` at the locations Pi opens (Pi's own path resolution: leading `@`, Unicode spaces, `file://` URLs, symlinks followed, the case the file system stores, `read`'s macOS name variants; `~` paths, dangling links and Windows are denied), so the protected `.amc` floor applies to the real target, and `bash` to the shell command plan, each with a lowest action class the signed ToolHub config may give it, and denies every other tool (Codemode and extension tools included) with `Pi tool <name> is not mapped to an allowed ToolHub tool.` Every Pi `ask` is denied (capability-lossy): a Pi call cannot carry an AMC approval and Pi's own confirmation is not one. An allow binds a P1-02 authorization record (principal and delegation from the hook lease, idempotency key = Pi's call id, execution id = AMC's action id) and is recorded as a v2 `action_state` receipt whose body digest covers Pi's response and the digest of the exact request; `enforcement` is `enforced` at `pi:tool_call` only for a qualified version. Before sending, the extension requires the call's input to be plain JSON data and freezes it in place (Pi runs that same object), so nothing can change what runs while AMC decides; it allows only when the receipt verifies under the pinned AMC keys and binds this call. Each request carries a nonce, so re-sending a call is a conflict, never a second decision. Any error, timeout, malformed or unbound answer, bad signature, lease or manifest failure, unrecognised Pi event, input that is not plain data or Bridge outage blocks the call: `AMC control unavailable; action denied.` Observe mode never blocks; in both modes requested and finished calls are recorded as `observed` events without arguments or output.

Claims come from session registrations, a lease-holder attestation: registration made with the session lease and matching on-disk extension and Pi digests. In control mode the extension registers each Pi session (`session_start`, or before the session's first call) with Pi's version, the session id and its module's SHA-256; AMC itself measures the installed extension file, AMC's module and the bound Pi install, refuses any mismatch with the signed manifest or a reported version other than the one on disk, and records a registration bound to that manifest with a receipt signed by the P1-08 `receipt` purpose key. A process holding the lease can still attest without Pi. AMC cannot prove Pi executed the hook; it can prove only that every allowed call went through AMC with a signed receipt. A call in a Pi session without a verified registration under the current installation, or naming another Pi version than its session registered, is denied, and nothing reads "enforced" for it. `amc connect hooks status|health --provider pi` report a `governance` claim from those registrations only: `enforced_at_pi_tool_call` while the installation is `installed`, otherwise `not_governed` (`observed` for observe installations); a drift in the extension, AMC's module, the receipt keys or the Pi install marks it `drifted`, and a reinstall starts with no registered sessions. AMC cannot see sessions where Pi did not load the extension; they are reported as not governed. Pi ask is always denied until an AMC approval path exists. Hook decision receipts are verified against the `receipt` purpose's keys (P1-08), which the Pi installation pins. Observed hook ingress receipts, `POST /verify/receipt` in Studio and ops receipt verification also verify against the `receipt` purpose's keys now, not the monitor role history, which also holds `ledger-row` keys.

Fix: `mintReceipt` now refuses exactly the version and kind pairs `parseReceipt` refuses (a v2 receipt is an `action_state` receipt, and the reverse), so AMC never signs a receipt its own verifier rejects; `parseReceipt` also refuses a v1 `action_state` receipt, which AMC never minted.

Not covered: OS containment; effects that bypass `tool_call` (another extension's own I/O, Pi Durable, Codemode-internal calls unless step 2 confirms they emit `tool_call`); an extension that rewrites Pi's tool registry itself. The qualification run confirmed that Codemode-internal calls emit `tool_call`; AMC denies the `codemode` tool in control mode. See docs/adapters/pi.md.

Internal: the provider request mapping and responses moved from `hookControl.ts` into `src/bridge/hookProviders.ts`, and the shared install helpers into `src/adapters/hookProviders/installFiles.ts`, with no behaviour change for Claude Code or Gemini CLI. `amc connect hooks health --provider` names `pi` among the accepted providers, and onboarding activation counts a Pi installation.
