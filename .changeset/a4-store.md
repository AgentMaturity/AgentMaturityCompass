A4 Forge preview groundwork (P1-56): the project store, its schema, contracts and identity land with no route or page yet, so no A4 surface is reachable.

- Ledger migration 13 adds twelve dormant `a4_*` tables the next time a workspace's evidence ledger is opened for writing: `a4_projects` (the one mutable head; a trigger refuses changes to its identity columns, and a partial unique index allows one active project per agent), the append-only `a4_transitions`, `a4_revisions`, `a4_gates`, `a4_decisions`, `a4_members`, `a4_comments`, `a4_evidence_refs`, `a4_releases` and `a4_deployments`, plus `a4_requests` (request deduplication) and `a4_effects` (effect liveness). An evidence ref in the `observed` lane must carry claim kind `observed`, an observed trust tier and a runtime-observation or executed-test method; the `verified` lane needs `independently_reviewed`.
- Fifteen A4 contracts are published as JSON Schemas: `spec/schemas/v1/a4-*.schema.json` for the project, revision, gate, decision, transition, intent, readiness, gate policy, integration claim, package, release, deployment receipt, rollback receipt, value claim and conformance statement. The schemas refuse a conformance control that is `not_evaluated` without a reason, a readiness item in the `integrity` section that carries a claim or evidence refs, and a value claim whose observed value is set without at least one resolved ref or while a ref dangles.
- `/api/v1/a4` and every path under it are native Studio paths: requests pass the same Host, Origin, intent-header and CSRF admission as native tasks, and the console's `apiNativeRequest` accepts them. No A4 route exists yet, so they still answer not found.
- New sign kind `A4_RECORD` (in both sign-kind lists, not in `requireNotaryFor`) and artifact kind `a4-stage-output`. Evidence with `meta.source: "a4-store"` is classified as a manual producer, so A4 rows are `SELF_REPORTED` and cannot carry an observed tier.
- `deleteVaultSecret` removes one vault secret and is refused while the vault is locked. User records in `users.yaml` accept an optional `createdBy` (`{ principalKey, admission }` or null); existing files parse unchanged, and a missing creator is treated as self-provisioned.

A4 rows are signed with the workspace's own keys: a local audit trail, not a portable verdict. Every A4 write is refused with `A4_VAULT_LOCKED` (423) before anything is written while the vault cannot sign (locked and no `AMC_VAULT_PASSPHRASE`); only the encryption of a comment body itself needs no vault. Every transition body signs the head state it leaves (`headAfter`: stage, step, hold, revision and release ids). Before each write the store hash-links the whole chain from its first transition, checks the last verified transition and every one after it against its signed audit row, checks that the head row equals the last signed `headAfter`, and refuses with `A4_INTEGRITY_FAILED` (409) on any break or when a side table holds a row no transition names. The chain, member, revision and self-approval-ratchet readers use only a chain that verifies whole up to its signed head and fail with the same error otherwise; they ignore a side row no transition names and fail on a named one that is missing or changed. A side row filed under another project, and a `CREATED` transition anywhere but a new project's first, are refused. A ledger evidence ref is resolved before it is recorded: a missing row is refused with `EVIDENCE_REF_DANGLING`, a row whose digest, signature or chain does not verify with `EVIDENCE_REF_UNVERIFIED`; its trust tier is the reader's effective tier, so imported, manual and external rows count as `SELF_REPORTED` whatever tier they declare. A stage-output ref needs an `a4-stage-output` signature, and a file with the ref's bytes but no valid signature is reported unsigned, not dangling. A member is named by principal key only: an add reads the ACTIVE user or live host session (`A4_PRINCIPAL_UNKNOWN` otherwise), a change or removal the current membership (`A4_NOT_A_MEMBER`), and a request key that names another principal is refused (`INPUT_INVALID`). Comment bodies are stored encrypted per project outside the ledger, under a project key wrapped by the vault secret `a4:<projectId>:wrap` and named by its public key's sha256 (`projectPublicKeySha256`) in the signed `CREATED` record; a substituted public key is refused, and a replayed request writes no second ciphertext. Reading a body reports `VAULT_LOCKED` only when no passphrase is available; a wrong passphrase or a damaged vault is `VAULT_UNREADABLE`. Destroying a project's key leaves a tombstone, deletes the wrap secret and the key file, and every later read or write for that project reports `PROJECT_KEY_DESTROYED`; the bodies are unreadable only once every backup older than the destruction has been rotated. A workspace-router user holds only the roles every live session record for that user grants, and unreadable session records count as unknown, never as "no other users", so single-user self-approval is then off; an unreadable `users.yaml` marks the member-candidate list as limited.
