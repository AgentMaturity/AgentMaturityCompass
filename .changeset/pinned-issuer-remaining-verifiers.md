Security: `amc bench registry verify`, `bom verify`, `domain pack verify`, `enforce verify-certificate`, `imports verify-profile`, `notary verify-attest`, `passport verify-token`, `session verify-proof`, `transparency merkle verify-proof` and `transparency verify-bundle` now refuse a signer that the verifier operator has not pinned. Artifacts these commands accepted before need `--pubkey`, a signed trust list or `--allow-unpinned`, which gives an integrity-only result with exit code 2 and `UNTRUSTED:` on stderr.

Every portable verify command now takes `--trust-list`, `--trust-root`, `--allow-unpinned`, `--allow-unanchored` and `--json`, returns a `VerifierReportV1`, and exits 0 (trusted), 1 (failed) or 2 (integrity verified, untrusted because an allow flag was used). No command path is added. `bench registry verify`, `domain pack verify`, `notary verify-attest`, `transparency merkle verify-proof` and `transparency verify-bundle` gain `--pubkey`, and `bom verify --pubkey` now pins its key. A key the artifact carries (`registry.pub`, `notary.pub`, `auditor.pub`, a signature envelope) or the current workspace's auditor keys only help find the signer; they never vouch for it. `notary verify-attest` needs the notary key pinned for `notary`, `imports verify-profile` pins the authority key its `--authorities` file names for `evidence-authority`, and `session verify-proof` pins `--expect-auditor-key`; the built-in distrust list and the operator's trust lists apply to all of them.

An artifact that names no signer is never reported as trusted and exits 1 whatever the flags: an `enforce verify-certificate` proof certificate (an unkeyed hash), a `passport verify-token` token (an HMAC under the CLI's demo secret), an unsigned external-evidence profile (including every imported `SELF_REPORTED` profile) and an Industry Packs license signed with `AMC_INDUSTRY_PACKS_LICENSE_SECRET` or a legacy allowlisted key. `domain pack verify` counts only an Ed25519 license signature pinned by `--pubkey`, a trust list or `AMC_INDUSTRY_PACKS_LICENSE_PUBLIC_KEY`; `domain pack activate` is unchanged.

The exported verifier functions `verifyBenchRegistry`, `benchRegistryVerifyCli`, `verifyBomSignature`, `notaryVerifyAttestCli`, `verifyTransparencyProofBundle` and `verifyTransparencyBundle` take a required `TrustContext` and return a `VerifierReportV1` as `report`, with `ok` equal to `report.trusted`.

The API routes for these verifiers (`POST /api/v1/bom/verify`, `POST /api/v1/crypto/notary/verify-attest`, `POST /api/v1/attest/notary/verify`, `POST /api/v1/crypto/merkle/verify-proof` and Studio `POST /transparency/merkle/verify-proof`) use the server operator's trust context, return the report, and refuse request bodies that try to add pins or allow flags, now including `pubkeyPemFile`.

Studio's native task verification now uses the operator's trust context (the AMC home trust list and `AMC_EXPECTED_MONITOR_FINGERPRINT`), as `amc agent-loop verify` does. A task is `externally-anchored` only when that context admits its monitor key; an intact run whose monitor key is not admitted is `failed` with an `UNTRUSTED:` explanation, and Studio no longer reports `workspace-key-consistency`. In-chat `/verify` already used the operator's trust through `amc agent-loop verify`; a refusal there now says the run is not verified instead of reporting a failed command.
