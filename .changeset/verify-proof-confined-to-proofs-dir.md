Security: Studio `POST /transparency/merkle/verify-proof` and `POST /api/v1/crypto/merkle/verify-proof` now read only a proof bundle under the workspace's `.amc/transparency/proofs/` directory, with `file` taken relative to it. They read a regular, singly linked file reached with no symbolic link from `.amc` down, through one no-follow descriptor, and verify a private copy of those bytes. A path that leaves that directory (an absolute path elsewhere, or `..`), a missing file, a link, a hard link, a FIFO or another non-regular file all return the same 200 result: `ok: false`, `errors: ["UNREADABLE: cannot read proof bundle"]` and an all-zero `report.artifact.sha256`, which now names the file as requested. Before, either route verified any path the server could read and returned its operating-system or archive error text and its SHA-256. The API route's 500 answer is now always `Merkle verify-proof failed`, never the error message.

- Security: `verifyTransparencyProofBundle` (and `amc transparency merkle verify-proof`) reports a bundle it cannot read or extract as `UNREADABLE: cannot read proof bundle` instead of the error text, and takes the bundle's SHA-256 only after it extracts, so a file that is not a proof archive gets an all-zero digest.
- Security: Studio `GET /audit/binders/:id/verify` no longer checks whether a `?file=` inside `.amc/audit/binders/exports/` exists before verifying it, so it no longer answers 404 `binder export not found` for a missing named file (it still does when no `?file=` is given and the binder id has no export). A missing `.json` industry-pack audit verifies as `UNREADABLE: cannot read audit file` (422), and a missing binder archive answers 500 `internal server error`. Neither shows operating-system error text.
