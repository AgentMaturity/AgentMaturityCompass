Security: Studio `POST /transparency/merkle/verify-proof` and `POST /api/v1/crypto/merkle/verify-proof` now read only a proof bundle under the workspace's `.amc/transparency/proofs/` directory. `file` is resolved against the workspace, as prove's `outFile` is, so the `.amc/transparency/proofs/<entryHash>.amcproof` that Studio's prove writes and the absolute `outFile` either prove route returns both verify. Studio used to resolve `file` against its own working directory. They read a regular, singly linked file reached with no symbolic link from `.amc` down, through one no-follow descriptor and never past the 128 MiB archive cap, and verify a private copy of those bytes. On Linux the opened descriptor's path is checked too; elsewhere the link refusal is best effort against a workspace writer racing directory swaps. A path that leaves that directory (an absolute path elsewhere, or `..`), a missing file, a link, a hard link, a FIFO or another non-regular file all return the same 200 result: `ok: false`, `errors: ["UNREADABLE: cannot read proof bundle"]` and an all-zero `report.artifact.sha256`; `report.artifact.path` now names the file as requested. Before, either route verified any path the server could read and returned its operating-system or archive error text and its SHA-256. The API route's 500 answer is now always `Merkle verify-proof failed`, never the error message.

- Security: `POST /api/v1/crypto/merkle/prove` now writes only under the workspace's `.amc/transparency/proofs/`. `outFile` is resolved against the workspace, and one that resolves anywhere else (an absolute path outside that directory, `..`, or the directory itself) is refused with 400 `outFile must lie under .amc/transparency/proofs/` before anything is written. Before, an absolute `outFile` or `..` created directories and overwrote files anywhere the server could write. A failed prove now answers 500 `Merkle prove failed`, never the error message, which named server paths. `amc transparency merkle prove --out` still writes where its operator names.

- Security: `verifyTransparencyProofBundle` (and `amc transparency merkle verify-proof`) reports a bundle it cannot read or extract as `UNREADABLE: cannot read proof bundle` instead of the error text, and takes the bundle's SHA-256 only after it extracts, so a file that is not a proof archive gets an all-zero digest. A bundled `root.json` or public anchor it cannot read is reported as `invalid signed root in the bundle` or `public anchor invalid: the public anchor is malformed`, without the error text.
