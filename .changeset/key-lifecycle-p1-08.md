Key lifecycle (P1-08): one signing key per purpose, signed rotation statements, atomic key changes, anti-rollback marks, single-file anchored revocation lists, m-of-n trust roots with signed root-set rotation, and `amc keys list|rotate|revoke|export-public`. See docs/KEY_LIFECYCLE.md.

- Purposes: `ledger-row`, `receipt`, `artifact-seal`, `revocation-list`, `config-signature`, `lease` and `session` each sign with their own key, taken from `getSigningKey(workspace, purpose)`. On the first unlock, a 1.x vault (payload v1) becomes payload v2 with the same key bytes, so no public key changes; the v1 envelope is kept in AMC home (`<AMC home>/state/keyset-recovery/<workspace scope>/previous-vault.amcvault`), out of the workspace. AMC 1.x cannot read a v2 vault: downgrading is unsupported.
- Key changes (vault creation, migration, rotation) are one key-set generation, staged and committed by rename. Signing and verifying refuse while a generation is pending; `amc keys rotate --resume` finishes or rolls it back without deleting key material.
- `amc keys rotate --purpose <p>` writes a signed, chained `amc.key-rotation` statement (overlap at most 30 days, default 7; `key-compromise` needs a pinned root). `amc vault rotate-keys` remains as an alias for the monitor purposes.
- Revocation lists are one signed, sequenced file, anchored in the workspace transparency log and in this machine's high-water file (`<AMC home>/state/high-water.json`). An older list, a fork, a deleted list once anchored, or a symlinked anchor is refused. Lease revocations move from `revocations.json` + `.sig` to `revocations.signed.json` on the first write; the old pair is replaced by a tombstone, so a 1.x binary refuses every lease instead of reading an empty list. `amc lease resign-revocations` refuses a store that fails the schema. A revocation whose lease expiry is known (`amc lease revoke --token <lease>`, or `revokeLease`'s `expiresTs`) is pruned once the lease has lapsed, with the sequence still rising.
- Every key use checks the workspace's key revocation list (`keys:<workspaceId>`); a missing or unverifiable list refuses every key.
- On a machine that committed a key set, AMC accepts only that exact generation (its generation and digest are this machine's mark in AMC home, raised only on commit or resume), and every public key it reads, for signing or verifying, must be the key that key set names. A workspace-only writer can no longer swap a public key, restore older keys or rewrite `keyset.json`. Key-set recovery copies (older vaults among them) now live in `<AMC home>/state/keyset-recovery/`. Once a mark exists, a missing or mismatched `keyset.json` refuses unlock, key creation and every key use. AMC never re-creates a vault or adopts legacy key files there; `amc keys rotate --restore` (owner mode) puts back the committed key set from AMC home. A machine that never committed the key set adopts it on first use, visibly: it records the adoption, prints "adopted unanchored (trust on first use)", and refuses any newer generation until the owner accepts it (`amc keys rotate --accept <generation> --digest <sha256>`, the digest `amc keys list` shows on the committing machine). `amc keys rotate --restore` also puts back the vault that holds the committed key ids. A purpose key file in a 1.x workspace (1.x never wrote one) is bound at migration when it is the vault's own key and refused by name otherwise; `amc keys rotate --quarantine-unbound-pub` (owner mode) moves such strays aside. Every refusal and its recovery path is listed in docs/KEY_LIFECYCLE.md. Every state-changing key-set function checks owner mode itself (agent mode refuses rotate, revoke, resume, restore, accept, quarantine and key-set commits, whoever calls them). Rotate, revoke, restore, accept and quarantine also need the vault passphrase. `revokeKey` takes the passphrase as a new optional last argument. Accept takes exactly the next generation unless `--allow-gap <reason>`, and only when the owner's vault holds its keys. Each key-set commit first records its generation and digest in AMC home. `amc keys rotate --resume` finishes only a pending generation with that record, and only with the vault passphrase; `resumeKeyRotation` takes the passphrase as a new optional argument. A planted pending generation is moved aside with `--quarantine-unbound-pub`. Under `trustBoundaryMode: shared` an agent that can also write AMC home defeats this binding; use the `isolated` mode or pinned keys.
- A key-compromise rotation takes its root authority and threshold from `<AMC home>/trust/trust-roots.json`; a `--root-key` that is not pinned there is refused. Key-history revisions are also logged at vault creation, migration and explicit admission, and a history is checked against the workspace log whenever this machine has no mark at its revision.
- Deployments: the compose files and the Helm chart (0.3.0, `amcHomeState`) keep `<AMC home>/state` on a persistent volume, so anti-rollback marks survive a restart.
- Trust lists: `trust-roots.json` may set `threshold` (m-of-n) and `rootSetId`, and a list may set `rootThreshold`. Flags never lower the threshold, and this machine refuses an older list, an older list version or a lower threshold than it accepted. Root sets rotate only with an `amc.root-rotation` statement signed by m of the pinned set and m of the new set (`applyTrustRootRotation`; `scripts/trust-list.mjs root-rotate|root-sign|root-apply`); once rotated, an edited, missing or pre-rotation `trust-roots.json` is refused.
- Cross-agent claims bind issuer, audience, key purpose and id, issue and expiry times (at most 24 hours) and a nonce. `createAgentClaim` now requires `opts.audience`, and the API's create-claim body requires `audience`. `verifyAgentClaim(claim, policy, secret, expected?)` refuses without an expectation (audience, issuer, scope, grants, the key ids bound to each issuer in the new required `issuerKeyIds`, replay cache). A `SELF_REPORTED` claim (a shared secret, or a key issuer admission does not vouch for) is never trusted, at most `limited`, with no scope; only an `ATTESTED` Ed25519 claim can be trusted. 1.x claims no longer verify.
- API: `ClaimExpectation.issuerKeyIds` is required; `getPrivateKeyPem` also accepts a local purpose (resolved as `getSigningKey` does); `RotationResult.recoveryDirectory` is in AMC home; `rotateMonitorKeyInVault` moves from `src/vault/vault.ts` to `src/keys/purposeKeys.ts` (the package index still exports it); `leaseRevocationPaths` returns `{ file, pending, legacyFile, legacySig }` (was `{ file, sig }`); `signLeaseRevocations` returns the signed `LeaseRevocations` (was the signature `Buffer`); `revokeLease` takes an optional `{ expiresTs }`; `verifySignedTrustList` takes an optional `threshold`; `TrustListErrorCode` adds `ROLLBACK_DETECTED` and `FORK_DETECTED`. `issueLeaseToken`, `verifyLeaseToken`, `revokeLease` and `revokedLeaseIdSet` keep their signatures and behaviour.
