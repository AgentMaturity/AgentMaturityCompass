Experimental redaction of protected data before a native session row is committed (partial P2-02 source, slice 2). Tokenization reduces the identifiers that reach model context and logs. It is not de-identification or anonymization under any standard or regulation, and detection is heuristic.

**Opt-in, per workspace.** Redaction applies only where the processor registry `.amc/dataflow/processors.yaml` or its `.sig` exists (or that cannot be checked), the same opt-in as protected-request admission. In other workspaces, native sessions and gateway and ToolHub evidence are unchanged; the bridge and the built-in privacy rules are the exceptions listed below. In an opted-in workspace, native sessions composed by `amc agent run`, scheduled passes, ACP, the SDK, A4 Assemble and delegated child sessions tokenize the following before any row, spill or model-visible part is written: queued inbox text, user messages, text attachments (content and file name), tool results, native-validation check output, and operator compaction text (`amc session compact`).

- A token is `[[amc:<class>:<16 hex>]]`: the first 64 bits of HMAC-SHA256 under a per-workspace key. The same value gives the same token within a workspace; another workspace gives a different token.
- The keys are one vault secret, `dataflow.token-keys.v1`, created on first use. Values are kept AES-256-GCM encrypted in `.amc/dataflow/token-vault.sqlite`, which the default `.amc` backup scope includes.
- Tool definitions in the signed tools config can declare `protectedFields` (dot paths into the JSON result, for example `patient.name: phi`). These are tokenized first, for `OK` results; the existing detectors are the backstop. Such a result is always committed as its re-serialized parse (a duplicate key keeps its last value). Numbers keep their source text on Node 21 and later; on Node 20 a number literal a double would change refuses. A declared value that already is a token is left as it is.
- Each redaction writes one `PROTECTED_DATA_REDACTED` audit row whose payload is the new public contract `redaction-receipt` (`amc.redaction-receipt/v1`, `spec/schemas/v1/redaction-receipt.schema.json`, sources `user/message`, `user/attachment`, `tool/result`, `loop/inbox` and `operator/compaction`). It holds classes, detector names, counts, the matched declared paths, the detector-set digest and the SHA-256 of the redacted text, never a raw value. Gateway and bridge redactions write no receipt.
- In a redacting session, `stdout` evidence rows drop `outputSha256` (a plain hash of the raw output), and in an opted-in workspace the action journal's `outcomeDigest` no longer binds the output's digest.
- The new deletion target kind `token-vault` lets `deleteTokens` remove rows only through the legal-hold deletion gate.

**Refusals.** Every failure refuses the commit with `RedactionRefused` (code `REDACTION_REFUSED`) and a static reason; the raw value is never committed:

- `vault_unavailable`: a locked vault or unavailable keys.
- `vault_integrity`: a vault row that does not verify.
- `token_collision`: a different value under an existing token, in the vault or earlier in the same redaction.
- `receipt_failed`: the receipt row could not be written.
- `detector_invalid`: text over 1,048,576 characters.
- `content_not_text`: tool output or queued input that is not UTF-8.
- `attachment_not_redactable`: image and audio attachments, media inbox input (refused before anything is spilled) and non-UTF-8 text attachments, refused in opted-in sessions whatever the provider's processor contract covers.
- `declared_fields_unparseable`: a declaring tool's `OK` result that is not JSON, or (Node 20 only) one with a number a double would change.
- `declared_fields_unverifiable`: a signed tools config that no longer verifies, an `OK` result whose call the session never recorded while some tool declares fields, or any Code Mode (`run_code`) result while some tool declares fields.

A refused tool result or native-validation output is not thrown: the call is answered with `[amc] tool output withheld: protected-data redaction refused (<reason>)`, keeping the tool's recorded outcome, after a `PROTECTED_DATA_REDACTION_REFUSED` audit row naming the call and the reason. The session continues.

**Gateway and ToolHub evidence (opted-in workspaces).** The same detectors run over the bodies the gateway stores and over ToolHub evidence payloads (`redactBody`, which now takes `{ protectedData }`). A detected card number, IBAN, SSN, email, phone number, IP address, keyword-bound ID, health-record number or credential shape becomes `[REDACTED]` with a `protectedData:<class>` redaction reason, so `originalPayloadSha256` is omitted. JSON bodies stay valid JSON, and a detected number leaf becomes the marker string. A text over 1,048,576 characters is replaced whole, and a body whose scanned keys and leaves pass 16,777,216 characters is stored whole as `"[REDACTED]"` (`protectedData:unscanned`). Forwarded traffic is unchanged.

**Bridge evidence (every workspace, no opt-in).** Text that passes through `redactBridgeText` (stored stdout and stderr telemetry, every key and leaf of object telemetry payloads such as `amc wrap`'s command arguments, request summaries, hook identifier fields) is redacted with the same detectors, with `<AMC_REDACTED>`. `amc wrap` keeps writing the wrapped agent's own terminal output with secrets-only redaction.

**Admission detectors.** A detector span inside an AMC token's 16-hex part is no longer a detection, but only when that hex contains a letter: an all-decimal "token" is scanned as text, so a raw card number in token brackets is still detected. A span that crosses token text (a JSON `password` value holding a token beside raw text) stays a detection. A bare 13-digit run starting with 1 (a Unix-millisecond timestamp) is no longer a card number. These change the detector-set digest.

**Privacy redaction rules (every workspace).** `getBuiltInRedactionRules` and `applyRedaction` keep the same six rule IDs and replacements but delegate to the shared detectors instead of a second rule set, without narrowing them. Email, SSN, card and IP use the protected-data detectors: card numbers must now pass the Luhn check, IPv6 addresses are matched, and clock times and millisecond timestamps are no longer redacted as IP addresses or card numbers. The phone rule uses the DLP phone pattern, bare 10-digit runs included. The API-key rule applies the shared secret table (provider keys, bearer tokens, JWTs, `api_key`/`apikey`/`api_secret` forms) and then its earlier keyword form (`token=`, `secret:` and similar). Text over 1,048,576 characters is replaced whole. A built-in rule's `pattern` now shows the shared regexes for reference. A caller's own rule, or a built-in rule with a changed pattern, still applies as a regex.

Known gaps (debt): no restoration path yet (the detokenization gate, processors on destinations and purpose binding are slice 3); opt-in through classes declared in the compiled policy; per-sub-call declared fields for Code Mode; the system prompt, tool schemas, model output (including model-written compaction summaries), approval questions and operator compaction reasons are recorded unredacted; names outside declared fields are missed; the bridge's hook evidence and ToolHub's own action journal still hold plain digests of tool output; hostile text can hold the gateway for about 10 s per body before the scan budget replaces it. Synthetic fixtures, the labelled corpus, the detector quality report and the issue's tests are not written. This is partial, unqualified source; nothing was run beyond build-level checks and local probes.
