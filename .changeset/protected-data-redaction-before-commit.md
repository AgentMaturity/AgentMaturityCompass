Experimental redaction of protected data before a native session row is committed (partial P2-02 source, slice 2). Tokenization reduces the identifiers that reach model context and logs. It is not de-identification or anonymization under any standard or regulation, and detection is heuristic.

**Opt-in, per workspace.** Redaction applies only where the processor registry `.amc/dataflow/processors.yaml` or its `.sig` exists (or that cannot be checked), the same opt-in as protected-request admission. Every composed native session is wrapped and checks the opt-in on each record, so a long-lived session starts redacting as soon as the workspace opts in; the opt-in is latched per process, so removing the registry never turns it off mid-process. In other workspaces, native sessions, gateway and ToolHub bodies and the action journal are unchanged; bridge evidence gains secrets redaction of object payloads, the stored stdout, stderr and argv of adapter runs and monitored processes gain the shared secret table, `SANDBOX` adapter runs no longer put the environment in argv, gateway rows always redact credential headers, cookies and credential query keys and give other header values the shared secret table and the configured `textRegexDenylist`, and the built-in privacy rules are the exception listed below. In an opted-in workspace, native sessions composed by `amc agent run`, scheduled passes, ACP, the SDK, A4 Assemble and delegated child sessions tokenize the following before any row, spill or model-visible part is written: queued inbox text, user messages, text attachments (content and file name), tool results, native-validation check output, and operator compaction text (`amc session compact`, validated after redaction, its receipt written just before the append).

- A token is `[[amc:<class>:<16 hex>]]`: the first 64 bits of HMAC-SHA256 under a per-workspace key. The same value gives the same token within a workspace; another workspace gives a different token.
- The keys are one vault secret, `dataflow.token-keys.v1`, created on first use; an evicted vault session is reopened from `AMC_VAULT_PASSPHRASE`, as signing does. Values are kept AES-256-GCM encrypted in `.amc/dataflow/token-vault.sqlite`, which the default `.amc` backup scope includes.
- Only tokens this workspace issued are treated as tokens: the redactor and admission look token-shaped text up in the token vault (read-only, cached per request), and any other token-shaped text, such as a raw card number in token brackets, is scanned as data.
- Tool definitions in the signed tools config can declare `protectedFields` (dot paths into the JSON result, for example `patient.name: phi`). These are tokenized first, in every outcome (an `OK` result must be JSON; error text that is not JSON gets the detectors only; the tool seam's exact `[amc] outcome unknown: ...` notice is set aside and the output after it redacted as itself); the existing detectors are the backstop. Strings, numbers, booleans and object keys under a declared path are tokenized. JSON held in a string leaf at any depth (an MCP result's text block, an HTTP-style `body` inside it) is part of the result: a path that reaches it continues inside it, and every path also applies from its top. A string, number or key a declared path tokenized is tokenized wherever else the result repeats it whole (a `structuredContent` copy in the text block), however short it is, and a repeat as a JSON string, key or number inside text the detectors do not parse (JSON nested deeper, JSONL), as it is or decoded, tokenizes that whole text (the lookup is indexed once per result, so it is linear in the text); a boolean only where its path reaches it, so a tool that mirrors `structuredContent` in its text block should declare both paths, or a bare path, which also applies inside the text. Such a result is always committed as its re-serialized parse (a duplicate key keeps its last value), and numbers keep their source text. A declared value that is an issued token is left as it is. A call ID that two calls share is matched to no tool.
- JSON (an object, an array or a string) is scanned as a JSON reader sees it: string leaves and keys decoded, numbers as their literals, and JSON inside a string leaf (an MCP result's text) one level deep, so a value right after an escape such as `\n` or `\t` is found. Text that is not one JSON document (JSONL, a log-prefixed line) and JSON nested deeper inside a string are scanned as they are and then searched decoded: JSON escapes, percent-encoding (a form's `+` between letters or digits as a space), HTML character references and base64 or base64url runs that decode to UTF-8 text, breadth first over each new view, up to 27 views (`alice%40example.com`, `4111+1111+1111+1111`, `alice&#64;example.com`, `alice%2540example.com`, `alice&amp;#64;example.com`, JSON percent-encoded in a form field, a base64 mail body); anything only decoding shows tokenizes the whole text. Each string or number leaf is also checked with its member name (an array's items with their member's): any non-empty value of a member named `password`, `passwd`, `pwd`, `secret`, `client_secret`, `api_key`, `apikey`, `access_token`, `refresh_token`, `private_key` or `aws_secret_access_key`, and a value of eight characters or more under a name ending in a secret word or holding an API-key word (`DB_PASSWORD`, `dbPassword`, `GITHUB_TOKEN`, `x-api-key`, `openaiApiKey`, `vault_passphrase`; a bare `token` name is not enough, though a value of eight or more non-space characters under it reads as an env secret line), is a credential, and the name read as words is scanned beside the value, so a keyword-bound ID under its keyword (`mrn`, `passportNumber`, `national_id`) is found; either tokenizes the whole value. JSON is committed re-serialized, compact, only when something in it was tokenized, or when it repeats a key, whose earlier value the parse drops unread; otherwise its bytes are kept. It is not scanned again as a whole, so tokens never push it over the input limit. In other text, a JSON password detection replaces the whole quoted value, escaped quotes included.
- Each redaction writes one `PROTECTED_DATA_REDACTED` audit row whose payload is the new public contract `redaction-receipt` (`amc.redaction-receipt/v1`, `spec/schemas/v1/redaction-receipt.schema.json`, sources `user/message`, `user/attachment`, `tool/result`, `loop/inbox` and `operator/compaction`, with `gateway` and `bridge` reserved). It holds classes, detector names, counts, the matched declared paths, the detector-set digest and the SHA-256 of the redacted text, never a raw value. Gateway and bridge redactions write no receipt yet.
- In an opted-in workspace, evidence binds tool output with a keyed digest (HMAC-SHA256 under the workspace token key over the output's SHA-256) instead of a plain SHA-256 a short output could be brute-forced from. The tool pipeline decides the form once per call; the action journal's `outcomeDigest` binds it and names it (`outputDigest: { kind: "hmac-sha256", value }` instead of `outputSha256`), and the call's `stdout` row carries the same field. A delegate's `stdout` row and the `web_fetch` and `web_search` receipts (`contentDigest`, `deliveredDigest`) are keyed the same way. If the keys cannot load, the receipt is not written and the evidence recorder failure latches.
- The new deletion target kind `token-vault` lets `deleteTokens` remove rows only through the legal-hold deletion gate.

**Refusals.** Every failure refuses the commit with `RedactionRefused` (code `REDACTION_REFUSED`) and a static reason; the raw value is never committed:

- `vault_unavailable`: a locked vault or unavailable keys.
- `vault_integrity`: a vault row that does not verify.
- `token_collision`: a different value under an existing token, in the vault or earlier in the same redaction.
- `receipt_failed`: the receipt row could not be written.
- `detector_invalid`: text over 1,048,576 characters, JSON nested too deeply to parse, text whose decoding still changes after 27 decoded views, or a redaction that scans more than 33,554,432 characters in all.
- `content_not_text`: tool output or queued input that is not UTF-8.
- `attachment_not_redactable`: image and audio attachments, media inbox input (refused before anything is spilled), non-UTF-8 text attachments, and a tool result holding media (an MCP image or audio block, or a resource blob whose `mimeType` is not text or JSON), refused in opted-in sessions whatever the provider's processor contract covers.
- `declared_fields_unparseable`: a declaring tool's `OK` result that is not JSON.
- `declared_fields_unverifiable`: a signed tools config that no longer verifies, a result whose call the session never recorded (or whose call ID two calls share) while some tool declares fields, or any Code Mode (`run_code`) result while some tool declares fields.
- `runtime_unsupported`: every redaction on a runtime without `JSON.rawJSON` (Node 20, which `engines` still admits), because a re-serialized number could change.

A refused tool result or native-validation output is not thrown: the call is answered with `[amc] tool output withheld: protected-data redaction refused (<reason>)`, keeping the tool's recorded outcome, after a `PROTECTED_DATA_REDACTION_REFUSED` audit row naming the call and the reason. The session continues.

**Gateway and ToolHub evidence (opted-in workspaces).** The same detectors run over the bodies the gateway stores and over ToolHub evidence payloads (`redactBody`, which now takes `{ protectedData }`). A detected card number, IBAN, SSN, email, phone number, IP address, keyword-bound ID, health-record number or credential shape becomes `[REDACTED]` with a `protectedData:<class>` redaction reason, so `originalPayloadSha256` is omitted. JSON bodies stay valid JSON, and a detected number leaf becomes the marker string. A string leaf holding a JSON object or array (an MCP result's text) is read one level deep, so a value right after `\n` or `\t` is found, and every text is also searched decoded as in the session: anything only that shows replaces the text whole (`protectedData:unscanned`). A member's value is checked with its name as in the session and replaced whole (`protectedData:credential`, or the class a keyword-bound detection shows). A JSON body that does not parse, or whose walk fails, is replaced whole (`protectedData:unscanned`), and so is a body of another content type (a form post) in which the detectors still find something once decoded, or that is not plainly UTF-8 (a charset other than UTF-8, a byte-order mark, invalid UTF-8 or a zero byte, as UTF-16 has). A form, query or multipart field named as a secret (`password=`, `client_secret=`) has its value replaced. A streamed body is also checked across its chunks (the events of `text/event-stream`, the lines of `application/x-ndjson`, the elements of a top-level JSON array such as Gemini's `streamGenerateContent`): each chunk's delta strings (`delta.text`, `partial_json`, `thinking`, `delta.content`, `delta.reasoning`, `delta.reasoning_content`, `function.arguments`, the Responses API's `delta`, Gemini's `parts[].text`, Ollama's `message.content`) are joined per stream (path plus each object's `index`, `output_index` and `content_index`) and all together, and a value only the joins show, a chunk that is not JSON, or any failure there replaces the whole body (`protectedData:unscanned`); before this, a value a model streamed over several deltas was stored unredacted. Where the workspace opted in, stored request and response header values are scanned too, with the header name as the member name (an email in `x-user-email` or `helicone-user-id`, a `referer` query, `x-forwarded-for`, JSON metadata headers), and their reasons join the row's `redactionReasons`. The stored request path and query are scanned the same way. A JSON integer that parsing rounded (beyond 2^53, such as a 17-19 digit card number sent as a number), a text over 1,048,576 characters, and a body whose scanned text (keys, leaves, decoded views and member contexts) passes 16,777,216 characters are replaced whole (`protectedData:unscanned`). ToolHub's `tool_result` row also applies the signed tool definition's declared `protectedFields` (the session's walk, `[REDACTED]` for each declared value and every repeat the session would tokenize, inside JSONL or deeper JSON too; a tools config that no longer verifies stores the body as `"[REDACTED]"`), and a denial's message and the blast-radius consent, which quote argument paths, are stored redacted in payload and meta, with the consent digest over the redacted copy. Forwarded traffic is unchanged.

**Gateway credentials (every workspace).** The gateway stores the credential and lease headers it strips (`x-amc-lease`, `authorization`, `x-api-key`, `x-goog-api-key`, `api-key`, `x-openai-key`, `x-anthropic-api-key`) and `cookie`/`set-cookie` as `[REDACTED]` whatever `headerKeysDenylist` says, and also `proxy-authorization`, `x-amz-security-token` and any header whose name ends in `token`, `secret`, `auth`, `session`, `password` or `api-key`; every other stored header value gets the shared secret table and the configured `textRegexDenylist`. It stores the credential query keys (`key`, `api_key`, `api-key`, `access_token`, `amc_lease`) as `[REDACTED]` in the stored query; before this, `x-amc-lease` and `x-goog-api-key` were stored raw by default. The default denylist adds those headers, and the default `sk-` pattern becomes `(?i)\bsk-[A-Za-z0-9_-]{10,}` (project and Anthropic keys).

**Bridge evidence.** What the bridge stores (stdout and stderr telemetry, every key and leaf of object telemetry payloads such as `amc wrap`'s command arguments, and `POST /bridge/evidence` payloads, which were stored unredacted) goes through the new `bridgeEvidenceRedactor`: secrets in every workspace, and the same detectors, with `<AMC_REDACTED>`, where the workspace opted in; text and string leaves are read as in the gateway (JSON one level deep, searched decoded, a member's value checked with its name); each stored value may take 4,194,304 characters of detector scanning, and past that, on any scan failure, or for text holding a zero byte (UTF-16 output read as UTF-8), it is stored as the marker. `redactBridgeText` stays secrets-only, so control responses, deny reasons, the hook's stderr, `amc wrap`'s terminal output, hook identifier fields and request summaries are unchanged. `amc wrap` posts stdout and stderr telemetry a line at a time (or past 64 KiB), not per write, and settles every row before the exit row. The same redactor now covers the stored stdout and stderr rows of `amc adapters run`, `amc monitor --stdin` (stored raw before) and processes observed through `amc wrap <runtime>`, `amc supervise` and governed children, with their forwarded stdin: secrets in every workspace, detectors where opted in; terminal output is unchanged. So are the command and arguments those processes are recorded with (the `process_start` row of `amc wrap <runtime>`, wrap-any, `amc supervise`, governed children and sandbox runs, the `SANDBOX_EXECUTION_ENABLED` attestation, and `amc adapters run`'s `agent_process_started` row), after the run's lease, AMC's own lease and the vault passphrase are scrubbed. `amc adapters run` in `SANDBOX` mode passes the environment to the container by name (`docker run -e NAME`) instead of as `export` lines in its `sh -lc` script, which put the lease, the vault passphrase and every other environment secret into the stored argv in every workspace; the container's gateway and proxy endpoints now win over host-side values of the same name.

**Admission detectors.** A detector span inside an AMC token's 16-hex part is no longer a detection, but only for a token this workspace issued (looked up in the token vault); token-shaped text it did not issue, such as a raw card number in token brackets, is still detected, and an issued token whose hex happens to look like a card number is not. A span that crosses token text (a JSON `password` value holding a token beside raw text) stays a detection. A bare 13-digit run starting with 1 (a Unix-millisecond timestamp) is no longer a card number. A tool result is also scanned with its JSON escapes decoded, so a value right after `\n` or `\t` in a JSON result (every MCP result) is counted. The JSON password pattern covers the whole value, escaped quotes included, which also changes `scanForPII`'s replacement. The credential class adds OpenAI project, service-account and admin keys, GitHub `gh[pousr]_` and `github_pat_` tokens and Stripe live keys (also in `scanForPII` and the shared secret table), the shared table's Anthropic, Slack and Google keys, bearer values holding a digit, JWTs, a PEM private key block whole, a URL's password, `api_key`/`apikey`/`api_secret` assignments, a quoted member in text (JSON, a Python or JS literal), a form, query or command-line field and a multipart form part whose name passes the member check above, and env or YAML lines whose key ends in `PASSWORD`, `PASSWD`, `SECRET`, `SECRET_KEY`, `SECRET_ACCESS_KEY`, `PRIVATE_KEY`, `API_KEY` or `TOKEN` (value only); these count in admission too, and so does what a member name shows beside its value (a number leaf and an array's items included). The keyword-bound detectors also read their keywords joined by `_` (`medical_record_number`, `passport_no`, `national_id`, also in `scanForPII`) and a value after `=`. A value two rules find is one detection. These change the detector-set digest.

**Privacy redaction rules (every workspace).** `getBuiltInRedactionRules` and `applyRedaction` keep the same six rule IDs and replacements but delegate to the shared detectors instead of a second rule set, and never narrow them: each built-in rule keeps its earlier pattern and redacts the union of its matches and the detector spans, so non-Luhn 4x4 digit groups, any dotted quad, bare 10-digit runs, long email local parts and the `token=`/`secret:` key forms are still redacted. The detectors add Luhn-valid cards in other groupings, IPv6 addresses, E.164 phone numbers and the shared secret table's shapes (provider keys, bearer tokens, JWTs, `api_key`/`apikey`/`api_secret` forms). The earlier email pattern now matches in linear time. Text over 1,048,576 characters is replaced whole. A built-in rule's `pattern` now shows the union for reference. A caller's own rule, or a built-in rule with a changed pattern, still applies as a regex.

Known gaps (debt): no restoration path yet (the detokenization gate, processors on destinations and purpose binding are slice 3); opt-in through classes declared in the compiled policy; per-sub-call declared fields for Code Mode; the system prompt, tool schemas, model output (including model-written compaction summaries), approval questions and operator compaction reasons are recorded unredacted; names outside declared fields and values split across JSON fields or lines are missed, a member name is read only as far as the secret-name and keyword lists go (`vat_number` is not a VAT keyword), base64 that decodes to binary is not scanned (opted-in sessions withhold MCP media in tool results, but gateway, ToolHub and bridge evidence store it as it is), the caller-supplied fields of monitored process rows (mode, agent ID, route URLs) are stored as they are, and so is a value split across two writes in the per-write stdout and stderr rows of `amc adapters run` and the monitor; admission does not decode percent-encoding or HTML references; a declared object whose keys repeat the result's own structure (`type`, `text`) also tokenizes those keys elsewhere in the result; `ask_user` answer files and their receipt digest, and `amc wire serve` acceptance rows (the request prompt), hold raw values or plain digests because their signatures and the client's `requestSha256` bind the raw text; gateway and ToolHub evidence write no redaction receipt yet; the bridge's hook evidence and ToolHub's own action journal still hold plain digests of tool output; hostile text can hold the gateway for about 10 s per body before the scan budget replaces it. Synthetic fixtures, the labelled corpus, the detector quality report and the issue's tests are not written. This is partial, unqualified source; nothing was run beyond build-level checks and local probes.
