Experimental redaction of protected data before a native session row is committed (partial P2-02 source, slice 2). Tokenization reduces the identifiers that reach model context and logs. It is not de-identification or anonymization under any standard or regulation, and detection is heuristic.

**Opt-in, per workspace.** Redaction applies only where the processor registry `.amc/dataflow/processors.yaml` or its `.sig` exists (or that cannot be checked), the same opt-in as protected-request admission. Every composed native session is wrapped and checks the opt-in on each record, so a long-lived session starts redacting as soon as the workspace opts in; the opt-in is latched per process, so removing the registry never turns it off mid-process. In other workspaces, native sessions, gateway and ToolHub evidence and the action journal are unchanged; bridge evidence gains secrets redaction of object payloads, and the built-in privacy rules are the exception listed below. In an opted-in workspace, native sessions composed by `amc agent run`, scheduled passes, ACP, the SDK, A4 Assemble and delegated child sessions tokenize the following before any row, spill or model-visible part is written: queued inbox text, user messages, text attachments (content and file name), tool results, native-validation check output, and operator compaction text (`amc session compact`, validated after redaction, its receipt written just before the append).

- A token is `[[amc:<class>:<16 hex>]]`: the first 64 bits of HMAC-SHA256 under a per-workspace key. The same value gives the same token within a workspace; another workspace gives a different token.
- The keys are one vault secret, `dataflow.token-keys.v1`, created on first use; an evicted vault session is reopened from `AMC_VAULT_PASSPHRASE`, as signing does. Values are kept AES-256-GCM encrypted in `.amc/dataflow/token-vault.sqlite`, which the default `.amc` backup scope includes.
- Only tokens this workspace issued are treated as tokens: the redactor and admission look token-shaped text up in the token vault (read-only, cached per request), and any other token-shaped text, such as a raw card number in token brackets, is scanned as data.
- Tool definitions in the signed tools config can declare `protectedFields` (dot paths into the JSON result, for example `patient.name: phi`). These are tokenized first, in every outcome (an `OK` result must be JSON; error text that is not JSON gets the detectors only); the existing detectors are the backstop. Strings, numbers, booleans and object keys under a declared path are tokenized. Such a result is always committed as its re-serialized parse (a duplicate key keeps its last value). Numbers keep their source text on Node 21 and later; on Node 20 a number literal a double would change refuses. A declared value that is an issued token is left as it is. A call ID that two calls share is matched to no tool.
- JSON holding `\u` escapes is committed re-serialized, so the detectors scan the characters it stands for, and a JSON password detection replaces only the value.
- Each redaction writes one `PROTECTED_DATA_REDACTED` audit row whose payload is the new public contract `redaction-receipt` (`amc.redaction-receipt/v1`, `spec/schemas/v1/redaction-receipt.schema.json`, sources `user/message`, `user/attachment`, `tool/result`, `loop/inbox` and `operator/compaction`, with `gateway` and `bridge` reserved). It holds classes, detector names, counts, the matched declared paths, the detector-set digest and the SHA-256 of the redacted text, never a raw value. Gateway and bridge redactions write no receipt yet.
- In an opted-in workspace, evidence binds tool output with a keyed digest (HMAC-SHA256 under the workspace token key over the output's SHA-256) instead of a plain SHA-256 a short output could be brute-forced from. The tool pipeline decides the form once per call; the action journal's `outcomeDigest` binds it and names it (`outputDigest: { kind: "hmac-sha256", value }` instead of `outputSha256`), and the call's `stdout` row carries the same field. A delegate's `stdout` row and the `web_fetch` and `web_search` receipts (`contentDigest`, `deliveredDigest`) are keyed the same way. If the keys cannot load, the receipt is not written and the evidence recorder failure latches.
- The new deletion target kind `token-vault` lets `deleteTokens` remove rows only through the legal-hold deletion gate.

**Refusals.** Every failure refuses the commit with `RedactionRefused` (code `REDACTION_REFUSED`) and a static reason; the raw value is never committed:

- `vault_unavailable`: a locked vault or unavailable keys.
- `vault_integrity`: a vault row that does not verify.
- `token_collision`: a different value under an existing token, in the vault or earlier in the same redaction.
- `receipt_failed`: the receipt row could not be written.
- `detector_invalid`: text over 1,048,576 characters.
- `content_not_text`: tool output or queued input that is not UTF-8.
- `attachment_not_redactable`: image and audio attachments, media inbox input (refused before anything is spilled) and non-UTF-8 text attachments, refused in opted-in sessions whatever the provider's processor contract covers.
- `declared_fields_unparseable`: a declaring tool's `OK` result that is not JSON, or (Node 20 only) one with a number a double would change.
- `declared_fields_unverifiable`: a signed tools config that no longer verifies, a result whose call the session never recorded (or whose call ID two calls share) while some tool declares fields, or any Code Mode (`run_code`) result while some tool declares fields.

A refused tool result or native-validation output is not thrown: the call is answered with `[amc] tool output withheld: protected-data redaction refused (<reason>)`, keeping the tool's recorded outcome, after a `PROTECTED_DATA_REDACTION_REFUSED` audit row naming the call and the reason. The session continues.

**Gateway and ToolHub evidence (opted-in workspaces).** The same detectors run over the bodies the gateway stores and over ToolHub evidence payloads (`redactBody`, which now takes `{ protectedData }`). A detected card number, IBAN, SSN, email, phone number, IP address, keyword-bound ID, health-record number or credential shape becomes `[REDACTED]` with a `protectedData:<class>` redaction reason, so `originalPayloadSha256` is omitted. JSON bodies stay valid JSON, and a detected number leaf becomes the marker string. A JSON integer that parsing rounded (beyond 2^53, such as a 17-19 digit card number sent as a number), a text over 1,048,576 characters, and a body whose scanned keys and leaves pass 16,777,216 characters are replaced whole (`protectedData:unscanned`). Forwarded traffic is unchanged.

**Bridge evidence.** What the bridge stores (stdout and stderr telemetry, every key and leaf of object telemetry payloads such as `amc wrap`'s command arguments, and `POST /bridge/evidence` payloads, which were stored unredacted) goes through the new `bridgeEvidenceRedactor`: secrets in every workspace, and the same detectors, with `<AMC_REDACTED>`, where the workspace opted in. `redactBridgeText` stays secrets-only, so control responses, deny reasons, the hook's stderr, `amc wrap`'s terminal output, hook identifier fields and request summaries are unchanged.

**Admission detectors.** A detector span inside an AMC token's 16-hex part is no longer a detection, but only for a token this workspace issued (looked up in the token vault); token-shaped text it did not issue, such as a raw card number in token brackets, is still detected, and an issued token whose hex happens to look like a card number is not. A span that crosses token text (a JSON `password` value holding a token beside raw text) stays a detection. A bare 13-digit run starting with 1 (a Unix-millisecond timestamp) is no longer a card number. These change the detector-set digest.

**Privacy redaction rules (every workspace).** `getBuiltInRedactionRules` and `applyRedaction` keep the same six rule IDs and replacements but delegate to the shared detectors instead of a second rule set, and never narrow them: each built-in rule keeps its earlier pattern and redacts the union of its matches and the detector spans, so non-Luhn 4x4 digit groups, any dotted quad, bare 10-digit runs, long email local parts and the `token=`/`secret:` key forms are still redacted. The detectors add Luhn-valid cards in other groupings, IPv6 addresses, E.164 phone numbers and the shared secret table's shapes (provider keys, bearer tokens, JWTs, `api_key`/`apikey`/`api_secret` forms). The earlier email pattern now matches in linear time. Text over 1,048,576 characters is replaced whole. A built-in rule's `pattern` now shows the union for reference. A caller's own rule, or a built-in rule with a changed pattern, still applies as a regex.

Known gaps (debt): no restoration path yet (the detokenization gate, processors on destinations and purpose binding are slice 3); opt-in through classes declared in the compiled policy; per-sub-call declared fields for Code Mode; the system prompt, tool schemas, model output (including model-written compaction summaries), approval questions and operator compaction reasons are recorded unredacted; names outside declared fields, values split across JSON fields or lines, and `\u` escapes in text that is not JSON are missed; `ask_user` answer files and their receipt digest, and `amc wire serve` acceptance rows (the request prompt), hold raw values or plain digests because their signatures and the client's `requestSha256` bind the raw text; gateway and ToolHub evidence write no redaction receipt yet; the JSON password heuristic does not fire in gateway and bridge JSON evidence; the bridge's hook evidence and ToolHub's own action journal still hold plain digests of tool output; hostile text can hold the gateway for about 10 s per body before the scan budget replaces it. Synthetic fixtures, the labelled corpus, the detector quality report and the issue's tests are not written. This is partial, unqualified source; nothing was run beyond build-level checks and local probes.
