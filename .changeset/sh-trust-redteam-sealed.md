Red-team runs are ledgered, sealed and signed (SH-TRUST-03). `amc redteam run` without `--no-sign` writes every attack prompt, reply and graded result into a sealed `amc-redteam-runner` ledger session (`source: "redteam"`), verifies the ledger, and seals the report with the artifact-seal key (`reportJsonSha256`, `runSealSig`, `sessionId`); `verification` reads `signed: true, status: SIGNED_VALID, mode: vault-signed` (or `SIGNED_INVALID` when the ledger did not verify). A locked vault refuses a signed run with the assurance runner's remediation. `--no-sign` (the `amc ci redteam` default; `amc ci redteam --sign` opts in) writes rows only under `AMC_NO_SIGN=1`, into the unsigned store, and otherwise records nothing, and says so; `AMC_NO_SIGN=1` makes every red-team run unsigned whatever flag was passed. A signed `--evil-mcp` run writes the Evil MCP scenarios into the same sealed session (pack `evil-mcp`, `evilMcp.scenarioResults`), and the readers gate them. An interrupted signed run (SIGINT, SIGTERM) seals its session before the process dies of the signal, for the assurance runner too. Gateway receipts an agent under test returns are admitted as the reply arrives only when bound to that exchange; a forged or replayed one is audited and dropped, never a reason to refuse the run. New reader `src/redteam/redteamStore.ts` (`verifiedRedTeamReports`, `verifyRedTeamReportFile`) returns only signed runs whose seal and ledger provenance verify (`REDTEAM_UNSIGNED`, `REDTEAM_SEAL_INVALID`, `REDTEAM_PROVENANCE_*`) and names the refused files that block the newest one (`blocking`, the assurance readers' `refusedRunsBlocking` rule); `amc ci redteam --sign` re-reads the signed run it just wrote and fails with that name. The assurance evidence writers take a `source`, and `REDTEAM_SCENARIO_INCONCLUSIVE` is registered as non-maturity. `amc redteam attack` is unchanged.
