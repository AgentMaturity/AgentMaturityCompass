Breaking: the native shell is refused on macOS and Windows unless the operator passes `--unsafe-unconfined-shell` or starts Studio with `AMC_UNSAFE_UNCONFINED_SHELL=1`; opted-in sessions record enforcement none.

On macOS the `bash` tool used to run `/bin/sh` with your full user rights on every `--tools workspace` run, and nothing recorded that it was unconfined. It is now offered only after an explicit opt-in: `--unsafe-unconfined-shell` on `amc agent-loop run`, `amc agent-loop chat` and `amc acp`, `allowUnconfinedShell` in the SDK, or `AMC_UNSAFE_UNCONFINED_SHELL=1` in the environment of `amc studio start` or `amc up` (the only opt-in Studio accepts; the CLI, ACP and SDK never read it). No workspace file can opt in: `runtime.shell.allowUnconfined` in `.amc/amc.config.yaml` is not honoured even when signed, because a workspace can sign its own config. Each opted-in session prints a warning on stderr and records `NATIVE_SHELL_UNCONFINED_ENABLED`; each unconfined call records `enforcementLevel: "none"`. Windows and other platforms are refused even with the flag. Linux without a usable `/usr/bin/bwrap` no longer offers the shell at all, and the opt-in never enables an unconfined Linux shell. `amc verify --sign-config` signs the config, as earlier messages already advised; a signature does not make the config an opt-in. Studio's native-task options now include `shell`, and task setup shows its refusal or warning text as a banner. `AMCNativeClient` does not surface the spawned process's stderr, so SDK callers see the receipts but not the printed warning.
