A4 Forge command line (P1-65, preview). `amc a4` adds 22 commands: `guide`, `list`, `show`, `readiness`, `verify`, `approve`, `deny`, `request-changes`, `complete`, `hold`, `resume`, `reopen`, `tune`, `retire`, `members`, `gate-policy`, `release`, `deploy prepare`, `deploy record`, `deploy verify`, `rollback` and `export`. Without `AMC_A4_PREVIEW=1` every one of them is refused with `A4_PREVIEW_DISABLED` and exit code 1, as the API answers 404.

- Same routes as the API: each command except `verify` and `export` runs the `/api/v1/a4` route in process, with the same body schemas, refusals, gate functions, separation of duties, quorum, request deduplication (`--request-id`; a retry answers the recorded result), audits and effects. A refusal prints `amc a4 <command> refused (<status>): <CODE>: <message>` (or the API's JSON error with `--json`) and exits 1. An effect that `complete`, `release` or `rollback` leaves running finishes before the command does; one that fails exits 1 although the consumed gate stays recorded.
- Identity: writes need `--session-token-file`, an `amc approvals login` token file that is a regular, private (0600) file and not a symbolic link. Its user is re-read from the signed `users.yaml` and recorded with admission `native_login_token` and identity check `users_yaml`. A user who is no longer ACTIVE is refused, and so is a token that holds a role `users.yaml` no longer grants. The route's role class then applies as for a browser session. `--username`, `--roles` and `--user-id` are refused with `IDENTITY_FLAG_REFUSED`. Reads without a token answer as the admin token does: every project, reads only. Writes are refused with `NATIVE_READ_ONLY` while the users or trust signature does not verify, and `amc mode agent` blocks the owner-gated commands.
- Decisions: `approve`, `deny` and `request-changes` take `--gate`, `--reason`, `--expect-binding-digest` and `--expect-gate-seq`. Approve and deny also take an optional `--expect-readiness-digest`. The digests and seq are checked inside the governed transition (request-changes checks the binding digest before it). `amc a4 guide <projectId>` prints the stage model, the next action and these pins for every open gate.
- Results: `list`, `show`, `readiness`, `verify`, `release`, `deploy verify` and `export` print their claim label, or carry `claimKind`, `statusDimensions` and `claimLabel` with `--json`. `readiness --json` prints the readiness object the API returns.
- Verify: `amc a4 verify <projectId|file>` checks a project's chain (`verifyA4Chain`), or an exported `.amcbundle` or `amc.a4-record/v1` file (`verifyA4Bundle`), under the caller's own `--trust-list` and `--trust-root`. It exits 0 when trusted, 1 when it fails, and 2 when it is integrity-only under `--allow-unpinned` or `--allow-unanchored`. This is the only A4 surface where the caller names a trust list.
- Export: `amc a4 export <projectId> --run <runId> --out <file>` is `amc bundle export` for the project's agent, with its A4 records. `--out` must lie inside the workspace and must not be a symbolic link.
- REPL: "a4 status <projectId>" runs `amc a4 readiness`, "show project <projectId>" runs `amc a4 show`, and either without an id lists the projects.
