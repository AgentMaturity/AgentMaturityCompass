RFC 9162 transparency trees and public anchoring in Rekor v2 (P1-26). New workspaces grow their transparency Merkle index as an RFC 9162 tree (`rfc9162-sha256`: domain-separated SHA-256 over the entry hashes' raw bytes, promoted odd subtrees, inclusion and consistency proofs checked from leaf index and tree size). Signed roots, proofs and ledger checkpoints name their tree in `algorithm`; one without it is `amc-legacy-v1`, the older tree in which `[a, b, c]` and `[a, b, c, c]` share a root, which existing workspaces keep until `amc transparency merkle rebuild --algorithm rfc9162-sha256` migrates them (the legacy root must verify; a signed `migration.json` binds both roots, and a `MERKLE_TREE_MIGRATED` log entry re-seals the log). Asking for the legacy tree on an RFC 9162 log is refused. Proof bundles from `amc transparency merkle prove` now also carry the signed `root.json` and `root.sig`, and export refuses when the proof's root is not the signed current root. Existing passports, certificates, binders, bench bundles, session anchor proofs and proof bundles keep verifying as legacy proofs; AMC versions before this one cannot verify RFC 9162 proofs and fail them. Operators can pin public logs in signed trust lists (`transparencyLogs`) and name them in `.amc/amc.config.yaml` (`transparency.anchors`, `transparency.anchorEvery`: `daily` by default, or `checkpoint`). With anchors and a TSA configured, the Studio scheduler signs a C2SP checkpoint note for the newest ledger checkpoint whose tree is RFC 9162 (origin `amc-transparency/<workspaceId>`, bound to the ledger checkpoint by an extension line), timestamps its SHA-256 with RFC 3161 first, then submits only that digest as a Rekor v2 `hashedrekord` entry signed with a one-time P-256 key, through the egress host decision, without redirects; replies are stored verbatim under `.amc/transparency/anchors/`. Proof bundles carry the newest anchor and an RFC 9162 consistency proof to their signed root, and their verifier report gains `anchoring.public` (`anchored` with backend and log index, `not-anchored`, or `invalid`, which is also an integrity failure). An anchor shows that a checkpoint digest was recorded in a public log, not that the evidence is true. SCITT anchoring is not included. No dependency was added.

Security: the tree a log grows is sticky and fails closed. It is legacy only while the signed current root, the log seal (re-signed on every append with `merkleAlgorithm` and bound to the last entry) and the absence of a migration record all say so; anything missing or unverifiable means RFC 9162, and a legacy root after a migration fails verification. Verifiers take the tree and tree size from the signed root (bundle `root.json`, `proofs/merkle.root.json`, the session proof's signed root), never from the proof; a bundle without a signed root is checked as legacy only. Public anchors verify only against logs and TSAs pinned in signed trust lists and an auditor key admitted for `artifact-seal`; a key a log reply carries never counts. The workspace's own key checks of roots and seals are a local audit trail only.
