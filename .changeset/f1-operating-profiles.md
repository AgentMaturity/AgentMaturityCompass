`amc domain apply` now also writes a station operating profile, `amc-operating-profiles/<agent>/<station>.operating-profile.json` (or `--profile-out <path>`, never under `.amc/`). It proposes the tool allowlist posture, firewall mode, approval classes, budget ceilings, retention, audit sampling, human oversight and incident-reporting clocks, each with the source it rests on and the date that source was read. The JSON result gains `operatingProfile` (station, risk tier, path, written, consistency). A profile is self-reported configuration, not a compliance verdict, and its regulatory citations are experimental until an expert signs them off.

Every profile value carries a fact status (`asserted`, `observed` or `reviewed`, with `reviewedBy` and `reviewedAt` for reviewed). Every value is `asserted` when a profile is emitted, and the profile counts them in `profileFacts`. Profiles now have `schemaVersion: "2026-10-07"`; a `"2026-10-03"` profile is still read, with every value treated as asserted.

The wealth profile cites Federal Reserve SR 26-2 (17 April 2026) instead of the superseded SR 11-7, and only for validating the traditional models the agent calls, because SR 26-2 does not cover generative or agentic AI. Approval counts, the financial budget, reviewer roles and the override path that SR 11-7 used to back keep their values. They now cite the AMC operating choice and are flagged for expert review.

New flags on `amc domain apply --agent <id>`: `--sign-profile <path>` signs a reviewed profile with the workspace auditor key (`<path>.sig`) and refuses an inconsistent profile. `--activate-profile <path>` writes and signs the approval policy, budgets (only this agent's entry), tools, action policy, ops policy and runtime firewall policy from a signed profile, then records `<station>.activation.json`. Activation refuses a profile that is unsigned, edited after signing, signed by a key that is not the workspace auditor key (or, when an operator trust list exists, a key the list does not admit for config signatures), inconsistent, or written for another agent. It also refuses any profile that would weaken a current signed config unless `--allow-widening` is passed, and lists every accepted weakening in the activation record. Every field of all six configs is compared. Fewer approvals, an added tool or allow entry, a removed deny entry, a relaxed action rule, shorter retention, a raised or removed limit and a weaker firewall mode are among the changes that count as weaker. Any change the comparison cannot rank also counts as weaker. A missing budgets, tools or action-policy file or firewall policy fails closed at runtime, so activating one counts as weaker too. Because station profiles keep audit logs for the period their sources require, which is shorter than the default ops policy's 3,650-day archive retention, activation on a default workspace needs `--allow-widening`. `--dry-run` prints the target paths and digests and writes nothing. A signature shows who signed a profile and that it is unchanged, not that its values are correct.

Security: `--sign-profile` and `--activate-profile` are blocked in agent mode, in the signing and activation functions themselves, so an agent cannot rewrite the policies that govern it. Activation checks and writes under the action-policy writer lock that `amc policy pack apply` also holds, and `--allow-widening` lifts none of these gates.

Security: the weakening check covers all six configs, including tools, the action policy and the ops policy, and every field of an approval rule, including a removed rule. It fails closed on changes it cannot rank.
