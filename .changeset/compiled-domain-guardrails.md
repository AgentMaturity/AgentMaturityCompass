Compiled control plans are enforced in the native tool pipeline, every native session records the policy it ran under, and domain apply no longer claims rules it does not enforce (P1-12). The catalog content stays experimental: enforcing a control is evidence of conformity planning, not a compliance claim.

- Activation: `amc catalog compile ... --activate <approvalRequestId>` makes the plan just compiled the workspace's active compiled policy. It is blocked in agent mode and refuses unless the plan's digest and `CONTROL_PLAN` signature verify, the plan is `ready`, the shipped catalog matches the plan's lockfile, the named plan review (from `--request-review`) approved exactly this plan, and, against the plan already active, nothing weakens unless `--allow-weakening`. The review is consumed, so one review activates once. The plan is kept in a signed control journal under `.amc/control-plan/` with its checkpoint and signer pin outside the workspace, so deleting or rolling back the journal is an integrity failure, not "no policy". No new command path.
- An active plan makes the workspace a regulated profile. Native sessions and the kernel tool service load it at start, verifying the journal, the plan's digest and signature in the same read, and the catalog lockfile; a plan that does not verify refuses the session (`Refusing to start: the active compiled policy cannot be verified (...)`).
- A new `compiled-policy` guard runs first and fails closed. It denies a tool not in the plan's `toolPipeline.visibleTools`, enforces `identity-binding` (no verified lease: `IDENTITY_UNRESOLVED`; no authenticated principal, an OS user name being self-reported: `PRINCIPAL_UNRESOLVED`), denies any compiled guard it does not implement, denies an action class whose live signed approval policy is weaker than the compiled approval rule, and denies every call once the active plan differs from the one the session started with. Denials name the control: `compiled policy denied this call (control <id>@<version>): <reason>`. Native sessions carry no lease yet, so under any plan that includes `L0-IDN-01` every native tool call is denied until a composition supplies one. The compiler now counts `identity-binding` as registered, so `L0-IDN-01` is no longer listed `unsupported`.
- Under a plan every call is bound to an authorization record, the plan's `approvalRequiredFor` classes need a signed approval, and records carry `control.controlId`, `control.controlVersion`, `policy.compiledPolicyDigest` and `policy.policyRevision`; the compiled digest is part of the deployment digest an approval binds. Egress and deletion rules are kept on the policy object and are not enforced (P2-01).
- Effective-policy receipt: before its first governed tool call, and again when its guard set changes, every native session writes an `EFFECTIVE_POLICY` audit row and a signed artifact (`effective-policy-receipt`, `.amc/effective-policy/<receiptId>.json`) listing the compiled policy, plan and lock digests and revision, each control in force with its enforcement, boundary and catalog review status, the guard labels, the 14 guardrails as the session ran them, domain-apply rules (`enforcement: "none"`), strict evidence binding (always enabled since P1-07) and the downgrades `no_compiled_policy` and `unenforced_domain_rules`. Every authorization record cites the receipt in `evidenceRefs`. A receipt that cannot be written denies the call.
- `amc domain apply` writes `domainRuleProposals` (`status: "proposed"`, `enforcement: "none"`) instead of `domainRules` booleans, converts existing booleans into proposals, and renders each rule as `Proposed control (not enforced by AMC until compiled): ...`. `DomainApplyResult` gains `guardrailsProposed`; `guardrailsEnabled` is deprecated, always `[]`, and is removed in the next minor release. The CLI prints `Proposed Controls (not enforced by AMC)`.
- Guardrail status gains `enforcement` and `boundary` for all 14 guardrails: the three Runtime Firewall rules are `enforced` in block mode, `observed` in observe or warn mode, else `none`; `tool-call-allowlist` and `cost-budget-limit` are `enforced` at `tool-pipeline:guard:tool-allowlist` and `tool-pipeline:guard:budgets` (source `tool-pipeline`); `human-approval-gate` is `none` in the workspace listing and `enforced` at `approvals` only in a session whose receipt lists a compiled approval rule; the other eight are "Catalog reference; not enforced by AMC." `amc guardrails list` shows `PIPELINE` for the pipeline rows, and `amc guardrails profile` marks each guardrail it cannot request `(not enforced)` or `(enforced at <boundary>)`.
