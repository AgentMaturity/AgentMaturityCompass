## P0-45 · Stop amc verify --repair from deleting reports and blobs

**Gate** G0 · **Epic** E03 Verification, keys and trusted time · **Priority** High · **Due** 2026-10-22 · **Effort** S (under 1 person-week) · **Route** Agent-Doable · **Tags** Bug

**Blocked by** none · **Blocks** GATE-G0 · **Old Linear issues** none · **Plan refs** gap G23 (High: retention deletes without checking holds, L104); strategy "How AMC makes a regulated claim › Failure behaviour" (legal hold unknown at deletion: deny, L330) and decisive acceptance test "Unknown legal hold at scheduled deletion" (L344); design rule 6 "Fail closed" (L365); Layer 0 family 10 "Logging and retention" (L441); Agent contract truth rule 2

### Why this matters

`amc verify --repair` destroys evidence. Before it checks anything, it deletes `.amc/blobs` (every encrypted evidence payload and the signed blob index) and `.amc/reports`. The re-check then finds events whose payloads are gone, and that error makes it delete the SQLite ledger too. On a healthy workspace that stores any payload as a blob, the command leaves no evidence, prints "Repair complete" and exits 0. The CLI even recommends `--repair` when signatures fail, which is what tampering looks like. A regulated deployment must keep its record, and no routine command may erase the trace of an attack.

### Goal

`amc verify --repair` never deletes or rewrites evidence. Alone it diagnoses and prints a plan; with `--apply` and a confirmation it moves a failing evidence store into a timestamped quarantine folder, after a legal-hold check, and writes a signed receipt. Every original byte stays reachable.

### Scope

**In:** removing every delete from the `verify` path; plan mode; quarantine with a manifest; `--apply` and `--yes`; legal-hold refusal; a signed receipt (`REPAIR_RECEIPT`); disclosure of archived stores in `amc verify`; corrected messages; tests, changeset and docs. **Out:** a hold registry at every deletion executor (P2-01); signing-key purposes and rotation (P1-08, P0-37); 1.x relabelling and migration receipts (P1-35); recovering lost evidence (impossible; repair reports it); `amc doctor-fix` (see Risks).

### Step-by-step

1. Branch `rtd/p0-45-verify-repair-no-delete` from `origin/main`.
2. Write the tests first (below). Run the CLI cases on `main` and confirm the healthy-workspace case fails because the blobs and the ledger vanish.
3. Create `src/ledger/verifyRepair.ts`. It imports no CLI, compliance or signing module; the caller injects them.

```ts
export type RepairErrorClass = "missing_blob" | "payload_mismatch" | "signature_invalid"
  | "trust_root" | "ledger_missing" | "other_chain" | "governance";
export interface StoreFile { path: string; bytes: number; sha256: string } // workspace-relative, POSIX
export interface RepairPlan {
  verified: boolean;
  chainOk: boolean;
  errorCounts: Partial<Record<RepairErrorClass, number>>;
  errors: string[];                          // first 200 verifier messages
  action: "none" | "archive_evidence_store";
  files: StoreFile[];                        // what --apply would move
}
export interface RepairReceipt {
  v: 1; type: "amc.verify-repair"; id: string; createdAt: string; amcVersion: string;
  trigger: { errorCounts: RepairPlan["errorCounts"]; errors: string[] };
  legalHold: { state: "none"; checkedAt: string };
  moved: Array<{ from: string; to: string; bytes: number; sha256: string }>;
  untouched: string[];                       // always includes ".amc/reports"
}
export type HoldState = { state: "none" } | { state: "active"; holdIds: string[] } | { state: "unknown"; reason: string };
export class RepairRefused extends Error {}
export function planVerifyRepair(workspace: string): RepairPlan;
export function applyVerifyRepair(workspace: string, plan: RepairPlan, deps: {
  legalHolds: () => HoldState;
  sign: (digestHex: string) => SignedDigest; // the return type of signDigestWithPolicy
  now?: () => Date;
}): { quarantineDir: string; receipt: RepairReceipt };
```

4. `planVerifyRepair` runs `verifyLedgerIntegrity` and classifies messages by text ("Missing blob file", "payload hash mismatch", "payload authentication failed", "signature invalid", "trust root:", "Evidence ledger is missing"). `action` is `none` when the workspace verifies, when only governance failed (`chainOk` true: evidence is fine, configs need re-signing) or when the ledger is already missing. Otherwise it is `archive_evidence_store`, and `files` lists every existing file among `.amc/evidence.sqlite` with its `-wal` and `-shm`, everything under `.amc/blobs/`, and `.amc/sessions/*.jsonl` for a JSONL-backend workspace, each hashed now. Nothing else is ever listed.
5. `applyVerifyRepair` runs in this order; a refusal before step 6 changes nothing:
  1. `action` must be `archive_evidence_store`.
  2. Refuse on `trust_root` errors: the monitor key does not match `AMC_EXPECTED_MONITOR_FINGERPRINT`, so a fresh ledger would be signed with an unexpected key.
  3. `legalHolds()`: `unknown` refuses with `legal hold state unknown: <reason>`; `active` refuses and names the hold ids.
  4. Re-hash every planned file; any change refuses ("evidence changed since the plan").
  5. Call `sign()` once on the plan digest as a pre-flight; a throw (for example "trust config signature invalid") refuses.
  6. Create `.amc/quarantine/<id>/` (`<id>` = UTC `YYYYMMDDTHHMMSSZ` plus 8 random hex characters; fail if it exists) and write `repair-plan.json` there first as the intent record.
  7. `renameSync` each file to the same relative path under the quarantine folder, the three SQLite files together. On any error (`EXDEV`, `EPERM`), move back what already moved and refuse. Never copy and then delete.
  8. Re-hash each file at its new path; a mismatch aborts and names the file.
  9. Write `repair-receipt.json` and `repair-receipt.json.sig` (the envelope from `sign()` over the receipt's SHA-256), each through a temp file and a rename.
6. Create `src/cli-verify-repair.ts` exporting `runVerifyRepair(opts: { apply: boolean; yes: boolean }): Promise<number>` (the exit code). Plan mode prints error counts, the files and total size `--apply` would move, and "Nothing has been changed." With `--apply` it asks the user to type `archive` on a TTY and requires `--yes` otherwise. Holds: `getActiveLegalHolds(undefined, workspace)` filtered to unexpired holds (the `isTenantUnderLegalHold` rule); a throw means `unknown`. Signing: `signDigestWithPolicy({ workspace, kind: "REPAIR_RECEIPT", digestHex })`. Exit codes: 0 verified, nothing to do, or archive done; 1 verification failed and nothing changed; 2 refused.
7. Rewrite the `verify` action in `src/cli.ts`: delete both `rmSync` blocks and the ledger-deletion block; route `--repair` to `runVerifyRepair`; add `--apply` and `--yes` (options on an existing command, not new command paths). Help text for `--repair`: "Diagnose a failed verification and print a recovery plan (changes nothing)". Replace the hint at 6360-6363 with "Every event signature failed. A re-initialized vault and altered evidence look the same here; keep the files and run amc verify --repair to see the options." Replace the tip at 6372-6374 with "Tip: amc verify --repair explains the failure; it changes nothing without --apply."
8. After any verdict, if `.amc/quarantine/*/repair-receipt.json` exists, print `Note: N archived evidence store(s) failed verification; latest receipt: <path>`. Warn about a quarantine folder with a plan but no receipt (an interrupted repair).
9. Add `"REPAIR_RECEIPT"` to `SIGN_KINDS` and `signKindValues`; keep the two lists identical.
10. Changeset: "`amc verify --repair` no longer deletes `.amc/blobs`, `.amc/reports` or the evidence ledger. It prints a recovery plan; `--apply` moves a failing evidence store to `.amc/quarantine/` with a signed receipt after a legal-hold check." ### Risks and gotchas

- Move `evidence.sqlite` together with its `-wal` and `-shm`; moving the database alone loses committed rows. Refuse while another AMC process holds the ledger open (Not verified how a writer is detected; start at `src/ledger/ledgerConnection.ts`).
- Archiving moves the whole store even when one blob failed. That is deliberate: a ledger with holes cannot verify, and the plan says so.
- A fresh ledger makes `amc verify` pass again. The receipt and the archived-store note keep the failed history visible; never make the note optional.
- Refusing on any active hold is broad (a hold for one tenant blocks the whole workspace). Accept that for G0; P2-01 scopes holds.
- Windows: renaming an open file fails with `EPERM`; report it and leave the files in place.
- `amc doctor-fix` also deletes files (`unlinkSync` at `src/doctor/doctorFix.ts:122, 126, 158`). Not verified what it removes; check that it never touches evidence under `.amc/`, and propose a follow-up issue if it does.
