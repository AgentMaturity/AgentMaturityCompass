The untrusted-project run registered nothing. Per-case results per version are in `pi-conformance.json` and rendered into `docs/adapters/pi.md`.

Twenty from the earlier rounds, one per guard (request binding, receipt signature, input freeze, version gate, server-derived action id, single-use nonce, ask denial, mapping table and its prototype-name guard, event shape, record binding, fail closed, mint/parse kind agreement, receipt purpose key pin, five on session registration). - Decision latency (extension handler to result through the loopback Bridge): p50 60 ms (1.0.2) and 66.5 ms (1.0.4), p95 101.8 ms and 99.6 ms (n = 100 each), above the 50 ms p95 overhead target, with a load average near 13 from other worktrees' test runs. The per-call disk recheck alone measured p50 0.49 ms and p95 0.95 ms warm.

What this supports: AMC's decisions at Pi's `tool_call` hook were honoured by these two Pi releases in these cases, for sessions that registered with AMC. Every call rechecks the installed extension file, AMC's module and the Pi install against the registration (a digest cache keyed on dev, inode, size and ctime); after a swap the call is denied as not governed. A registration is a lease-holder attestation: registration made with the session lease and matching on-disk extension and Pi digests. A process holding the lease can still attest without Pi. AMC cannot prove Pi executed the hook; it can prove only that every allowed call went through AMC with a signed receipt. This does not cover OS containment, effects outside `tool_call`, an extension that rewrites Pi's tool registry, or a Pi that does not load the extension: AMC cannot see sessions where Pi did not load the extension; they are reported as not governed (the untrusted-project case shows a write running with no AMC decision and no registration). Pi ask is always denied until an AMC approval path exists. Decision and registration receipts are signed with the workspace's own receipt purpose key: a local audit trail, not a portable verdict.
