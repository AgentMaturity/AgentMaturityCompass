# P1-19 oracle v2: fixed financial policy and exact expectations

This is a separate, closed, unexecuted private correction. The v1 source, interface, README and pins remain byte-identical. No repository source, product runtime, import, parser, SQL connection, test or service was executed while preparing v2.

The first correction separates signed artifact integrity from approval strength. V1 independently verified signatures and counted votes but trusted the request's own quorum fields. Authentic bytes could therefore describe a weaker request than the signed policy's FINANCIAL requirement. V2 adds external manifest fields `approvalPolicySha256` and `financialRule`. The former is the operator-reviewed exact default approval-policy byte hash, recorded independently of a later possibly weaker live policy. The latter must be the finite current default: two approvals, distinct users, the exact unique role set OWNER and AUDITOR, and ten minutes. Those defaults are directly present in `src/approvals/approvalPolicyEngine.ts`; this is not an invented OWNER-only policy or a second YAML evaluator.

`inputs` validates the profile and hash syntax. `authorization` separately requires the actual auditor-signed policy bytes and record policy digest to equal that external hash, and every signed request to match the fixed count, distinctness, role set and TTL. It still independently verifies actual execute decisions, distinct IDs, raw signatures, request binding, identity, policy digests, expiry and consumption execution ID. A CONSUMED status cannot replace the vote recount. The genuinely weaker-policy negative may therefore retain valid inputs, ledger/action/provider integrity and actual completed effect while specifically failing authorization. Its default expected hash must be captured before the public-API required-one override; the actual signed weaker policy and its rule/hash remain honestly separate.

The TTL check is exactly `expiresTs - createdTs === 600000`. No grace was added. `createApprovalRequestRecord` currently calls Date.now separately for those two fields, so a future measured clock-call drift remains a strict failure to preserve and explain. The parent checked an already retained real default request with exactly 600000 ms; this is not a new runtime claim by this proposal.

The second correction requires `bodyFields` to contain unique strings and exactly equal the normalized payment body's keys, including cardinality. A duplicate allowed field name can no longer pass the minimal-payload check.

The third correction makes the supported expected contract explicit: exactly `decision`, `terminalReceiptState`, `posts` and `commits`. Counts contain only `exact` and a nonnegative safe integer. The first two fields must be equal and one of completed, denied, cancelled or outcome_unknown. Additional dimensions, obsolete conflated digest strings, extra count predicates and contradictory outcomes fail at input validation. The oracle still returns its full 16-check schema with an explicit failed input diagnostic and unavailable checks false; it does not launch a cold verifier after an unsupported expectation. The negative test must not claim that the later provider/action checks ran on that refusal path. A genuine retained positive with an added unsupported expectation is still a meaningful oracle regression: ignoring the unknown field would incorrectly accept that valid positive.

The preserved lifecycle, wire and cryptographic boundaries remain unchanged: inherited outer PGID, natural nested closure and PID-only probes, unchanged actual DB/WAL/key snapshot around the pinned cold ledger CLI, independent action/intent/member and auditor-authority/mapping checks, no AMC imports or writable recovery, and no driver success or provenance Boolean as authority. Full normative F01 equality, installed action-CLI criterion, cancellation, compliance, runner and F01–F38 claims remain open.

`v1-to-v2.patch` is the exact text delta. Both source files remain below 800 lines. All writes and reads for this correction are finished; root alone reviews, applies and runs any future candidate.
