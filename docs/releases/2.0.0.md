# AMC 2.0.0

<!-- P0-34. The two release-notes blocks are generated from .changeset/*.md: run `npm run release:notes` (release:prepare runs it before `changeset version` consumes the changesets). Edit everything else by hand. -->

## Summary

2.0.0 is the first release since 1.1.1 (npm, 15 July 2026). It is a major release because it carries AMC's truth reset: results AMC cannot back with evidence now read "not evaluated" instead of a score, a pass or a partial; every score, level, verdict and compliance result carries a claim kind (`synthetic_example`, `self_reported`, `observed` or `independently_reviewed`) and status dimensions; verifiers refuse issuer keys the operator has not pinned; trust tiers come from who produced the evidence, never from a flag; and the native shell is refused outside Linux unless the operator opts in. AMC output is evidence of conformity, not a certification.

Version 1.2.0 was prepared in this repository but never published. Its changes are part of 2.0.0, and CHANGELOG.md lists them under 2.0.0.

## Security

2.0.0 fixes security issues that affect 1.1.1. A GitHub security advisory for 1.1.1 accompanies this release. Its link is added here when it is published (P0-39); until then these notes give no detail. Upgrade to 2.0.0. Do not run `amc verify --repair` on 1.0.0, 1.1.0 or 1.1.1: their `--repair` deletes evidence.

## Migration from 1.1.1

Each item names the changesets it covers.

### Before you upgrade

- With the 1.1.1 CLI, before any 2.0.0 command touches the workspace, take a signed backup (`AMC_BACKUP_PASSPHRASE=<passphrase> amc backup create --out <file>`; 1.1.1 refuses without `AMC_BACKUP_PASSPHRASE` or `AMC_BACKUP_PASSPHRASE_FILE`) and record `amc verify all --json` (1.1.1 has no `amc verify --json`). Once 2.0.0 has unlocked the vault, 1.1.1 can no longer unlock it to take that backup. 2.0.0 applies ledger migrations 10 to 16 when it opens a 1.1.1 workspace ledger: bridge request usage, guard events, the action journal, the A4 Forge tables (empty without the preview, see "Hidden and excluded surfaces"), the evidence-store encryption rule, agent lifecycle state and incident clock runs. These notes describe no downgrade path back to 1.1.1. (`action-journal-receipt-states`, `p2-09a-ledger-encryption`, `p2-23-agent-lifecycle`, `p2-26a-incident-clocks`)
- Record the monitor key fingerprint outside the workspace: `shasum -a 256 .amc/keys/monitor_ed25519.pub` (or `sha256sum`). After the upgrade `amc verify`, `verify all`, `session verify` and `verify --relabel-legacy` fail an unanchored ledger, so pass that fingerprint as `--expect-monitor <sha256>` or `AMC_EXPECTED_MONITOR_FINGERPRINT` (see "Verification and trust"). (`pinned-issuer-verifiers`)
- Do not run `amc verify --repair` on 1.1.1. In 2.0.0 it only prints a recovery plan; `--apply` moves a failing store to `.amc/quarantine/` with a signed receipt and never deletes evidence. (`verify-repair-no-delete`)

### Vault and signing keys

- Set `AMC_VAULT_PASSPHRASE` (and `AMC_HOST_VAULT_PASSPHRASE` for the host vault) yourself. `NODE_ENV=test` and `VITEST` no longer select a passphrase written in AMC's source. A vault created with those variables and no passphrase used a public passphrase: re-create it and re-sign what it signed. (`vault-no-test-passphrase`)
- A failed unlock now locks the vault, including a vault another process or command had unlocked: a wrong `AMC_VAULT_PASSPHRASE` in the environment stops every key use until the right one is set. Unlock also refuses when a public key in `.amc/keys/` does not match the vault; docs/VAULT.md, "When unlock refuses", gives the recovery. (`vault-unlock-fails-closed`)
- Emergency overrides need a verifiable auditor signature under the `AMC_BREAK_GLASS_OVERRIDE_V1` domain tag. Overrides recorded by 1.x read as invalid; re-issue any that are still needed with a signing key. (`signed-break-glass`)
- On the first unlock a 1.x vault becomes a version 2 vault with the same key bytes, and AMC 1.x cannot read it afterwards: keep the backup from "Before you upgrade". Keep `<AMC home>/state` on persistent storage, as the compose files and Helm chart 0.3.0 (`amcHomeState`) do, so anti-rollback marks survive a restart. Lease revocations move to `revocations.signed.json` on the first write, after which a 1.x binary refuses every lease. API callers: `createAgentClaim` needs `opts.audience`, `ClaimExpectation.issuerKeyIds` is required, 1.x agent claims no longer verify, and `leaseRevocationPaths` and `signLeaseRevocations` return new shapes. docs/KEY_LIFECYCLE.md lists every refusal and its recovery. (`key-lifecycle-p1-08`)

- `amc doctor` fails `key-history-monitor`, `key-history-auditor`, `key-history-lease` and `key-history-session` on a 1.1.1 workspace ("legacy history has no admission signature"): 1.x key history files are unsigned arrays, which no longer authorize any historical key. For each role, review `.amc/keys/<role>_history.json`, then run `amc vault history migrate --role <role> --expected-sha256 <sha256 of that file>`, adding `--approve-fingerprint <fingerprint>` only for historical keys you confirmed from trusted records. The original is kept as `<role>_history.json.untrusted-<sha256>`. docs/KEY_HISTORY.md, "Existing workspaces", describes it. (`key-lifecycle-p1-08`)

- Key providers remain opt-in, with canonical default vault signature bytes preserved. Inventory historical signature encodings and independent trust pins before upgrading: DER/high-S P-256 and unreduced Ed25519 signatures previously accepted by permissive verification now refuse; preserve original evidence rather than silently normalizing or re-signing it. Generic binding supports ledger-row/session; config-signature uses `amc keys rotate --purpose config-signature --config-candidate <file>`. Removing an editable ref never releases a committed binding. Ledger delegates need a current scoped delegation, renewed at least daily, within shared usage quota; renewal advances the key-set generation. Direct private-key APIs refuse provider-held signing except the explicitly authorized ledger delegate. Scripts parsing `amc keys list` must account for provider/algorithm/protection/basis fields. New notary responses carry protection basis; historical absent basis remains absent to preserve signed bytes. Typed failures and no fallback remain enforced. Plugin publication refuses no-sign mode even with an unlocked vault, and NOTARY plugin records require the current authenticated policy pin. Changing or removing that pin can refuse historical records; preserve the applicable policy and trust evidence. Other purpose/caller migrations, held owner handoffs, live cloud/HSM and hosted CI qualification remain pending; see docs/KEY_PROVIDERS.md for the precise surface. (`key-providers-p2-08`)

### Verification and trust

- `amc verify all` and `amc evidence verify` report an optional part the workspace never set up (passport, A4 projects, prompt packs and the prompt scheduler, audit binder and bench exports, the schema bundle, the forecast scheduler, backups, release bundles) with the new check status `NOT_CONFIGURED` and name it in the new JSON `notConfigured` list; it neither passes nor withholds the headline. JSON consumers that match check statuses against `PASS`, `FAIL` and `SKIP` must accept this fourth value. Absent files alone no longer prove a part was never set up, because a file and its signature can both be deleted. 2.0.0 writes a `PASSPORT_POLICY_CONFIGURED`, `PROMPT_SCHEDULER_CONFIGURED` or `FORECAST_SCHEDULER_CONFIGURED` witness the first time the passport policy (saved, applied, or created by `amc passport init` or the API and Studio init) or the prompt or forecast scheduler state is saved: an audit row in the evidence ledger, then an entry in the transparency log; an applied passport policy also logs `PASSPORT_POLICY_APPLIED`, and each prompt pack build logs `PROMPT_PACK_CREATED` and writes a ledger row of that type for its agent when the ledger lacks one. Each record is written whenever it lacks the witness, so restoring either one alone to an older copy is repaired by the next save. Such a part reads `NOT_CONFIGURED` only when the verified, anchored ledger and the verified log both hold no witness of it and both hold the `WITNESSING_ENABLED` marker that a new workspace records in both at creation, before anything can be configured, where creation writes it (the ledger's first row, and a log entry preceded only by the creation-time `KEY_HISTORY_REVISION` entries; a marker anywhere else counts as absent); a ledger that holds the marker while the log does not (or the reverse) fails `transparency-log`. A default passport policy created on demand by a passport read is not witnessed, since it is only the default and any later read recreates it; an explicit init witnesses it. When either record holds a witness and the files are gone, the check fails (critical for the passport policy), and when the ledger holds a witness the transparency log lacks, `transparency-log` fails: the log was restored to an older copy. Restoring the ledger and the log together to a copy taken before the configuration, or deleting both and running `amc init` again, cannot be told apart from a workspace that never configured the part; only an anchor outside the workspace (the public transparency anchor, or the verifier's high-water marks) detects that. An A4 project is witnessed by its hash-chained ledger audit rows, so "no A4 project" holds only when the ledger hash chain verifies. A missing transparency log or seal is no longer recreated or re-signed by `verify all`: `transparency-merkle` and any witnessed part without its files are skipped, and `transparency-log` fails when the ledger holds a witness or the marker the log should hold (every 2.0.0 workspace), else is skipped, so the headline reads `FAIL` or `INCOMPLETE` (exit 1). Restore the log from a backup rather than deleting it. A workspace created before 2.0.0 (1.1.1, or a 2.0 pre-release) has no `WITNESSING_ENABLED` marker, and none is backfilled, since a marker written after the fact would vouch for files that may already be deleted (init writes it only when no ledger exists and the transparency log is absent or holds only the creation-time `KEY_HISTORY_REVISION` entries, as after an init interrupted before the ledger, so re-running init after deleting the ledger writes none): there a part without a witness reads `SKIP` instead of `NOT_CONFIGURED`, so `verify all` reads `INCOMPLETE` (the critical passport policy) until each part's first explicit witnessed save records its witnesses: `amc passport init` for the passport policy, `amc prompt scheduler init` or `enable`, `amc forecast scheduler enable` or `run-now`, and `amc prompt pack build` for the non-critical parts. A4 projects are the exception: A4 Forge is new in 2.0 and preview-only, and every 2.0.0 project create writes the `A4_PROJECT_CREATED` pair, so with no project and no A4 witness in either verified record `a4-projects` reads `NOT_CONFIGURED` with or without the marker, and such a workspace reads `PASS` after `amc passport init` without enabling the A4 preview. After that save, deleting the part's files fails. Exported audit binders and bench artifacts read `NOT_CONFIGURED` when none are on disk, without a witness: they are outputs meant to leave the workspace, and their transparency entries remain. `INCOMPLETE` (exit 1) and `skippedCritical` mean a critical check was not performed, such as the ledger trust root under `--allow-unanchored`. A fresh 2.0.0 workspace reads `PASS` and lists its unconfigured parts in `notConfigured`. (`verify-all-not-configured`)
- Pin the issuers you trust. `amc verify`, `bundle verify`, `cert verify`, `passport verify`, `release verify`, `audit binder verify`, `backup verify`, `plugin verify`, `federate verify-bundle` and the other portable verifiers take `--pubkey`, `--trust-list`, `--trust-root` or `--expect-monitor` (or `AMC_EXPECTED_MONITOR_FINGERPRINT`). A key inside an artifact never vouches for it. `--allow-unpinned` and `--allow-unanchored` give an integrity-only result with exit code 2 and `UNTRUSTED:` on stderr, so CI scripts must treat 2 as not trusted. Workflows written by `amc ci init` read the pins from the repository variables `AMC_AUDITOR_PUBKEY` and `AMC_MONITOR_FINGERPRINT`. (`pinned-issuer-verifiers`, `pinned-issuer-verifiers-pr3`, `pinned-issuer-remaining-verifiers`)
- API verify routes no longer report unsigned artifacts or shared-secret tokens as valid: trust-token and agent-claim verification answer `not_evaluated`, and a body carrying `secret`, `sharedSecret`, a pin or an allow flag is refused with 400. Creating an agent claim needs a body `sharedSecret` or the server's `AMC_TRUST_SECRET`; the well-known default secret is gone. (`api-unsigned-verdicts`, `g0-security-followups`)
- A verify command whose verdict is not passed prints `Evidence: untrusted`, and a claim line says `Evidence: sufficient` only for verified evidence or a D-03 self-reported pass with evidence attached. Parsers of claim lines and `statusDimensions.evidence` see these values change. (`verify-claim-untrusted`, `claim-evidence-verified-only`)
- `amc eval import --trust-tier` and `amc value ingest --attested` are removed (exit 2); imported eval and value events are `SELF_REPORTED`. `amc attest` records `ATTESTED` only with `--attester-signature` from a third-party key pinned for `independent-attestation` in a signed trust list. Stale `OBSERVED` events older than 90 days count as `SELF_REPORTED`. (`trust-tiers-from-provenance`, `value-trust-and-stale-evidence`)
- Issuer admission judges revocation, the key's validity window and distrust at the verification time, not at the signing time an artifact claims. An artifact signed by a key that has since been revoked (for any reason), has passed its `validTo` or is distrusted no longer verifies. Before you rotate a key, publish signed key history (an anchor with `allowKeyHistory: true`) or keep the old key admitted in your trust list, so artifacts it signed still verify. (`issuer-admission-at-verification-time`)

Levels are cumulative and earned only from runtime evidence that a registered emitter wrote (methodology `2026.10.08-r226`); no question can score above L2 in this release, self-reported evidence caps at L1, and `STRICT_EVIDENCE_BINDING=false` no longer has an effect. Pack audits gain `currency` and `contentStatus` and the schema id `amc.industry-pack-audit/5`; readers that pin `/4` must accept `/5`, and older receipts still verify their checksum. - An unanswered industry-pack question is not evaluated instead of level 1: pack results and pack audits list it in `notEvaluatedQuestionIds`, give it no question result, gap or level, and report `percentage`, `level` and `eligibleLevel` as `null` until every question is answered. `amc domain pack run --baseline` therefore computes no score. Read these fields as nullable. (`pack-unanswered-not-evaluated`)
- Assurance runs mark refused, canned and tool-call-only replies inconclusive, the 17 industry packs fail closed on empty or canned replies, and keyword-graded pack results no longer satisfy a compliance requirement. (`assurance-grading-inconclusive`, `slice-b-fail-closed-packs`)

Scripts that parse CLI text must skip the new line; `AMC_CLAIM_LABELS_STRICT=1` makes an unlabelled result fail. (`cli-claim-labels`)
- Results stored by 1.x read "Legacy (1.x)" under notice AMC-LEGACY-2026-001 and are capped at level 1; originals are never modified. `amc verify --expect-monitor <sha256> --relabel-legacy` records the relabel in a signed, hash-chained log; without a monitor pin the integrity check fails UNANCHORED and the relabel records nothing. Add `--dry-run` first to list what it would record. (`legacy-relabel-migration`)
- `amc evidence export --agent` includes the agent's native sessions; the dataset `schemaVersion` is 2 and `agentFilter` is an object. Exports refuse rows that violate the published evidence-event contract, and the published JSON Schemas are regenerated from the schemas AMC enforces, so their digests change. (`o20-runtime-findings`, `public-contracts-generated-schemas`)

### Runtime, gateway and actions

- The gateway proxy resolves every destination and refuses non-public addresses. List the IP literal of an internal host next to its name in `proxy.allowlistHosts`; give upstreams on non-public addresses `allowLocalhost: true`, an IP-literal `baseUrl` or `allowNonPublicAddresses`, then sign `gateway.yaml` again. (`gateway-proxy-resolve-and-check`)
- Tool calls outside `READ_ONLY` and `WRITE_LOW` are bound to an authorization record and rechecked before they run. `FINANCIAL` tools must declare `bindingFields` for `amount`, `currency` and `recipient` in `.amc/tools.yaml`, and `DATA_EXPORT` tools for `destination`; an answerer's `allow` no longer approves these classes. (`authorization-record-recheck`)
- A 1.1.1 `budgets.yaml` from `amc budgets init` sets `daily.maxCostUsd: 50`. A hard USD budget now admits a native model request only under a signed, auditor-attested request bound, so every `amc agent-loop run` turn, the keyless `--provider stub` turn included, refuses `AMC_NATIVE_BUDGET_REFUSED` before dispatch. Either set `daily.maxCostUsd: null` for a token and count budget (the 2.0.0 default) or add reviewed `nativeUsdBounds` records, then run `amc budgets sign`, which signs the edited file without changing its limits. docs/BUDGETS.md, "Native USD Request Bounds", gives the record format. (`wp28b-budget-reservations`)
- Consequential calls are journaled. An `outcome_unknown` call blocks the agent's later consequential calls until it is reconciled or settled with `amc action resolve`; the journal refuses `AMC_LEDGER_SQLITE_SYNCHRONOUS=OFF` or `NORMAL` and `AMC_NO_SIGN=1`. (`action-journal-receipt-states`)
- Native sessions are fenced by a signed writer epoch and lease. AMC 1.x cannot resume a session that 2.0.0 has appended to, and a 1.x session gets one signed `session/migration` row on its first 2.0.0 claim. A writer replaced by a newer claim is refused `STALE_EPOCH` (was `STALE_HEAD`) and dispatches nothing. A remote or unresponsive writer is claimed only with `amc agent-loop run --session <id> --takeover-expired-writer "<reason>"` once its lease has been expired for one more lease. Resume refuses a session journal older than this machine's mark (`ROLLBACK_DETECTED`) or forked from it (`FORK_DETECTED`), so keep `<AMC home>/state` on persistent storage. Interrupted calls get a signed `tool/reconciled` row before the resumed turn; `amc agent-loop run` composes no reconcile adapters, so an interrupted consequential call stays blocking until `amc action resolve`. (`session-writer-fencing`)
- Under `AMC_NO_SIGN=1`, diagnostics and monitored processes write to `.amc/unsigned/evidence.sqlite` and read as `UNSIGNED`. (`g0-security-followups`)
- A lease no longer counts as a principal. Under a plan whose identity binding requires one (L0-IDN-01), mint leases that name an active `users.yaml` user (`issueLeaseForPrincipal`); leases from 1.x or `amc lease issue` name nobody, and their calls refuse `PRINCIPAL_UNRESOLVED`. A lease for another workspace is refused. Direct `agentToolset` callers must open the ledger session before the toolset records into it, or calls refuse `UNVERIFIABLE_TOOL_EVIDENCE`. Where a class requires distinct users, the initiator can no longer approve their own request. Authorization records read `deploymentId: "not_bound"` (was `unregistered`) until you recompile and reactivate the plan to bind the deployment. (`layer0-enforcement-gaps`)
