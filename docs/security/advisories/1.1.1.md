## Advisory text

**Title:** Canned, forgeable or readable evidence in agent-maturity-compass 1.1.1 and earlier

**Package** npm `agent-maturity-compass` · **Affected** `<= 1.1.1` (npm 1.1.1; GitHub releases v1.0.0, v1.1.0 and v1.1.1 with their desktop archives; images and the Homebrew formula built from those tags) · **Patched** `2.0.0`

**Summary.** agent-maturity-compass (AMC) 1.1.1 and earlier can produce results that look like evidence but are not. Assurance and red-team runs graded a built-in canned reply instead of the agent under test and stored it as observed evidence. Several verifiers accepted signatures from keys supplied inside the artifact being verified. Evidence written without a vault was encrypted with a key published in the source. Private signing keys of workspaces committed to the repository sat, passphrase-encrypted, in public Git history from February to September 2026. Imported evidence received a high trust tier by default, and operators could raise it. `amc domain` commands returned pseudo-random scores. Version 2.0.0 fixes these issues. Upgrade, then re-run any assessment you relied on.

**1. Assurance and red-team runs graded a canned reply.** `amc assurance run` did not call the agent. `syntheticResponse()` (`src/assurance/assuranceRunner.ts:133` in v1.1.1) built an ideal refusal from prompt keywords, line 315 graded it, and the ledger recorded it with trust tier `OBSERVED` (line 266; `OBSERVED_HARDENED` in sandbox mode). Every pack reported no vulnerabilities, signed and stored as observed. The red-team runner (`src/redteam/runner.ts:206,502` in v1.1.1) and the jailbreak TAP engine (`src/redteam/jailbreak/tap.ts:192,324` in v1.1.1) used the same pattern. *Affected:* anyone who relied on assurance, red-team or jailbreak results from these versions, or on certificates built from them. *Fixed by:* `fba5824e` (assurance runs the real agent and fails closed without a reachable target; test `tests/assuranceAgentResponder.test.ts` "assuranceRunner no longer contains a synthetic response path"), `c0ebbf69`, `15dc87e2` and `8f9fa7ac` (red-team runner, evil-MCP red team and TAP require a real responder; `tests/redteamRealExecution.test.ts` "never reports a perfect score when nothing was attacked"), and P0-19 merges `3aa75a11` and `da093617` (one grading rule; an ungradable reply is inconclusive, never a pass). *Workaround:* none; treat these results as not evaluated. *Suggested severity:* High (integrity). *CWE:* TBD (Sid); CWE-345 is a candidate.

**2. Hard-coded fallback key for evidence blobs.** Blobs written without an unlocked vault were encrypted with the constant `amc-no-sign-fallback-key-32bytes!` (`src/storage/blobs/blobKeys.ts:131,168` in v1.1.1). No-sign mode also switched on automatically when an existing vault was locked and no passphrase was available (`src/cli.ts:1408-1414,1735-1736` in v1.1.1). `exportEvidenceBundle` copies `.amc/blobs/*` into `.amcbundle` files (`src/bundles/bundle.ts:335` in v1.1.1), so anyone holding such a bundle could decrypt those payloads. *Affected:* workspaces that ran without an unlocked vault, and recipients of their bundles. *Fixed by:* `3a7c4752` (random per-workspace key, mode 0600; the old constant is kept read-only for old blobs; `tests/storage/blobKeyNoVault.test.ts` "never uses the published constant for a new workspace"). *Workaround:* always set `AMC_VAULT_PASSPHRASE`, check that JSON output says `signed: true`, and treat payloads from no-sign workspaces as disclosed. *Suggested severity:* High where payloads hold personal or confidential data, otherwise Moderate. *CWE:* CWE-321.

**3. Verifiers trusted keys shipped inside the artifact.** `amc cert verify` read the verification keys from the certificate (`src/assurance/certificate.ts:463` in v1.1.1); `amc bundle verify` read the auditor key from the bundle (`src/bundles/bundle.ts:571` in v1.1.1); `amc passport verify` and `amc assurance cert-verify` used `signer.pub` from the artifact unless a key path was given (`src/passport/passportVerifier.ts:103,138` and `src/assurance/assuranceVerifier.ts:100` in v1.1.1); `amc release verify` without `--pubkey` used the bundle's own `keys/release-signing.pub` (`src/release/releaseVerifier.ts:62` in v1.1.1). `amc verify` reported PASSED for a ledger re-signed after replacing `.amc/keys/monitor_ed25519.pub` (demonstrated in `521f21e7`). Anyone could create a certificate, bundle, passport, release bundle or ledger that verified as valid. *Affected:* anyone who accepted an AMC artifact from another party on the strength of these commands. *Fixed by:* P0-09 merges `0e681948` (#45, trust lists, issuer admission, built-in distrust list), `0b818f4f` (#53, verifiers admit only pinned issuers, `amc release verify` included; unanchored ledgers fail by default) and `6b899a60` (#55, remaining verify surfaces), plus `521f21e7`; tests `tests/trust/embeddedKeyForgery.test.ts` "a forged copy re-signed with an embedded key fails as not-pinned by default" and `tests/ledgerTrustRootAnchorCli.test.ts` "fails the workspace-write forgery as UNANCHORED by default". `docs/security/verifier-inventory.md` lists every verify command and its wiring. *Workaround:* pass `--pubkey` with a key obtained out of band where the command accepts it (in 1.1.1: `passport verify`, `release verify`, `backup verify` and others; see `--help`); otherwise compare the embedded key's fingerprint with an independently obtained one, or treat the artifact as unverified. *Suggested severity:* High to Critical. *CWE:* CWE-347.

**4. Signing keys of the example workspace in public Git history.** `.amc/vault.amcvault`, a passphrase-encrypted vault whose payload holds four Ed25519 private keys (monitor, auditor, lease, session; `src/vault/vault.ts:8,13-16` in v1.1.1) of the repository's own example workspace, was tracked from 17 Feb 2026 (`40358680`) to 21 Aug 2026 (`cb6bba21`), including at tags v1.0.0, v1.1.0 and v1.1.1. The keys are exposed to offline passphrase guessing. A second vault, `--/.amc/vault.amcvault`, was tracked from 22 Aug (`521f21e7`) to 14 Sep 2026 (`7cfcb767`). History was not rewritten. Separately, 1.1.1 sealed new workspace vaults with the passphrase `amc-test-passphrase`, published in the source, whenever `NODE_ENV=test`, `VITEST=true` or `VITEST=1` was set and `AMC_VAULT_PASSPHRASE` was not (`src/vault/vault.ts:109-110` in v1.1.1), and new host vaults with `amc-host-vault-test-passphrase` under the same variables (`src/identity/hostVault.ts:72-73` in v1.1.1). `cb7893e1` limited this to Vitest; `8ca67399` removed it (`tests/vaultPassphraseSource.test.ts`). *Affected:* anyone who trusted artifacts signed by these keys, used the repository's `.amc/` directory as their own workspace, or created a vault or host vault with one of those variables set and no passphrase. *Fixed by:* TBD (P0-37): the distrust list entries for the exposed keys, their fingerprints, the rotation date and the list's location. The built-in distrust list on this base is empty (`src/trust/amc-distrust.json`). *Workaround:* re-create affected workspaces and re-sign what they produced; distrust the listed fingerprints once P0-37 publishes them. *Suggested severity:* High. *CWE:* TBD (Sid); CWE-538 is a candidate.

**5. Imported evidence was trusted by default.** `amc eval import` assigned `ATTESTED` to all seven formats (`src/eval/evalImporters.ts:78-84` in v1.1.1), accepted `--trust-tier OBSERVED` (`src/cli.ts:6919` in v1.1.1) and stored each case at the timestamp the file claimed (`src/eval/evalImporters.ts:1600` in v1.1.1), and `amc attest` (`src/cli.ts:15155` in v1.1.1) signed with the operator's own auditor key. Operators could raise maturity results with self-asserted data. *Fixed by:* P0-18 merges `2a5d6325` (#70, tiers from provenance; `ATTESTED` only with a pinned third-party key) and `8206fe46` (follow-ups); tests `tests/evalImportTrust.test.ts` "amc eval import --trust-tier OBSERVED exits 2 with the removal message and writes nothing" and `tests/trustTierWriteGuard.test.ts` "ATTESTED with the workspace's own monitor or auditor key is refused". *Workaround:* treat imported evidence as self-reported. *Suggested severity:* Moderate to High (integrity).

**6. `amc domain` returned invented scores.** `amc domain assess`, `gaps`, `report` and `roadmap` used `pseudoRandomScore` (`src/domains/domainCliIntegration.ts:58-77` in v1.1.1) seeded by agent, domain and question ids, and reports printed a `Certification Readiness` line (`src/domains/domainReportBuilder.ts:65` in v1.1.1). *Fixed by:* P0-15 merge `f4646429` (#67, "not evaluated" without evidence; a labelled `--example` mode that cannot be attested); tests `tests/noFabricatedDomainResults.test.ts` "the agent id no longer decides the output" and `tests/domainExampleMode.test.ts`. *Workaround:* do not use these outputs. *Suggested severity:* Moderate to High (integrity).

**Remediation.** Upgrade with `npm install -g agent-maturity-compass@2.0.0` or the updated release archive; re-run assessments; re-verify artifacts with pinned keys (`docs/releases/2.0.0.md`, `docs/TRUST_LIST.md`); distrust the keys listed for issue 4 once that list is published.

**Other hardening in 2.0.0** (not separate vulnerabilities): key-history files were written 0644 and any listed key was accepted (`cb6bba21`); notary keys were admitted before their config was saved (`cb7893e1`); seventeen commands that read outside archives ran `tar -xzf` without AMC's own path, size and entry checks (`cb6bba21`, `tests/tarTraversalGuard.test.ts`). With macOS bsdtar 3.5.3 those extractions stayed inside their output directory for `..`, absolute, symlink and hard-link members; GNU tar and Alpine's tar are not yet checked (see "Notes for Sid").
