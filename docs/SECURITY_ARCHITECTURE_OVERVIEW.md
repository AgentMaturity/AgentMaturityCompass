# AMC Security Architecture Overview

*How AMC makes AI agent trust scores tamper-resistant and verifiable.*

---

## Design Philosophy: Behavioral Over Documentary

Every AI governance framework today shares a fundamental weakness: the agent being evaluated provides its own evidence. An agent can claim it logs every decision, handles errors gracefully, and respects data boundaries — and score perfectly — without any of it being true.

AMC was built on a different premise: **trust must be earned through observed behavior, not documentation.**

The Execution-Proof Evidence System (EPES) is AMC's answer to documentation inflation. Rather than asking "did you implement logging?" and accepting a config file as proof, EPES observes whether the agent actually logs during execution, verifies the logs are structurally sound, and weights the resulting score based on how that evidence was collected.

This is the difference between a self-reported credit score and one built from transaction history.

## The Four Trust Tiers

EPES classifies every piece of evidence into one of four tiers, each carrying a different weight in the final maturity score:

| Tier | Description | Trust Weight |
|------|-------------|-------------|
| **Observed Hardened** | Evidence collected by AMC-controlled instrumentation in a hardened environment the agent cannot tamper with. | Highest |
| **Observed** | Evidence directly observed by AMC's gateway proxy during live agent execution. | High |
| **Attested** | Evidence cryptographically signed by a trusted third party (vault, notary service, external auditor). | Moderate |
| **Self-Reported** | Claims made by the agent itself, with no independent verification. | Lowest (capped) |

The tier system means an agent cannot achieve a high maturity score through self-reported claims alone. The ceiling on self-reported evidence is deliberate — it forces agents (and their operators) to submit to independent observation if they want meaningful scores.

## Cryptographic Foundation

AMC's evidence chain is built on two cryptographic primitives:

### Digital Signatures (Ed25519)

Every evidence artifact — a log entry, a test result, an observation record — is digitally signed using Ed25519 elliptic curve signatures. This provides:

- **Authenticity**: proof that the evidence came from a specific, identified source
- **Integrity**: any modification to the evidence after signing invalidates the signature
- **Non-repudiation**: the signer cannot later deny having produced the evidence

Ed25519 was chosen for its speed, small key/signature size, and resistance to timing side-channel attacks — properties that matter when signing thousands of evidence artifacts during a scoring run.

### Transparency Logs (Merkle Trees)

Individual signed artifacts are organized into Merkle tree structures — append-only transparency logs where:

- Each entry is cryptographically linked to all previous entries
- Any tampering with historical records breaks the chain and is immediately detectable
- Third parties can independently verify the integrity of the entire log without trusting AMC
- Inclusion proofs allow verification of specific evidence without downloading the full log

Together, these primitives create an evidence chain where every score can be traced back to specific, signed, tamper-evident observations.

## Anti-Gaming: Closing the 84-Point Gap

In testing, AMC demonstrated an 84-point gap between keyword-based scoring (which gave a test agent 100/100) and execution-verified scoring (which revealed the true score of 16/100). This gap represents the documentation inflation that EPES is designed to eliminate.

EPES resists gaming through several reinforcing mechanisms:

- **Tiered evidence weighting** — Self-reported claims are mathematically capped. No amount of documentation can substitute for observed behavior.
- **Execution observation** — AMC's gateway proxy watches what agents actually do, not what they say they do. The agent doesn't control the observation pipeline.
- **Cryptographic binding** — Evidence is signed at the point of collection. Retroactive fabrication requires compromising the signing key, which is held in the vault — not by the agent.
- **Temporal verification** — Evidence carries timestamps that are cross-referenced against observation windows. Claims outside observed execution periods are flagged.
- **Structural analysis** — AMC doesn't just check if evidence exists; it analyzes whether the evidence is structurally consistent with genuine behavior (e.g., log entries that follow realistic timing patterns vs. bulk-generated artifacts).

The design principle: **make honest behavior the path of least resistance, and dishonest behavior cryptographically expensive.**

## Key Management

AMC's trust model depends on the integrity of its signing keys. The key management approach follows defense-in-depth:

- **Vault-based storage** — Signing keys are managed through AMC Vault, which supports software-based key storage for development and HSM/TPM-backed storage for production deployments.
- **Key rotation** — Keys have defined lifetimes. Rotation is automated, with overlap periods to ensure continuity of evidence chains during transitions.
- **Compromise recovery** — If a key is compromised, AMC's revocation mechanism invalidates the key and flags all evidence signed during the suspected compromise window for re-evaluation. The Merkle tree structure means historical evidence signed by uncompromised keys remains valid.
- **Separation of concerns** — Different keys serve different purposes (observation signing, attestation, vault sealing). Compromise of one key type does not automatically compromise others.

## Trust Boundary Model

AMC defines clear trust boundaries between components:

- **Agent boundary** — The agent under evaluation is untrusted by default. All agent-provided evidence enters at the Self-Reported tier.
- **Gateway boundary** — AMC's gateway proxy sits between the agent and external services, observing behavior. Evidence from the gateway enters at the Observed tier.
- **Vault boundary** — The cryptographic vault is the root of trust. It holds signing keys and produces attestations. Only authenticated, authorized components can request signatures.
- **Notary boundary** — External attestation services (third-party auditors, HSM-backed notaries) provide independent verification. Their evidence enters at the Attested tier.
- **Hardened boundary** — AMC-controlled instrumentation in isolated environments produces the highest-trust evidence. The agent has no access to modify the observation infrastructure.

Each boundary crossing requires authentication and produces a signed record. No component implicitly trusts another.

## Evidence Decay: Why Freshness Matters

Trust is not permanent. An agent that demonstrated robust error handling six months ago may have been updated, retrained, or modified since then. AMC's maturity function includes a formal evidence decay model:

- **Recent evidence carries more weight** than older evidence in score calculations.
- **Decay rates vary by dimension** — security-critical behaviors decay faster than operational ones, reflecting the reality that security posture can change rapidly.
- **Continuous assessment is incentivized** — because scores naturally decay over time, operators are motivated to run regular assessments rather than relying on a single point-in-time evaluation.
- **Stale scores are visibly flagged** — consumers of AMC scores can see when a score is based on aging evidence, enabling informed trust decisions.

Evidence decay ensures that AMC scores reflect current agent behavior, not historical snapshots. It transforms trust scoring from a one-time certification into an ongoing relationship.

## Residency routing and storage admission (P2-01, partial source)

`src/residency/checkEgress.ts` checks outbound routes and session storage against the operator-signed destination registry and the profile pinned by the active compiled plan. Both checks are opt-in: they apply only to a workspace with an active compiled plan or a destination registry. A workspace with neither returns `no_rule`, which is not a residency assessment. A present but invalid registry, an active plan that does not verify, or an unregistered or disallowed destination refuses with a typed `EgressBlocked` decision.

The control checkpoint root must sit outside the workspace. When the workspace contains it, as when the workspace is the home directory, nothing outside the workspace anchors the control journal, so a missing plan cannot be told apart from a deleted one. Every read of the compiled plan, and with it storage admission, every egress check and native sessions, therefore refuses as `control_checkpoint_root_in_workspace` (fail closed), and the message names `AMC_CONTROL_CHECKPOINT_DIR` without any host path. This configuration error is never reported as an unverifiable plan. With the root outside the workspace, residency checks are opt-in: a workspace with no destination registry and no active plan is not checked. Route decisions record operator declarations; they are not legal approval or proof of physical location. See [OPS_HARDENING.md](https://github.com/AgentMaturity/AgentMaturityCompass/blob/main/docs/OPS_HARDENING.md#residency-routing-p2-01-source-slice).

## Protected native model requests (P2-02, partial source)

Admission is opt-in per workspace. It runs only when the processor registry `.amc/dataflow/processors.yaml` or its detached `.sig` exists; a workspace with neither file keeps the existing flow and is not scanned. In an opted-in workspace, the native `LlmRuntime.prepare` boundary reuses the existing committed request assembly and capability assertion. Experimental detectors reuse the DLP patterns and their Luhn/IBAN checks, then identify candidate `phi`, `pii`, `card_number`, `bank_account` and `credential` classes in supported request text. The detector does not count clock times (`HH:MM[:SS]`) that the IPv6 pattern matches, except right after `::` where they are the tail of a compressed IPv6 address, or bare 10-digit runs not preceded by `+` that the phone pattern matches, so a phone number written as a bare 10-digit run (including a JSON number) is not detected; E.164 (`+14155552671`) and 11-digit (`14155552671`) forms are detected. Nor does it count a phone-shaped number whose area code starts with 0 or 1, which no North American number has (DOI suffixes such as `10.1673/031.010.6301` do). Nor does it count a bare 13-digit run starting with 1 as a card number: such runs are Unix-millisecond timestamps (2001 to 2033), about one in ten of them Luhn-valid, and no card network issues a 13-digit number starting with 1. A dropped noise span is retried from its next character, so it cannot hide an overlapping match. Detected classes require a verified operator processor and purpose declaration before encoding or request-header creation. A permitted request keeps its original content, encoder and digest, preserving historical reconstruction. Supported requests without detections keep the existing flow. A detector refusal (an unsupported value shape or a limit below) refuses preparation with the typed `DataFlowRefused` reason `detector_invalid`; this is not proof that uninspected content is safe.

The scanner bounds nesting depth to 32, each text leaf to 1,048,576 characters and the characters scanned across one request to 16,777,216; exceeding a bound refuses, and nothing is skipped. The request budget is far above any provider context window. It bounds the synchronous scan time of hostile text, which is linear but measured at up to about 0.55 s per MiB. Empty or malformed tool-call arguments are scanned as text after decoding their JSON escapes. Valid arguments are also scanned as decoded raw text, because the provider receives those bytes whatever a parser keeps (a duplicate key would otherwise hide its earlier value). Each tool result is scanned as it is and again after decoding its JSON escapes, the second pass adding only classes not yet counted, so a value right after an escape such as `\n` in a JSON result (every MCP result is one) is seen; the result is not parsed, so its nesting never refuses. A number that overflows to Infinity is treated as null, and other arguments are scanned leaf by leaf, so arguments nested deeper than 32, or too deeply to parse, still refuse, and every later preparation of that session refuses again. No pattern backtracks quadratically: the email pattern bounds its lengths (RFC 5321), which also applies to `scanForPII`, and the keyword patterns use an unambiguous whitespace separator that matches the same text as before. A card or IBAN match that fails validation is retried as shorter prefixes and from the next character, which recovers cards and IBANs that a greedy match had merged with a neighbouring number or word. The scanner does not inspect image/audio bytes or binary buffers. The detector-set digest binds actual pattern metadata, the span-scan revision, class mappings, the noise filters, declared validator revisions and traversal limits; it is not an executable or binary provenance digest.

The operator-signed processor registry binds a provider and exact canonical route base URL to a processor and purpose. Every detected class needs an effective, unexpired covering contract declaration and purpose permission; the experimental PHI rule also requires a declared BAA. Purpose comes from signed operator data rather than prompt text or provider parameters. The static `model.request` permission applies to this native preparation operation and grants no ToolHub or action authorization. In an opted-in workspace, a request with detections is refused when the registry is unreadable, unsigned or malformed, or when its declarations are ambiguous or insufficient. Signatures establish who endorsed the data, not whether a contract is legally sufficient or applies to a particular deployment. The experimental backing lives at `.amc/dataflow/processors.yaml` with a detached `.sig`; source helpers `initProcessorRegistry` and `signProcessorRegistry` require owner mode and have no CLI command yet, so opting in currently needs those helpers. The loader verifies bounded non-follow byte snapshots against auditor key history. Initialization refuses existing registry/signature paths; the two-file publication is not a transaction. Concurrent owner writes, key/clock trust and registry rollback pinning remain unresolved. This separate preparation registry is not a compiler-pinned extension of the destination registry.

Detection evidence is a signed, non-surface audit row containing only classes, counts, detector-set digest and processor ID. It contains no plaintext, match spans or hashes of protected values. Failure to persist that row refuses preparation with reason `audit_failed`. The existing source cutoff and bytes remain unchanged, so the audit does not become model content or alter cold reconstruction. The system prompt, the tool-schema commitment, model output and rows written before a session was wrapped may contain raw data; redaction before commit (below) covers user input and tool results from then on and does not rewrite existing records. A detector span lying inside the 16-hex part of an AMC token (`[[amc:<class>:<hex>]]`) is the token's own hex and is not a detection, but only for a token this workspace issued: admission looks each token-shaped string up in the workspace token vault (one read-only connection per request, each answer cached). Token-shaped text the workspace did not issue is scanned as text, so a raw card number or IBAN written in token brackets is still detected. An issued token whose hex happens to be all-decimal and Luhn-valid (about 5e-5 of tokens) is therefore not counted as a card number. A span that crosses token text, such as a JSON password value that holds a token beside raw text, remains a detection when it still is one with the issued tokens removed.

This is preparation-time admission against the pinned route base URL. In an opted-in workspace it runs on every request, not only on one with detections: a registry that is missing after opt-in (the opt-in is latched per process) or does not verify refuses every request with its reason, and a request needs a BAA route when the signed run purpose allows `phi` or the request holds a PHI token this workspace issued, even when every identifier in it is tokenized, because the rest of the text may still be PHI; the `PROTECTED_DATA_DETECTED` row then carries `declaredClasses`. Purpose binding of tool calls is described below. Final envelope destinations, delayed dispatch (admission runs at prepare, and dispatch follows it at once), gateway and bridge provider traffic, and exec output remain later scope. Regex rules miss names and free-text identifiers. Counts and detector metadata establish neither complete detection nor clinical, PCI or legal approval. An owner CLI to initialize and sign the registry, opt-in through classes declared in the compiled policy, and compaction and retry handling of `DataFlowRefused` are outstanding. Named expert review and current legal applicability remain outstanding. These sources remain partial and unqualified; no product execution, tests, evaluation, CI or release qualification was performed.

## Redaction before commit (P2-02, partial source)

**Tokenization reduces the identifiers that reach model context and logs. It is not de-identification or anonymization under any standard or regulation.** The text around a token may still identify a person, a token is a stable pseudonym within its workspace, and equal tokens reveal equal values. Detection is heuristic and experimental.

**Opt-in.** Redaction uses the same opt-in as admission: it applies only in a workspace where `.amc/dataflow/processors.yaml` or its `.sig` exists, or where that cannot be checked. Opt-in through protected classes declared in the compiled policy is not built, because the compiled policy declares no such classes yet. The native session is wrapped where it is composed: `runComposedTurn` (`amc agent run` and scheduled passes), `openAgentSession` and `resumeAgentSession` (ACP, the SDK and A4 Assemble), and delegated child sessions. Every composed session is wrapped, and each record method checks the opt-in before it redacts, so a long-lived session composed before the registry existed redacts from the moment it does; until then every record method delegates unchanged. The opt-in is latched per process: once a workspace is seen opted in it stays so until the process exits, so the session, the action journal and stored evidence make the same choice, and removing the registry does not turn redaction off mid-process. `src/session/sessionService.ts` is unchanged; `createRedactingSession` wraps it.

**What is redacted, and when.** Each of the following is tokenized before the session writes its row, its spill or its model-visible part: queued inbox text (the `loop/inbox` row and, above the per-event cap, its spill); user messages; text attachments (content and file name); tool results; the output of native-validation checks (the `check-result` audit payload, recorded with the source `tool/result` and the check's call ID); and the replacement text of operator compaction (`amc session compact`). Spills therefore hold the redacted text too. Compaction text is redacted before the edit is validated, so the size check sees the tokens, and its receipt is written on the resumed writer immediately before the compaction append.

**Declared fields.** Values that a signed tool definition declares in `protectedFields` (in the signed tools config, for example `patient.name: phi`) are tokenized first; the definition is matched by the tool name the session records for the call. Paths are dot paths into the tool's JSON result. An array applies the rest of the path to each element, and a path that ends at an object or array covers every string, number, boolean and object key beneath it. JSON held in a string leaf, at any depth (an MCP result's text block, an HTTP-style `body` inside it), is part of the result: a path that reaches such a string continues inside it, and every declared path also applies from the top of each such string, so a bare `patient.name` covers an MCP text block and a `body` within it. A string, number or object key that a declared path tokenized is tokenized wherever else the result repeats it whole, as a string leaf, number or key, outside that JSON or inside it, so `structuredContent.patient.name` also covers the text block's copy. This holds however short the value is, and a declared object whose keys repeat the result's own structure (`type`, `text`) tokenizes those keys elsewhere too. A declared boolean covers only the copies its path reaches, because recording it would tokenize every `true` or `false` in the result; a tool that mirrors `structuredContent` in its text block should declare both paths, or a bare path, which also applies inside the text. A repeat as a JSON string, key or number inside text the detectors do not parse (JSON nested more than one level inside a string, JSONL), as it is or decoded, tokenizes that whole text; a repeat inside other free text is left to the detectors. The repeat lookup is indexed once per result, so it takes time linear in the text however many values are declared. Declared fields bind a declaring tool's result in every outcome, because a failing tool can still return the record: an `OK` result must be JSON (otherwise `declared_fields_unparseable`), while error, denial and cancellation text that is not JSON gets the detectors only. The static notice the tool seam puts before an unknown outcome's output (`[amc] outcome unknown: ...`, which every journaled call that ends `outcome_unknown` carries) is set aside when it matches exactly, and the output after it is redacted as itself, so a JSON record there still gets its declared fields. A parsed result is always committed as its re-serialization, never as its original bytes, so what is committed is exactly what was inspected: a duplicate key keeps only its last value, as the parse does. Every number keeps its literal, and a declared number is tokenized from that exact text. A declared value or key that is a token this workspace issued is left as it is. An unsigned tools config declares nothing. A signed config that no longer verifies, or a result whose call the session never recorded or whose call ID two calls share, while some tool declares fields, is refused (`declared_fields_unverifiable`). So is every Code Mode (`run_code`) result, in any outcome, while some signed tool declares fields, because the program received the declaring tools' output raw and can return it.

**Detectors over the committed text.** The admission detectors are the backstop over all of this text, with the same noise filters. Text that is JSON (an object, an array or a string) is scanned as a JSON reader sees it: every string leaf and key decoded, every number as its literal, and JSON inside a string leaf (an MCP result's text) decoded the same way, one level deep. Escaped, a value right after `\n` or `\t` has no word boundary in front of it, so the patterns would miss it. Some detections need the member name beside its value, so each string or number leaf is also checked with the name it sits under (an array's items with their member's): any non-empty value of a member named `password`, `passwd`, `pwd`, `secret`, `client_secret`, `api_key`, `apikey`, `access_token`, `refresh_token`, `private_key` or `aws_secret_access_key`, and a value of eight characters or more under a name that ends in a secret word or an API-key word (`DB_PASSWORD`, `dbPassword`, `db.password`, `SECRET_KEY`, `GITHUB_TOKEN`, `x-api-key`, `openaiApiKey`, `vault_passphrase`), is a credential; a bare `token` name is not enough, because usage counters use it (its value still counts when the name beside it reads as an env secret line, `token: <eight or more non-space characters>`), and neither is a page cursor (`nextPageToken`, `NextToken`, `continuation_token`), which the model must send back as it is, or a name that only starts with an API-key word (`api_key_name`). The name is also read as words and scanned beside the value (`medical record number: A1234567`, `passport: X1234567`), so a keyword-bound ID whose keyword is its member name (`mrn`, `passportNumber`, `national_id`) is found. Either tokenizes the whole value. Such JSON is committed as its compact re-serialization, whatever the source's layout, only when something in it was tokenized, or when it repeats a key, whose earlier value the parse drops unread; otherwise its bytes are committed unchanged. Neither is scanned again as a whole, so tokens longer than the values they replace never push committed JSON over the 1,048,576-character limit, which applies to the input. Text that is not one JSON document (JSONL, a log-prefixed line) and JSON nested more than one level inside a string are scanned as they are and then searched decoded: with their JSON escapes, their percent-encoding (a form's `+` between letters or digits read as a space), their HTML character references, or their base64 and base64url runs of 24 characters or more that decode to UTF-8 text decoded, and so on for each new view, breadth first, up to 27 views, then each decoder in turn for up to 8 rounds (decoders that do not commute make a view per order, even on an ordinary page). So `alice%40example.com`, `%2B14155552671`, `4111+1111+1111+1111`, `alice&#64;example.com`, a value encoded twice in any order (`alice%2540example.com`, `alice&amp;#64;example.com`, JSON percent-encoded in a form field) and base64-encoded text (a mail body, a text resource blob) are found. Anything only decoding shows tokenizes the whole text, and text still changing after those rounds refuses (`detector_invalid`). The member and field rules below are not applied to a decoded view: decoding an escaped backslash before a closing quote leaves an escaped quote, so a member's value would run on to the next quote (MediaWiki's logged-out `csrfToken` script did that on every page). So does a redaction that scans more than 33,554,432 characters in all (leaves, decoded views, declared-repeat lookups and member contexts), so no result can stall the session that records it. Decoded text is never committed: decoded, an escaped quote ends a password value early and a backslash no longer separates words. Overlapping detections in a text merge into one token. In text that is not JSON, a JSON password detection replaces the whole quoted value, escaped quotes included. Besides the DLP provider keys (OpenAI legacy, project, service-account and admin keys, GitHub `gh[pousr]_` and `github_pat_` tokens, Stripe live keys, AWS access keys), the credential class covers the shared secret table's Anthropic, Slack and Google keys, bearer values that hold a digit, JWTs, a PEM private key block whole, a URL's password, `api_key`, `apikey` and `api_secret` assignments, a quoted member (JSON, a Python or JS literal such as `{'password': '...'}`, a string or a number, its quotes escaped once too, as JSON inside a JSON string has them), a form, query or command-line field (`password=...`, `client_secret=...`, `DB_PASSWORD=...` after a space) and a multipart form part whose name the member check above accepts, and env or YAML lines whose key ends in `PASSWORD`, `PASSWD`, `SECRET`, `SECRET_KEY`, `SECRET_ACCESS_KEY`, `PRIVATE_KEY`, `API_KEY` or `TOKEN` with a value of eight characters or more. A member, field or part whose name read as words beside its value completes a keyword-bound detection (`"mrn": "A1234567"` in JSONL or a log line, `passport_no=X9876543`) is a detection under that detector. Where such a rule names a key, only the value is tokenized. A token this workspace issued (its row is in the token vault, or the running redaction just made it) is not tokenized again; token-shaped text it did not issue is scanned as data.

**Evidence about tool output.** A plain SHA-256 of a short output, such as an SSN or a card number, can be brute-forced, so in an opted-in workspace evidence binds tool output with a keyed digest: HMAC-SHA256 under the workspace token HMAC key over `amc.output-digest/v1`, a zero byte and the output's SHA-256 hex. The tool pipeline decides the form once per call. The action journal's `outcomeDigest` binds the outcome's facts and that digest, and the bound object names its form (`outputSha256` for the plain form, `outputDigest: { kind: "hmac-sha256", value }` for the keyed one); the call's `stdout` evidence row carries the same field, so a verifier holding the output and the key knows which form to check. Outside opted-in workspaces both are byte-identical to before. If the token keys cannot load, the receipt is not written (the execution stays `started` and blocks the agent's journaled calls) and the evidence recorder failure latches, rather than bind nothing. In a redacting session, a `stdout` row that still carries a plain `outputSha256` (a delegate's report) has it replaced by the keyed `outputDigest`. The `web_fetch` and `web_search` receipts key their `contentSha256` and `deliveredSha256` the same way (`contentDigest`, `deliveredDigest`).

**Tokens and keys.** A token is `[[amc:<class>:<16 hex>]]`: the first 64 bits of HMAC-SHA256 over the class, a zero byte and the value, under a per-workspace key. One vault secret, `dataflow.token-keys.v1`, holds a 32-byte HMAC key and a 32-byte AES key, created from the OS CSPRNG on first use under a file lock. The keys are never logged. Like signing, a vault session evicted after its 30-minute lifetime is reopened from `AMC_VAULT_PASSPHRASE`; with no passphrase a locked vault refuses (`vault_unavailable`). The same value gives the same token within a workspace, so a model can refer to one record consistently. Another workspace's key gives a different token, and its rows do not decrypt under this workspace's key.

**Token vault.** `.amc/dataflow/token-vault.sqlite` maps each token to its value, encrypted with AES-256-GCM under a fresh random 96-bit nonce, with the token as additional data and the authentication tag verified on every read. A token already present must decrypt to the same value. A different value under the same 64-bit token is a collision and refuses the commit rather than overwrite (`token_collision`), whether the earlier value is in the vault or earlier in the same redaction. A row that does not verify refuses (`vault_integrity`). Telling an issued token from token-shaped text reads only whether the token's row exists; nothing is decrypted. `deleteTokens` deletes rows only through the P2-01 deletion gate, under the deletion target kind `token-vault`, so an active legal hold covering it refuses. The file holds the protected values themselves, encrypted. The default backup scope (`.amc`) includes it, as it includes the vault that holds its key, so a backup carries both. Only the detokenization gate decrypts rows (see "Purpose binding and restoration at egress" below).

**Failure refuses the commit.** Every failure throws `RedactionRefused` (code `REDACTION_REFUSED`) with a static reason, and the raw value is never committed. No value, file name or key appears in the error. The reasons are `vault_unavailable`, `vault_integrity`, `token_collision`, `receipt_failed`, `detector_invalid` (text over 1,048,576 characters, JSON nested too deeply to parse, text whose decoding still changes after 27 decoded views and 8 rounds of each decoder in turn, or a redaction that scans more than 33,554,432 characters), `content_not_text` (tool output or queued input that is not UTF-8), `attachment_not_redactable`, `declared_fields_unparseable`, `declared_fields_unverifiable`, `redaction_failed` and `runtime_unsupported`. Redaction needs number source text (`JSON.rawJSON`, Node 21 and later), so that a re-serialized number keeps its literal: on Node 20, which the package's `engines` field still admits, every redaction in an opted-in workspace refuses with `runtime_unsupported`, so tool output is withheld and other input is refused. A tool call must still be answered, so a refused tool result is not thrown: the session commits the static text `[amc] tool output withheld: protected-data redaction refused (<reason>)` as that call's result, keeping the tool's recorded outcome, after a `PROTECTED_DATA_REDACTION_REFUSED` audit row that names the call and the reason. Native-validation output is withheld the same way. The output itself is committed nowhere. In an opted-in workspace, image and audio attachments and media inbox input are refused as `attachment_not_redactable`, whatever the model provider's processor contract covers, and a tool result that holds media (an MCP image or audio block, or a resource blob whose `mimeType` is not text or JSON) is withheld with that reason; media input large enough to spill is refused before its spill commitment or object is written. Media stays refused under every processor contract: admitting it under a BAA needs the pinned provider route at commit time, which is later scope (P2-04).

**Receipts.** Each redaction writes one `PROTECTED_DATA_REDACTED` audit row, before the commit it describes, whose payload is a `RedactionReceiptV1` (`amc.redaction-receipt/v1`, `spec/schemas/v1/redaction-receipt.schema.json`). The receipt carries the session ID, the source (`user/message`, `user/attachment`, `tool/result`, `loop/inbox` or `operator/compaction`), the tool call ID, the detector-set digest, findings as class, detector and count, the declared paths that matched, and the SHA-256 of the redacted text. It never carries a raw value, a span or a hash of one. Failure to write the receipt refuses the commit (`receipt_failed`). Receipts are enforcement bookkeeping, never maturity evidence. The sources `gateway` and `bridge` are reserved in v1 for the plan's gateway and bridge receipts; gateway and bridge redactions write no receipt yet.

**Gateway evidence (opted-in workspaces).** Where the workspace opted in, the same detectors run over what the gateway stores (`redactBody`: request and response bodies, ToolHub evidence payloads). A detection becomes `[REDACTED]`, with a `protectedData:<class>` redaction reason, so `originalPayloadSha256` is omitted. These are unkeyed markers, not tokens, so nothing there is restorable, and the gateway holds no vault, so an issued token whose hex looks like data may be redacted again. JSON bodies are redacted key by key and leaf by leaf, so they stay valid JSON. A string leaf that holds a JSON object or array (an MCP result's text) is redacted the same way, one level deep, and re-stringified when anything in it changed. Every text is then scanned as it is and searched decoded, as in the session (JSON, percent, HTML and base64 views, breadth first, up to 27, then each decoder in turn), which covers JSON nested deeper, a duplicate key's earlier value, JSON that does not parse, JSON after a log prefix and values encoded twice. Anything only decoding shows replaces that text whole (`protectedData:unscanned`), because decoded text loses the escaped quotes inside a password value and the backslashes that separate words. Escaped, a value right after `\n` or `\t` has no word boundary in front of it, so a plain scan would miss it. A member's value is checked with its name as in the session: under a secret name it is replaced whole (`protectedData:credential`), and a detection only the name beside it shows (an MRN, a passport number) replaces it whole under that class. A JSON body that does not parse, or whose walk fails (nesting too deep, the scan budget), is stored as `"[REDACTED]"` (`protectedData:unscanned`), never as text. A body of another content type is scanned as text and then checked decoded: anything found there replaces the whole body the same way. Such a body that is not plainly UTF-8 (a charset parameter other than UTF-8, a byte-order mark, invalid UTF-8, or a zero byte, as UTF-16 text has) is not scanned: it is stored as `"[REDACTED]"` (`protectedData:unscanned`), because a reader of its declared charset would decode raw values the scan never saw. A form post's or multipart part's secret field (`password=`, `client_secret=`) is replaced by the credential rules above. A JSON integer that parsing rounded (beyond 2^53, so a 17-19 digit card number sent as a number keeps only its leading digits) can no longer be checked and is replaced whole (`protectedData:unscanned`). A text over the per-leaf limit is replaced whole, and once one body's scanned text (keys, leaves, decoded views and member contexts) passes 16,777,216 characters the whole stored body becomes `"[REDACTED]"` (`protectedData:unscanned`): nothing is stored unscanned. Hostile text can still take about 10 seconds of synchronous scanning per body before that bound is reached. Every text is also searched percent- and HTML-decoded, as in the session, so a form post holding `alice%40example.com` is replaced whole. A streamed body is a model's output in token-sized deltas, so a value is split across chunks and no single chunk shows it. The chunks are the `data:` events of a `text/event-stream` body, the lines of an `application/x-ndjson` body (Ollama) and the elements of a JSON body that is a top-level array (Gemini's default `streamGenerateContent`). After the scan, each chunk's delta strings (Anthropic's `delta.text`, `partial_json` and `thinking`, OpenAI's `delta.content` and `function.arguments`, the reasoning deltas `delta.reasoning` and `delta.reasoning_content`, the Responses API's `delta`, Gemini's `parts[].text`, Ollama's `message.content` and `/api/generate` `response`) are joined per stream (by path and by each object's `index`, `output_index` and `content_index`, so parallel tool calls stay apart) and all together in stream order, and the joins are scanned as they are and decoded. Anything they show, a chunk that is not JSON, or any failure of that pass stores the body as `"[REDACTED]"` (`protectedData:unscanned`). The stored request path and query are scanned the same way (a secret query field's value is replaced), and a query or path in which only decoding shows something is stored as `[REDACTED]`. Stored header values are redacted too. In every workspace, the credential headers listed under the denylist, `proxy-authorization`, `x-amz-security-token`, cookies and any header whose name ends in `token`, `secret`, `auth`, `session`, `password` or `api-key` (`x-auth-token`, `helicone-auth`, `x-portkey-api-key`) become `[REDACTED]`, and every other value gets the shared secret table and the configured `textRegexDenylist`. Where the workspace opted in, each value is also scanned like a stored text, with the header name as its member name, so an end-user email (`x-user-email`, `helicone-user-id`), a `referer` query, `x-forwarded-for` addresses and JSON metadata headers are redacted; a value whose scan fails is replaced whole, and the header reasons join the row's `redactionReasons`. Other workspaces store gateway bodies exactly as before this change. Traffic the gateway forwards is unchanged.

**Gateway credentials (every workspace).** Whatever the configured `headerKeysDenylist` says, the gateway stores the credential and lease headers it strips before forwarding (`x-amc-lease`, `authorization`, `x-api-key`, `x-goog-api-key`, `api-key`, `x-openai-key`, `x-anthropic-api-key`) and `cookie` and `set-cookie` as `[REDACTED]`, and the credential query keys (`key`, `api_key`, `api-key`, `access_token`, `amc_lease`) as `[REDACTED]` in the stored query. These headers are also in the default denylist, and the default `sk-` text pattern now also covers project and Anthropic keys (`(?i)sk-[A-Za-z0-9_-]{10,}`; it has no word boundary, because it runs over re-serialized JSON, where a key after a newline follows the escape `\n`); a signed gateway config keeps its own lists.

**ToolHub evidence (opted-in workspaces).** ToolHub's `tool_result` row applies the declared `protectedFields` of the same signed tools config: the session's walk (arrays fan out, an object or array end covers every key and leaf beneath it, JSON held in a string leaf is followed) replaces each declared value with `[REDACTED]`, and so is every repeat of one the session would tokenize (a whole leaf or key, or a JSON string or number inside JSONL or JSON nested deeper, as it is or decoded), before the detectors run. A tools config that no longer verifies, or a walk that fails, stores the body as `"[REDACTED]"`. A denial's message, which quotes the agent's arguments (`path '...' not in allowlist`), and the blast-radius consent, whose summary quotes argument paths, are stored redacted in payload and meta alike, and the consent digest is taken over the redacted copy, so it cannot be matched against guessed paths.

**Bridge evidence.** What the bridge stores as evidence (stdout and stderr telemetry, every key and leaf of object telemetry payloads such as the wrapped command's arguments, and the payloads of `POST /bridge/evidence`) goes through `bridgeEvidenceRedactor`: secrets in every workspace, and, where the workspace opted in, the same detectors, with `<AMC_REDACTED>` (a rounded JSON integer is replaced whole). There, text and string leaves are read as in the gateway: JSON one level deep, searched decoded (anything only decoding shows replaces the text whole), and a member's value checked with its name. Each stored value may take 4,194,304 characters of detector scanning, because the bridge's event loop also answers hook control decisions; past that, on any failure of the scan, or for text holding a zero byte (UTF-16 output read as UTF-8), the whole value is stored as the marker. Text the bridge hands back to an agent (control responses, deny reasons, steer text, the hook's stderr and `amc wrap`'s own terminal output), the hook identifier fields and the request summaries keep secrets-only `redactBridgeText`, as before this change, so the detectors never alter what an agent is told. `amc wrap` posts stdout and stderr telemetry a line at a time (or past 64 KiB) rather than per write, so a value the agent prints over two writes is scanned in one row; a partial line (a token stream, a spinner) waits at most 250 ms, the rest is flushed, and every row settled, before the exit row, and on SIGINT or SIGTERM what is pending is posted and settled (at most 1 s) before amc dies of the same signal. Where the workspace opted in, the same redactor covers the stored stdout and stderr rows of `amc adapters run`, of `amc monitor --stdin`, and of processes observed through `amc wrap <runtime>`, `amc supervise` and governed children (their forwarded stdin too). Elsewhere those rows are stored as they were: the diagnostic's transcript audits (`POLICY_VIOLATION`) and a delegated child's folded answer read them, and the secret table would remove the `api_key=` keyword or a password-less connection string they need. What the terminal shows is unchanged. In every workspace the redactor covers the command and arguments those processes are recorded with, each argument under the flag before it as its member name where the workspace opted in (`--password hunter2`, `--mrn A1234567`, curl's `-u name:password`): the `process_start` row (`amc wrap <runtime>`, wrap-any, `amc supervise`, governed children and sandbox runs), the `SANDBOX_EXECUTION_ENABLED` attestation and `amc adapters run`'s `agent_process_started` row, after the run's lease, AMC's own lease and the vault passphrase are replaced as the output scrub replaces them. `amc adapters run` in `SANDBOX` mode hands the container its environment by name (`docker run -e NAME`, each value read from docker's own environment) instead of as `export` lines in the shell script, so no environment value (the lease, the vault passphrase, an operator's tokens) is in the recorded argv. The shared secret table's URL-password pattern is bounded to 256 characters a side and stops at `/` and `"`, so it no longer runs from one URL through JSON members to a later `@`, or takes quadratic time on text without whitespace.

**Built-in privacy rules (every workspace).** `getBuiltInRedactionRules` and `applyRedaction` delegate to the DLP detectors and the shared secret table instead of carrying a second rule set, and never narrow what they redacted before: each built-in rule keeps its earlier pattern and redacts the union of its matches and the detector spans on the text it is applied to (the API-key rule applies its earlier keyword pattern exactly as before, then the shared table). So a 4x4 digit group that fails the Luhn check, any dotted quad, a bare 10-digit run, an email local part over 64 characters and the `token=` and `secret:` key forms are still redacted, and the detectors add Luhn-valid cards in other groupings, IPv6 addresses, E.164 phone numbers and provider key shapes. The earlier email pattern's matches are found in linear time; the regex alone backtracked quadratically inside long runs of local-part characters.

**Not covered.** The system prompt, tool schemas, model output (assistant text, tool-call arguments as the model wrote them and model-written compaction summaries), approval questions, the reason text of operator compaction, and rows written before the session was wrapped are recorded as they are. Names and other free-text identifiers outside declared fields are missed, and so are values split across JSON fields or lines. A member name is read only as far as the secret-name and keyword lists go (a `vat_number` member is not a VAT keyword), and a decoded view is searched without its member name. Base64 that decodes to binary (images, audio, PDFs) is not scanned: an opted-in session withholds a tool result that holds MCP media, but gateway, ToolHub and bridge evidence store such data as it is. The caller-supplied fields of a monitored process's rows (mode, agent ID, route URLs) are stored as they are. The stdout and stderr rows of `amc adapters run` and of the monitor are redacted write by write where the workspace opted in, so a value split across two writes is missed there (`amc wrap` joins a line first); there the shared secret table also replaces a whole `api_key=...` assignment, so the transcript `POLICY_VIOLATION` audit no longer sees it in those rows, and a delegated child's answer, folded from them, carries the markers. Admission decodes a tool result's escapes once, so it misses a value right after an escape in JSON nested inside one of its strings, and it does not decode percent-encoding or HTML references. `ask_user` answers are written raw to `.amc/native-tools/<session>/ask-user/<question>.answer.json`, signed by the answerer, and the `NATIVE_ASK_USER` receipt holds a plain `answerSha256`; `amc wire serve` stores each accepted request, its prompt included, in the acceptance row that the client's `requestSha256` binds. Plain digests outside a native session remain: the bridge's hook evidence digests a third-party agent's tool output, and ToolHub's own action journal digests its result. Fixtures, the labelled corpus, the detector quality report and the tests the issue lists are not written yet. Expert review of the PHI, card-data and processor rules is pending.

## Purpose binding and restoration at egress (P2-02, partial source)

**Tokenization is not de-identification or anonymization under any standard or regulation.** Restoration puts protected values back into a request only for a processor the operator declared; a signature over the registry and a contract reference prove neither that the declaration is true nor that the contract is legally sufficient. The PHI, card-data and processor rules are experimental until a named expert approves them.

**Configuration.** Both apply only in an opted-in workspace. The owner sets `runPurpose: <purposeId>` (one purpose per workspace, which must be a declared purpose) and `processors[].destinationIds` (the P2-01 destination IDs a processor operates; a destination has at most one processor) in `.amc/dataflow/processors.yaml` and signs it with `signProcessorRegistry` (owner mode, auditor key). Restoration also needs a signed `.amc/residency/destinations.yaml` whose destinations those IDs name. `.amc/**` is a protected path, so an agent cannot rewrite either file.

**Purpose at binding.** The authorization record's `resource` is decided in one place for the approval intent, the binding and the recheck: from the signed registry's `runPurpose`, never from arguments, model text, tool output or request bodies (a model-supplied `consent` or `purpose` argument is only part of the arguments digest). With no `runPurpose` it is `{ purpose: null, dataClasses: [] }`, as in workspaces that have not opted in. With one, it is that purpose and its allowed classes, and a call to a tool its `allowedTools` does not list is denied `purpose_violation` before any approver is asked. A registry that is missing after opt-in or does not verify denies `authority_store_unavailable`. The recheck recomputes `resource` and denies `purpose_violation` on any change, so re-signing the registry without the tool between bind and execution stops the call. Bridge hook calls and ToolHub journaling bind through the same code. Every bound call is covered: by default every class but `READ_ONLY` and `WRITE_LOW`, and every class under a compiled plan; unbound calls cannot restore anything. Tool names are matched exactly, so MCP tools (`mcp_<server>_<hash16>`), `run_code`, `delegate` and bridge hook tool names must be listed. The residency guard now receives the purpose's classes through the record.

**The gate.** `detokenize` (`src/dataflow/detokenizeGate.ts`) is the last step before `http.fetch` and native MCP over HTTP send: after the simulate return, the pipeline's recheck and approval consumption, and the journal's start, and synchronous with the send. Outside an opted-in workspace, or for arguments with no token, it returns the arguments unchanged. Otherwise it decides in this order, and nothing is decrypted until every policy check has passed:

1. The call must carry a bound authorization record with an execution ID and a non-null `resource.purpose`; otherwise `purpose_violation`.
2. The processor registry must verify, and its `runPurpose` must be the record's purpose; otherwise `purpose_violation`.
3. The destination (the exact `http.fetch` URL, or the pinned MCP endpoint) must pass the P2-01 egress check with the token classes and the purpose, and match a registered destination that a processor lists in `destinationIds`; otherwise `processor_not_allowlisted`. Stdio MCP has no destination, so a stdio call carrying tokens is refused this way.
4. The purpose must allow the tool, the processor and every class present (`purpose_violation`), and the processor must hold an effective, unexpired contract covering each class, a BAA for `phi` (`processor_not_allowlisted`). This is the rule model admission uses.
5. Every token's row is read before any key is loaded; a token this workspace never issued, including another workspace's, is `token_unknown`. A row whose class differs from its token's, or that does not decrypt, is `vault_integrity`; a vault that cannot be read is `vault_unavailable`.
6. Values are restored (below); a payload that cannot be restored safely is `payload_not_restorable`.
7. A `DetokenizationReceiptV1` is written as the `receipt` of a `PROTECTED_DATA_DETOKENIZED` ops audit row before the send; a write that fails or is not acknowledged is `receipt_failed`.

A refusal throws `DetokenizeRefused` (code `PROTECTED_DATA_EGRESS_REFUSED`, the message `Protected data egress refused: <reason>`), a definite failure: nothing was sent, the journal records `completed/not_applied`, and an MCP mount stays open. It also writes a `PROTECTED_DATA_EGRESS_REFUSED` ops audit row (severity HIGH) with the reason, execution ID, purpose, tool name, destination and processor IDs, classes and token count; a failed write never permits anything. Neither row, nor any error, holds a value, a token, a URL or a hash of one. The receipt records a release, not a delivery: the action journal has the outcome.

**What is restored.** `http.fetch` restores its body and headers, never its URL, so an API must take identifiers in the body. A body that is JSON is restored leaf by leaf inside the parse, so a value can never change its structure; a header value is restored only when it is one whole token whose value has no control character; anything else holding a token (a form body, a token inside other header text, a header name) is `payload_not_restorable`. A content-length header the model supplied no longer matches a restored body; Node then refuses the request and nothing leaks. Native MCP over HTTP restores every argument key and leaf, JSON held in a string leaf included. MCP input schemas validate the tokenized arguments, not the restored ones. Restoring an MCP grant needs it bound, so its action class must be one that binds.

**Echoes.** Before the pipeline and the session see the response, restored values it echoes are turned back into tokens: a whole JSON leaf or key that equals a value, and inside other text any value of four characters or more. Shorter values inside text, and escaped or transformed echoes, are left to the session redactor at commit.

**What restoration never touches.** The record, the journal, the guards, the approvals and the evidence see only the frozen tokenized arguments, so approvers see tokens. Restored values exist in process memory while the request is sent.

**Not covered by the gate.** `web_fetch`, `web_search`, bash, `process.spawn`, `git.push`, `fs.write`, `ask_user`, `delegate` and a `run_code` program's own text send tokens as tokens; the purpose's `allowedTools` is the control there. ToolHub server `http.fetch` for external agents has no gate, because its callers hold raw values, not tokens. Model requests are never restored. Gateway and bridge provider traffic is not admitted for protected data; that gap predates this slice and is a follow-up. A processor's own onward sharing is a contractual matter AMC cannot enforce, and an attacker-controlled path on a covered host is narrowed only by the destination's `pathPrefixes`. Injected token-shaped text makes a send refuse (`token_unknown`), which fails closed. A provider schema with strict patterns may reject tokens.

## Summary

AMC's security architecture is designed around a single conviction: **trust in AI agents must be grounded in cryptographic proof of observed behavior.** The combination of tiered evidence, digital signatures, transparency logs, anti-gaming mechanisms, disciplined key management, clear trust boundaries, and evidence decay creates a system where scores are meaningful, verifiable, and resistant to manipulation.

The goal is not to make gaming impossible in theory — it's to make gaming harder than simply building a trustworthy agent.
