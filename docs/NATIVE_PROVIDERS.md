# Native provider routes

The native agent harness (`amc agent-loop run`, `amc agent-loop chat` and `guide`, `amc acp`, the schedules runner, `amc wire`, and the TypeScript and Python SDKs, which spawn `acp` and take the same reasoning, retention and retry options: `thinkingBudget`, `cacheRetention`, `maxRetries`, `retryMaxDelayMs`, `retryMaxProviderDelayMs` in TypeScript, `thinking_budget`, `cache_retention`, `max_retries`, `retry_max_delay_ms`, `retry_max_provider_delay_ms` in Python) sends model requests through AMC's own adapter seam: a route is pinned once per call, the request is committed in a signed `request/header` before any bytes leave, the credential is resolved per request by reference, the egress gate runs, and the settlement is signed. This page lists the routes `--provider` accepts, what each one sends, and the limits that hold in the current source build. Gateway templates (`docs/PROVIDERS.md`) are a different surface: they configure the recording proxy, not these routes.

`amc agent-loop providers --json` prints the bundled adapter contracts, explicit unknowns and the reporting rules. It never probes a server, a model, a credential or a cache. `docs/providers/CAPABILITY_MATRIX.md` lists, for every route here except the stub, what a contract test proved against a local fixture of that wire.

The OpenAI-compatible routes post to `<origin>/v1/chat/completions` with the unchanged `openai-chat@4` bytes, so a recorded request on any of them is reconstructable by the existing encoder. Their identity is honest: the signed header names the real provider id and the `openai-compatible-chat` adapter, whose capability contract marks `image-input`, `cache-read-usage` and `cache-write-usage` **unknown** for a generic endpoint (refused before spend when a request needs them; a reported `cached_tokens` is still recorded) and thinking (output and replay), audio, `image-output`, `video-input`, `prompt-cache-control` and the tool-result error flag **unsupported**. No catalog pricing attaches to them, so cost stays `unavailable` rather than borrowing OpenAI's price list. A server that streams output the shared Chat decoder does not decode (`reasoning_content` from a reasoning model, a `refusal`, audio, annotations or a legacy `function_call`) fails the request as `INVALID_REQUEST`, which is not retried, on these routes and on `openai`: the same request would fail the same way. Turn the server's separate reasoning output off, or use a route that decodes reasoning (`deepseek`, `ollama`). Perplexity and DashScope (Qwen) are not listed: their endpoints do not follow the `/v1/chat/completions` path convention and would need their own route; use the gateway templates or `--provider openai --base-url` (which signs `providerId: "openai"`, a known limit).

Origins were read from each provider's reference on 2026-11-07: Groq `https://api.groq.com/openai/v1` ([console.groq.com/docs/openai](https://console.groq.com/docs/openai)); Mistral `https://api.mistral.ai/v1/chat/completions` ([docs.mistral.ai/api](https://docs.mistral.ai/api/)); xAI `https://api.x.ai/v1` ([docs.x.ai/docs/api-reference](https://docs.x.ai/docs/api-reference)); OpenRouter `https://openrouter.ai/api/v1/chat/completions` ([openrouter.ai/docs/api-reference/overview](https://openrouter.ai/docs/api-reference/overview)); Together `https://api.together.ai/v1/chat/completions` ([docs.together.ai/reference/chat-completions-1](https://docs.together.ai/reference/chat-completions-1)); Fireworks `https://api.fireworks.ai/inference/v1/chat/completions` ([docs.fireworks.ai/api-reference/post-chatcompletions](https://docs.fireworks.ai/api-reference/post-chatcompletions)); LM Studio `http://localhost:1234/v1` ([lmstudio.ai/docs/app/api/endpoints/openai](https://lmstudio.ai/docs/app/api/endpoints/openai)); vLLM `/v1/chat/completions` on `vllm serve`'s default port 8000 ([docs.vllm.ai online serving](https://docs.vllm.ai/en/latest/serving/online_serving/)); llama.cpp `127.0.0.1:9931`, `POST /v1/chat/completions` ([tools/server/README.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)); Azure `https://<resource>.openai.azure.com/openai/v1/chat/completions` with the `api-key` header and no `api-version` ([Azure OpenAI v1 API](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/api-version-lifecycle)). `--base-url` always overrides, and AMC never probes an origin to pick one. Default credential references are used only against the provider's own documented origin; a different origin needs an explicit `--credential`, on `agent-loop run` and `acp` and equally in `agent-loop guide` and `chat`, which never carry a default reference to an `--base-url` override (`src/llm/nativeRouteDefaults.ts`). The guide accepts a path in `--base-url` only for the OpenAI-compatible routes, whose documented bases carry one. A local route without a credential is admitted only on a plain-http loopback origin (`127.x` or `[::1]`; `localhost` is not loopback).

Studio's native tasks (and A4 Forge builds, which run through them) offer their own reviewed set: `stub`, `openai`, `openai-responses`, `anthropic`, `deepseek`, `gemini`, `gemini-audio` and `ollama`. The OpenAI-compatible routes and Azure are not offered there, by design: that set is a contract repeated in the signed task-descriptor schema, Studio's OpenAPI schema and the A4 spec vocabulary, a browser-started task may not supply an origin (Azure needs one), and the local servers' fixed loopback ports (8000, 1234, 9931) are common to unrelated local services, which a browser user could otherwise make the Studio host call. Use them through `agent-loop run` or `chat`, `amc acp` or either SDK.

Not native in this build: Anthropic on Bedrock (SigV4 and the Converse event stream) and Anthropic or Gemini on Vertex (OAuth2 access tokens). Both remain gateway templates with operator-supplied upstream and auth, and are deferred with a sketch in the providers plan.

## Reasoning controls

`--thinking enabled|disabled`, `--reasoning-effort <value>` and `--thinking-budget <tokens>` (TypeScript SDK: `thinking`, `reasoningEffort`, `thinkingBudget`; Python SDK: `thinking`, `reasoning_effort`, `thinking_budget`) are mapped by `src/llm/reasoningParams.ts`, then validated by each provider's contract. Values are sent verbatim; AMC never remaps an effort name from one provider's vocabulary to another's, so the signed header only ever carries what the operator wrote.

| Provider | `--thinking` | `--reasoning-effort` | `--thinking-budget` |
| --- | --- | --- | --- |
| `deepseek` | `thinking: {type}` | `reasoning_effort` low, high, max | refused |
| `anthropic` | enabled: `thinking: {type: "adaptive"}` (Claude 4.6 and later), or manual `{type: "enabled", budget_tokens}` when a budget is given (Claude 4.5/4.6); disabled: `{type: "disabled"}` | `output_config.effort` low, medium, high, xhigh, max (admitted beside tools) | manual `budget_tokens`: at least 1024 and below `--max-tokens` |
| `gemini`, `gemini-audio` | `thinkingConfig.includeThoughts` (disabled also sets `thinkingBudget: 0`) | `thinkingConfig.thinkingLevel` MINIMAL, LOW, MEDIUM, HIGH | `thinkingConfig.thinkingBudget` (not with a level) |
| `ollama` | `think: true|false` | `think` low, medium, high, max (not with `--thinking`) | refused |
| `openai`, `openai-responses`, compat routes, `azure-openai`, `stub` | refused | refused | refused |

Limits:

- Anthropic models differ in what they accept, and AMC sends what the operator wrote. Anthropic's extended-thinking reference (read 2026-11-08) lists manual thinking (`thinking: {type: "enabled", budget_tokens}`, which `--thinking-budget` selects) as available on Claude Haiku 4.5, Sonnet 4.5 and Opus 4.5, deprecated but accepted on Opus 4.6 and Sonnet 4.6, and rejected with a 400 by Claude 4.7 and later, which take adaptive thinking (`--thinking enabled` without a budget) and `output_config.effort` (`--reasoning-effort`; Opus 4.5 accepts low, medium and high only, and Sonnet 4.5 and Haiku 4.5 reject effort). Claude Opus 5.5 and Sonnet 5.5 also reject `{type: "disabled"}`, and on Opus 5.5 thinking is always on. A model that rejects what was sent fails closed (`INVALID_REQUEST`, not retried) with the provider's message. Current models default thinking `display` to `omitted`, so adaptive thinking blocks usually arrive without text and are recorded as dropped (`dropped:empty`) thinking rows; AMC does not add a `display` value the operator did not write.
- A `redacted_thinking` content block (Anthropic's encrypted thinking, valid whenever thinking is enabled) is decoded as a thinking block with no text and recorded as a dropped (`dropped:empty`) thinking row; its `data` is never recorded or replayed. A truncated or malformed stream still fails as `TRANSPORT` and is retried; the partial usage it leaves can make budget admission refuse the retry (pre-existing budgets behaviour).
- Anthropic thinking (adaptive or manual) is admitted only with `--tools none`; `--reasoning-effort` alone asks for no thinking block and is admitted beside tools. `anthropic-messages@4` records thinking blocks but cannot replay them with their signature, so a thinking turn that also calls tools, a `--session` resume, a fork and `agent-loop chat` are refused at prepare by capability admission (`thinking-replay` unsupported) before any spend. Signed replay (`signature_delta` on a signed block row, an `anthropic-messages@6` encoder) is deferred (D-01).
- OpenAI `reasoning_effort` and Responses `reasoning.effort` are not sent: both decoders refuse reasoning output and admission marks `thinking-output` unsupported, so sending the parameter would be refused at prepare. Decoding reasoning items and summaries is deferred (D-05).
- `agent-loop chat` applies the same mapping before its first turn and forwards the flags to each turn's run, with two chat rules: tools-free DeepSeek chat needs `--thinking disabled` from the first turn, and Anthropic `--thinking enabled` is refused because the second turn could not replay the thinking block. The mappings reach run, chat, acp, schedules and both SDKs; the Python SDK applies the same provider gate before it spawns `acp`, which checks each provider's exact values at startup.

## Prompt caching

- Anthropic: `cache_control` breakpoints on the system text, the last tool and the last block of the last message since `anthropic-messages@2`; `--cache-retention long` pins `anthropic-messages@5`, which marks those breakpoints `ttl: "1h"`. Usage records `cache_read_input_tokens` and `cache_creation_input_tokens` as disjoint counts; the 5m/1h `cache_creation` detail is not recorded yet.
- OpenAI Chat and Responses: automatic caching; `cached_tokens` becomes `cacheReadTokens` (subtracted from `prompt_tokens`, refused when inconsistent); Responses also reports cache writes. `--cache-retention` pins `openai-chat@5` / `openai-responses@4`, which send a deterministic `prompt_cache_key` for the stable prefix and `prompt_cache_retention` `in_memory` (short) or `24h` (long).
- DeepSeek `prompt_cache_hit_tokens`/`miss`, Gemini `cachedContentTokenCount` and Ollama's optional count are recorded as reported; a missing count stays unknown, never zero.
- `--cache-retention` is refused for every other route, including the pi-ai routes and the OpenAI-compatible and Azure routes that share the OpenAI encoder: admission is keyed by adapter id (`anthropic-messages`, `openai-chat`, `openai-responses`), so the named compat and Azure routes never receive retention keys under a signed header that claims a retention they may ignore. The exception is deliberate and operator-made: `--provider openai --base-url <foreign origin> --credential <ref>` keeps OpenAI's adapter id, so it keeps retention too (and OpenAI's catalog identity); pointing the `openai` route at a server that is not OpenAI's wire is the operator's claim, and the signed header records the origin.

Per-request cache reads, the request hit rate and the token read share are reported by the run report, `amc session show` and chat (`docs/NATIVE_PROVIDER_CACHE_REPORT.md`).

## Retries and provider delays

Each route freezes a retry policy at registration (`normal`: 5 retries of `EMPTY_RESPONSE`, `RATE_LIMIT`, `SERVER`, `TIMEOUT`, `TRANSPORT` with 500 ms to 10 s jittered backoff; or `always`). The loop retries at the request boundary inside one step and writes a signed `loop/retry` row before each wait.

- `--max-retries <n>`, `--retry-max-delay <ms>` and `--retry-max-provider-delay <ms>` (TypeScript SDK: `maxRetries`, `retryMaxDelayMs`, `retryMaxProviderDelayMs`; Python SDK: `max_retries`, `retry_max_delay_ms`, `retry_max_provider_delay_ms`) set that policy from the command line on run, chat (forwarded to each turn), acp, schedules and the pi-ai routes; `--max-retries 0` gives up on the first failure. Each flag is bounded where it is parsed and the refusal names the flag: `--max-retries` 0 or more, `--retry-max-delay` 500 (the initial delay) through 2147483647, `--retry-max-provider-delay` from the local ceiling (`--retry-max-delay`, default 10000) through 2147483647.
- A provider's `Retry-After` (delta seconds or HTTP date) is honoured verbatim up to the route's provider ceiling, `backoff.maxProviderDelayMs` (`--retry-max-provider-delay`; default max(60 s, `maxDelayMs`)), which is separate from and never below the local backoff ceiling. A longer hint is clamped to the provider ceiling and the signed reason says so (`asked for 86400000ms, clamped to the route's 60000ms provider ceiling`). The loop has no turn deadline of its own, so the 60 s default applies where nothing else waits on the run: `agent-loop run` and the schedules runner, where the worst-case wait per step is 5 × 60 s with the default 5 retries. `amc acp` defaults the provider ceiling to the local one instead (`--retry-max-delay`, 10 s unless set), because every ACP client has a prompt deadline the child cannot see: the TypeScript SDK's `timeoutMs`, the Python SDK's `timeout` and Studio's native-task `turnTimeoutMs` are each 120 s by default, and a client that times out fails and ends the child. That keeps the worst case at about 50 s of waiting inside those deadlines. An ACP client raises it with `--retry-max-provider-delay` (TypeScript SDK: `retryMaxProviderDelayMs`, which the SDK always forwards, defaulting to `retryMaxDelayMs`, else 10 s), and should raise its own timeout with it. A clamped wait retries early and may meet the same 429, so the typed `RATE_LIMIT` ending after the retry budget is the bound, not a client timeout.
- On a 429 without `Retry-After`, the wait is read from the rate-limit reset header whose remaining counter the provider reports as 0: `x-ratelimit-reset-requests` / `x-ratelimit-reset-tokens` (durations such as `6m0s`, `1.5s`, `20ms`) or `anthropic-ratelimit-{requests,input-tokens,output-tokens}-reset` (RFC 3339). When several counters are exhausted the longest wait is taken; when none is, nothing is inferred and local backoff applies. The recorded failure names the header in `providerDelayHeader` beside `providerRetryAfterMs`, so a derived wait is never signed as a `Retry-After` the provider never sent; the `loop/retry` reason repeats the header name.
- A terminal condition that arrives as a 429 (a spend cap) still retries up to the budget with waits bounded by the provider ceiling; quota wording in the body is classified `QUOTA` and not retried.

There is no fallback model chain: a step retries on the exact route it pinned, and an exhausted budget ends the turn with the typed error and a provider-outage incident when the session journaled actions. An explicit, recorded chain is designed but deferred (see the providers plan, SH-05): the design must decide the chain before the outage incident is written, register every link at composition and resolve same-provider links, none of which the current composition does.

## Model catalog and cost

Every pinned route carries a model-metadata snapshot (`modelMetadata` in the header): context window, max output, modalities, reasoning, tiered pricing, source, as-of date and freshness, from the single table in `src/product/modelPricing.ts`. Cost is projected per request and per session from that snapshot; a provider-reported cost takes precedence, and a missing component keeps the estimate `partial` or `unavailable` rather than becoming zero. The table has ten rows with legacy dates, so for most current models the run report says `unavailable (model-price)`; that is the honest state. Adding current rows is deferred: the table's schema requires routing heuristics (`qualityScore`, `typicalLatencyMs`) that no pricing page states, so new rows would have to invent them, and the DeepSeek/OpenAI/Gemini protocols never report a cache-write count, which the projection lists as missing. Both are product-schema changes recorded in the providers plan (SH-03). Operator-reviewed snapshots can be attached to a route through `LlmRouteConfig.reviewedModels` (library seam; no command-line loader yet).

## Structured output and token counting

Tool schemas are the only schema-constrained channel. `response_format`, Responses `text.format` and Gemini `responseSchema` have no surface (deferred, D-03). There is no local or remote token counting; context pressure for compaction uses the previous request's reported prompt tokens (deferred, D-04).

## Credentials

Routes hold credential references, never values (`src/credentials/credentialRef.ts`); `amc credentials list|describe|set|unset` manage the layered local store. A reference appears in route config, argv and signed rows; its value is resolved per request and never recorded.
