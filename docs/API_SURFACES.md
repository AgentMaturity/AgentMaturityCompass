# API Surfaces

AMC exposes three HTTP surfaces with different contracts and auth models.

## 1) Lightweight Module API (`/api/v1/*`)

Scope:
- operational helper routes implemented in `src/api/*`
- intended for local/internal use, not internet-facing provider compatibility

Auth and stability:
- this surface is rate-limited and IP-filtered by Studio
- protected routes require a signed Studio session or the bootstrap `x-amc-admin-token`; agent and lease credentials cannot access internal `/api/v1` routes
- Studio applies the following centralized least-privilege role policy before a module router receives the request:

| Access class | Roles | Examples |
| --- | --- | --- |
| Read | `VIEWER`, `OPERATOR`, `APPROVER`, `AUDITOR`, `OWNER` | ordinary `GET`/`HEAD` status and report routes |
| Side-effect-free analysis | all human roles | Domain Proof inline checks, DLP redact/classify, Shield scanners, Enforce/Governor evaluation |
| Verify | `OPERATOR`, `AUDITOR`, `OWNER` | execution-ticket and work-order verification |
| Attest | `AUDITOR`, `OWNER` | evidence and Watch attestation |
| Approve | `APPROVER`, `OWNER` | execution-ticket issuance |
| Operate | `OPERATOR`, `OWNER` | diagnostics, assurance runs, imports, runtime runs, and exports |
| Owner control | `OWNER` | secrets, vault/key changes, identity, signing, policy, certificates, and control-plane configuration |

- sensitive read exceptions also fail closed: vault secret values require `OWNER`, while Studio logs require `OPERATOR`, `AUDITOR`, or `OWNER`
- unsupported HTTP methods require `OWNER` before normal route handling, and unknown state-changing routes default to `OPERATOR`/`OWNER`
- only the explicit public compatibility paths in `PUBLIC_API_V1_PATHS` bypass Studio auth
- treat the surface as internal and keep Studio network-restricted
- `amc api key create`, `amc api key list`, and `amc api key revoke` manage a local hashed key lifecycle, but those keys are not an accepted Studio HTTP auth carrier in the current runtime

Response envelope:
- most `/api/v1` routes return success as `{ "ok": true, "data": ... }`
- most `/api/v1` routes return errors as `{ "ok": false, "error": "..." }`
- exception: `GET /api/v1/health` returns the raw health payload

Webhook contract notes:
- Public OpenAPI schemas live in `website/openapi.yaml` under `WebhookSignatureHeaders`, `WebhookEventEnvelope`, `WebhookDeliveryRequest`, `WebhookAttemptReceipt`, `WebhookDeliveryReceipt`, `PortalWebhookPayload`, `OutcomeWebhookPayload`, and `ValueWebhookPayload`.
- `POST /api/v1/product/portal/submit` accepts `payload` as one of the portal, outcome, value, or generic webhook envelope schemas and includes examples in the OpenAPI file.
- Outbound webhook signatures use `x-amc-webhook-delivery-id`, `x-amc-webhook-attempt`, `x-amc-webhook-timestamp`, and `x-amc-webhook-signature`; the signature is HMAC-SHA256 over `<timestamp>.<body>`.
- `amc alert send` and `amc alert test` use the simple alert dispatcher and fail fast on non-2xx webhook responses.
- The integration dispatcher supports channel-level retry policy and dead-letter behavior for deterministic integration events; configure that path when delivery retries are required.
- Value KPI ingestion is a Studio-root route family, not an `/api/v1` module route. Single-workspace Studio accepts `POST /value/ingest/webhook`; host mode accepts `POST /w/:workspaceId/value/ingest/webhook`.
- Value webhook auth accepts an OWNER/OPERATOR Studio session, `x-amc-admin-token`, or `x-amc-webhook-token`.
- `x-amc-webhook-token` must match the vault secret stored at `value/webhook/token`. It is a bearer-style shared token compared with timing-safe equality; it is not an HMAC request signature and should not be sent in the query string or JSON body.
- Integration webhook helpers that are not listed above remain CLI/helper surfaces unless and until their route families are added to `API_ROUTE_REGISTRY`.

Common status codes:
- `200`, `201` success
- `400` invalid payload/params
- `404` missing resources
- `405` method mismatch (some routes)
- `429` rate limit (applied by Studio or Bridge/Gateway budget/lease enforcement)
- `500` internal errors

Rate-limit and retry contract:
- Studio's detailed API limiter returns `429` with `{ "error": "API rate limit exceeded" }` when a bucket is exhausted.
- Where the detailed limiter applies, responses include `x-ratelimit-limit`, `x-ratelimit-remaining`, `x-ratelimit-reset`, `ratelimit-limit`, `ratelimit-remaining`, and `ratelimit-reset`.
- Denied detailed-limiter responses also include `retry-after` in seconds. This follows RFC 6585's `429 Too Many Requests` pattern, where `Retry-After` can tell clients how long to wait before retrying.
- Bridge/Gateway lease and budget failures can also return `429` with JSON errors such as `lease rate limit exceeded` or `budget exceeded`; these are governance denials and are recorded as evidence, not generic transport failures.
- Clients should treat `429`, `502`, `503`, and `504` as retryable only when the operation is idempotent or has an AMC work-order/idempotency boundary. Use exponential backoff and respect `retry-after` when present.

SSE reconnect contract:
- Org realtime updates are available at `GET /events/org` and documented in `docs/REALTIME.md`.
- The org stream sends `retry: 15000`, emits events with `id: <summaryHash>`, and uses named event types such as `ORG_SCORECARD_UPDATED`.
- `/events/org` is a live-update stream, not a replay log. `Last-Event-ID` may be sent by clients for their own continuity logging, but missed org events are not replayed from that header today; reconnecting clients should refresh current state from a snapshot/read route.
